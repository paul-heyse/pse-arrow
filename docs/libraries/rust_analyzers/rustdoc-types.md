# rustdoc-types — Comprehensive Rust Library Reference

Target: rustdoc-types 0.61.0 · JSON schema version 61 · Researched October 29, 2026

## 1. Purpose and architectural position

`rustdoc-types` provides the strongly typed, Serde-compatible data model for rustdoc's structured JSON output. It exposes Rust's documented API surface as a navigable representation of items, types, signatures, generics, trait implementations, attributes, documentation, and relationships between definitions.

Its principal value is that it makes the results of rustdoc's compiler-backed semantic analysis accessible to independent Rust tooling without requiring that tooling to implement Rust's name resolution, type representation, or documentation processing from scratch.

The crate is an upstream-maintained mirror of the `rustdoc-json-types` definitions in the Rust compiler repository. It represents the JSON interchange format; it is not itself a parser, compiler frontend, type checker, or rustdoc execution engine.&#x20;

## 2. Core data model: a typed, ID-addressed API graph

The JSON output is organized as an entity collection with explicit references, rather than a recursively nested syntax tree.

### 2.1 `Crate` — root document

The root `Crate` contains:

| Field                                          | Meaning                                                            |
| ---------------------------------------------- | ------------------------------------------------------------------ |
| `root: Id`                                     | Identifier of the root module                                      |
| `index: HashMap<Id, Item>`                     | Detailed local items plus selected referenced external trait items |
| `paths: HashMap<Id, ItemSummary>`              | Path and kind metadata for referenced items                        |
| `external_crates: HashMap<u32, ExternalCrate>` | Crate-level dependency and provenance metadata                     |
| `crate_version: Option<String>`                | Version passed to rustdoc                                          |
| `includes_private: bool`                       | Whether private items were included                                |
| `target: Target`                               | Compilation target metadata                                        |
| `format_version: u32`                          | Version of the serialized schema                                   |

The `index` and `paths` maps serve different purposes: one provides detailed declarations; the other provides identity-oriented reference information. An ID can have a useful path summary without its full definition being available locally.

This is particularly important when analyzing a crate whose API depends heavily on types or traits from other crates.

### 2.2 `Item` — common envelope

Every indexed item has a common envelope containing its identity, metadata and kind-specific representation.

- Identity: `id`, `crate_id`, optional `name`.
- Source: optional `span`.
- Exposure: `visibility`, deprecation, stability and const stability.
- Documentation: `docs` and `links`, the latter resolving intra-documentation links to item IDs.
- Attributes: `attrs`, containing structured attribute representations.
- Semantic content: `inner: ItemEnum`.

This separates cross-cutting metadata from declaration-specific details. Consumers can apply common classification, indexing or documentation operations across item kinds before descending into their specialized representations.

A useful detail: `docs: None` means documentation is absent, whereas `docs: Some("")` means an explicitly present but empty docstring. They should not automatically be treated as equivalent in documentation-quality analysis.&#x20;

### 2.3 `Id` — scoped reference identity

In version 0.61.0, `Id` is a `u32` newtype that supports hashing, ordering, copying and Serde.

Its most important documented invariant is that IDs are valid only within one JSON document.

They are not guaranteed to be stable across builds, nor can the numeric IDs from two crate JSON documents be joined directly. Rustdoc expressly makes no guarantees about the internal numeric values.

Consequences:

- Within-document relationships should use `Id` directly.
- Cross-document analysis requires independently established identity.
- Persistent indexes should not treat `Id` as a durable symbol identifier.
- Semantic API comparisons require matching declarations using stronger evidence than the emitted ID alone.

The latter may involve crate identity, definition paths, item kind, signatures and provenance, with special handling for re-exports, generated items and multiple versions of the same crate.

Source: [https://docs.rs/rustdoc-types/0.61.0/rustdoc_types/struct.Id.html](https://docs.rs/rustdoc-types/0.61.0/rustdoc_types/struct.Id.html?utm_source=chatgpt.com)

### 2.4 Identity versus path spelling

`rustdoc-types` makes a useful distinction between several representations of names:

- `Item.name`: the item's optional declaration name.
- `Path.path`: the path spelling actually used at a reference site.
- `Path.id`: the referenced entity's ID.
- `ItemSummary.path`: a vector of fully qualified path components chosen by rustdoc.
- `Use.source` and `Use.name`: the source path and potentially renamed imported name.

Two `Path` instances can therefore reference the same item while using different spellings, such as `Vec`, `std::vec::Vec`, and `std::prelude::v1::Vec`.

Additionally, rustdoc documents that an `ItemSummary` exposes one implementation-selected path, not necessarily every valid public access path.

This makes it possible to distinguish definition identity, reference spelling and API reachability, rather than conflating all three into a string.

Source: [https://docs.rs/rustdoc-types/0.61.0/rustdoc_types/struct.Path.html](https://docs.rs/rustdoc-types/0.61.0/rustdoc_types/struct.Path.html?utm_source=chatgpt.com)

### 2.5 `ItemSummary` and `ExternalCrate`

`ItemSummary` contains `crate_id`, a `Vec<String>` path, and `ItemKind`. It supplies enough information to identify or link to an external declaration without requiring the dependency's entire item graph.

`ExternalCrate` provides:

- `name`: Rust crate name, which need not equal the Cargo package name.
- `html_root_url`: optional documentation root.
- `path`: the loaded crate artifact's path, typically an `.rlib` or `.rmeta`.

The artifact path is particularly useful for associating dependency metadata with the build that produced the documentation. It does not, on its own, establish a portable package identity.

For cross-crate analysis, this suggests a natural two-layer model: local IDs and edges inside each document, and an externally established mapping of referenced crates and declarations across documents.

## 3. Declaration and containment model

### 3.1 `ItemEnum` versus `ItemKind`

`ItemEnum` is the detailed tagged representation of declaration kinds. Version 0.61.0 covers 21 variants:

| Family                  | Representations                                              |
| ----------------------- | ------------------------------------------------------------ |
| Namespaces              | `Module`, `ExternCrate`, `Use`                               |
| Data declarations       | `Struct`, `StructField`, `Union`, `Enum`, `Variant`          |
| Callable declarations   | `Function`                                                   |
| Abstraction             | `Trait`, `TraitAlias`, `Impl`                                |
| Types and values        | `TypeAlias`, `Constant`, `Static`, `ExternType`, `Primitive` |
| Metaprogramming         | `Macro`, `ProcMacro`                                         |
| Associated declarations | `AssocConst`, `AssocType`                                    |

`ItemKind` is a lighter classification without the full declaration payload. It is used in summaries and can be obtained from an `ItemEnum` using `item_kind()`.

This distinction is useful for two-stage processing: classify or filter items cheaply, then inspect detailed payloads only where necessary. `ItemKind` also distinguishes procedural macro kinds such as attributes and derives, which are represented through the more general `ProcMacro` payload in `ItemEnum`.

### 3.2 Module containment

`Module` provides `items: Vec<Id>`, `is_crate`, and `is_stripped`.

The root module is a compiler-generated representation rather than necessarily corresponding to an explicit source declaration.

`is_stripped` indicates a module excluded from the public API that nevertheless contains re-exported public items. This is essential for correctly interpreting namespace boundaries: an implementation module can be private while declarations originating inside it remain publicly reachable elsewhere.

The module tree therefore provides a useful starting point for API navigation, but a public API cannot be completely characterized by recursively visiting public-looking modules and ignoring re-exports.

### 3.3 Re-exports

`Use` preserves:

- `source`: original imported path.
- `name`: name introduced into the importing scope.
- `id: Option<Id>`: referenced item, when applicable.
- `is_glob`: whether the import uses wildcard syntax.

The optional ID is meaningful. For example, a primitive-type re-export can have no referenced item ID.

Rustdoc also performs inlining and import normalization, influenced by visibility, `#[doc(inline)]`, `#[doc(no_inline)]`, `#[doc(hidden)]`, and whether an import comes from a private module.

These operations can affect the structure of the emitted documentation graph. An analyzer should distinguish explicit import records from items presented through rustdoc's inlining behavior.

## 4. Data declarations and structural completeness

`rustdoc-types` represents structural data definitions through declaration-specific records and ID references to their constituent items. This allows consumers to analyze fields, variants, discriminants, generics and associated implementations independently.

| Declaration   | Significant information                                               |
| ------------- | --------------------------------------------------------------------- |
| `Struct`      | `StructKind`, generics, implementation IDs                            |
| `Union`       | Field IDs, generics, implementation IDs                               |
| `Enum`        | Variant IDs, generics, implementation IDs, stripped-variant indicator |
| `Variant`     | `VariantKind`, optional discriminant                                  |
| `StructField` | Field type, with common item metadata in `Item`                       |
| `TypeAlias`   | Aliased type and generic parameters                                   |
| `Static`      | Declared type, mutability and expression                              |
| `Constant`    | Source-like expression and optionally evaluated value                 |

### 4.1 Shape-preserving treatment of hidden declarations

A subtle but consequential feature is that rustdoc preserves some information about stripped members:

- `StructKind::Unit` identifies unit structs.
- `StructKind::Tuple(Vec<Option<Id>>)` preserves tuple-field positions even when a field is not documented. A `None` position does not mean the field is absent from the actual Rust type.
- `StructKind::Plain { fields, has_stripped_fields }` provides listed field IDs and an explicit indicator when fields were removed.
- `Enum::has_stripped_variants` similarly distinguishes a complete-looking variant list from one that omitted private or hidden variants.
- `VariantKind` distinguishes plain, tuple and struct variants, including their corresponding stripped-field representations.

These flags are crucial when interpreting documentation as a schema. The absence of a field or variant from the JSON does not necessarily establish its absence from the compiled type.

This also affects API compatibility analysis. Public construction and exhaustive matching may depend on visibility, non-exhaustiveness and hidden members, not simply on the number of visible fields or variants.

### 4.2 Constants and discriminants

`Constant` exposes:

- `expr`: stringified source expression.
- `value: Option<String>`: a compiler-evaluated value when available, currently documented for numeric values.
- `is_literal`: whether the expression is a literal.

`Variant.discriminant` is optional and represents an explicitly supplied discriminant. An omitted discriminant should not be interpreted as the integer zero.

Stringified expressions and array lengths are useful for reporting and signatures, but they are not syntax trees and should not be assumed to preserve exact source spelling. Consequently, constant-expression equivalence cannot generally be established through raw string comparison.

## 5. Type representation: structural Rust type expressions

`Type` is one of the most valuable components of the crate. Rather than treating signatures as opaque text, it provides a recursive representation of Rust type expressions.

### 5.1 `Type` variants

| Representation                 | Captured semantics                                                |
| ------------------------------ | ----------------------------------------------------------------- |
| `ResolvedPath(Path)`           | Reference to a named type, with ID and optional generic arguments |
| `Generic(String)`              | Generic type parameter                                            |
| `Primitive(String)`            | Primitive type                                                    |
| `Tuple(Vec<Type>)`             | Ordered component types                                           |
| `Slice(Box<Type>)`             | Dynamically sized slice element type                              |
| `Array { type_, len }`         | Element type and stringified length expression                    |
| `BorrowedRef`                  | Borrowed type, optional lifetime, mutability                      |
| `RawPointer`                   | Pointed-to type and mutability                                    |
| `FunctionPointer`              | Function-pointer signature and qualifiers                         |
| `DynTrait(DynTrait)`           | Trait-object bounds and lifetime                                  |
| `ImplTrait(Vec<GenericBound>)` | Opaque `impl Trait` bounds                                        |
| `QualifiedPath`                | Associated type path with self type, optional trait and arguments |
| `Infer`                        | Inferred type placeholder                                         |
| `Pat`                          | Pattern-constrained type representation                           |

The `Pat` representation reflects newer Rust type-system syntax and should not be mistaken for general-purpose pattern-matching AST support. Its presence in the schema does not mean that every compiler or language feature producing it is stable.

### 5.2 Associated types and qualified paths

`QualifiedPath` carries a `name`, optional generic arguments, `self_type`, and optional `trait_`.

This permits structural representation of forms such as `<T as Iterator>::Item`, including the relationship between the self type and named trait. The trait field can be absent for inherent associated type paths.

This distinction matters for dependency analysis: a reference to an associated type introduces different semantic relationships from a simple reference to a concrete named type.

It also means that an analyzer can preserve the distinction between a declaration's nominal identity and a projection requiring further type-level reasoning.

### 5.3 Trait objects, opaque types and function pointers

`DynTrait` contains `PolyTrait` bounds and an optional lifetime. The bounds preserve distinctions between principal traits and additional bounds, including auto traits.

`ImplTrait` records its declared bounds but does not expose the hidden concrete type selected by the compiler.

`FunctionPointer` includes the function signature, header and higher-ranked generic parameters. This can distinguish function-pointer ABI and safety characteristics from ordinary callable trait bounds such as `Fn(A) -> B`.

These representations enable much more precise API inspection than name-based heuristics, but they remain surface-level type descriptions, not the compiler's complete internal type-inference representation.

### 5.4 Structural comparison versus semantic equivalence

Two types can be semantically related without having identical `Type` trees:

- Aliases can refer to the same underlying type.
- Different paths can reference the same nominal definition.
- Associated type projections can normalize under trait constraints.
- Lifetime elision and explicit lifetimes can lead to different representations.
- Const-generic expressions may have different textual forms.
- Generic parameters can be renamed without changing an API contract.

`rustdoc-types` supplies the information needed to construct structural comparisons and reference edges, but it does not implement alias expansion, trait solving, type normalization or a complete Rust type-equivalence algorithm.

## 6. Generics, bounds and associated-item constraints

The generic model is unusually expressive for a documentation interchange format. It retains several distinctions needed for interpreting advanced Rust APIs.

### 6.1 Declarations: `Generics` and `GenericParamDef`

`Generics` comprises `params` and `where_predicates`.

`GenericParamDefKind` supports:

- Lifetime parameters: declared lifetime and outlives relationships.
- Type parameters: trait/lifetime bounds, optional default type, and `is_synthetic`.
- Const parameters: const parameter type and optional default expression.

`is_synthetic` is significant because rustdoc can represent argument-position `impl Trait` using compiler-generated generic parameters. These should not be presented as user-authored, explicitly named parameters.

Bounds attached to a parameter and predicates appearing in a `where` clause are separate parts of the model. An effective constraint analysis examines both.

### 6.2 Argument syntax: `GenericArgs`

`GenericArgs` distinguishes:

| Variant              | Meaning                                                              |
| -------------------- | -------------------------------------------------------------------- |
| `AngleBracketed`     | Lifetime, type and const arguments, plus associated-item constraints |
| `Parenthesized`      | Callable-trait syntax such as `Fn(A, B) -> C`                        |
| `ReturnTypeNotation` | Return type notation such as `T::method(..)`                         |

Individual `GenericArg` values can represent a lifetime, type, constant or inference placeholder.

`AssocItemConstraint` separately represents associated-item equality bindings and bounds. This captures the difference between a constraint specifying an associated item and one restricting its capabilities.

For example, `Iterator<Item = T>` and `Iterator<Item: Clone>` impose different requirements and should not collapse into the same generic-argument representation.

### 6.3 `GenericBound` and `WherePredicate`

`GenericBound` includes:

- `TraitBound` with a referenced trait path, higher-ranked parameters and modifier.
- `Outlives` for lifetime relationships.
- `Use(Vec<PreciseCapturingArg>)` for precise captures in opaque types, including lifetime and type-parameter captures.

`TraitBoundModifier` distinguishes ordinary bounds, conditional `?Trait`-style bounds such as `?Sized`, and `~const`-related bounds.

`WherePredicate` captures:

- `BoundPredicate` for bounds on a type, including higher-ranked binders.
- `LifetimePredicate` for explicit lifetime outlives constraints.
- `EqPredicate` for type or constant equalities.

The right-hand side of an equality uses `Term`, which distinguishes type terms from constant terms.

### 6.4 Higher-ranked and associated-type relationships

Higher-ranked generic parameters appear in multiple places: trait bounds, where predicates, polymorphic trait bounds and function pointers. Consumers must account for their binding scope, not merely record every lifetime as a free-standing string.

A structural representation can support extraction of relationships such as:

- `T` must implement a referenced trait.
- An associated type is constrained to equal another type.
- A bound applies under `for<'a>` quantification.
- An opaque type explicitly captures selected lifetime and type parameters.
- A const generic parameter has a declared type and default.

These are useful inputs for interface constraint graphs, API search and compatibility analysis. They do not by themselves determine whether a particular concrete substitution satisfies a complete set of bounds.

## 7. Traits, implementations and associated items

The trait model is a major strength of rustdoc JSON. It exposes explicit relationships between traits, implementation blocks, implementors and associated declarations that would otherwise require extensive parsing and resolution machinery.

### 7.1 Trait declarations

`Trait` contains:

| Field                      | Significance                                                     |
| -------------------------- | ---------------------------------------------------------------- |
| `is_auto`                  | Auto-trait designation                                           |
| `is_unsafe`                | Unsafe trait contract                                            |
| `is_dyn_compatible`        | Whether the trait is dyn-compatible, formerly called object-safe |
| `items: Vec<Id>`           | Required and provided associated declarations                    |
| `generics`                 | Generic parameters and where predicates                          |
| `bounds`                   | Supertrait and other relevant bounds                             |
| `implementations: Vec<Id>` | Implementation items reported by rustdoc                         |

This allows several useful distinctions without reconstructing declarations from source text.

For example, a trait that can be used as `dyn Trait` has an explicit dyn-compatibility indicator; a tool need not approximate the relevant rules solely by inspecting method signatures. That indicator describes the compiler's assessment in the documented context, not an independent implementation of the dyn-compatibility rules.

`TraitAlias` separately provides generic parameters and the bounds making up an alias. Its presence in the JSON schema does not imply that the Rust trait-alias language feature is stable.

### 7.2 Implementation blocks

`Impl` exposes:

- `trait_: Option<Path>` — implemented trait, or `None` for an inherent implementation.
- `for_: Type` — the type receiving the implementation.
- `generics` — implementation-level parameters and constraints.
- `items: Vec<Id>` — associated declarations explicitly represented within the block.
- `provided_trait_methods: Vec<String>` — names of trait methods inherited through their defaults rather than written in the implementation.
- `is_negative` — explicit negative implementation.
- `is_synthetic` — compiler-generated implementation, notably for auto traits.
- `blanket_impl: Option<Type>` — additional information identifying blanket implementations.
- `is_unsafe` — unsafe trait implementation.

These fields distinguish several substantially different relationships:

| Implementation category             | Important interpretation                                                |
| ----------------------------------- | ----------------------------------------------------------------------- |
| Inherent implementation             | Defines associated functionality without implementing a trait           |
| Explicit trait implementation       | Provides a declared `Trait`-for-`Type` relationship                     |
| Blanket implementation              | Applies to a family of types subject to generic constraints             |
| Negative implementation             | Explicitly excludes a trait implementation                              |
| Synthetic auto-trait implementation | Derived by the compiler rather than directly declared by the programmer |

A method's absence from `Impl.items` does not necessarily mean the method is unavailable on that implementation: default trait methods are separately recorded in `provided_trait_methods`.

Likewise, a negative implementation must not be counted as a positive capability. Synthetic implementations should remain distinguishable from explicitly authored ones, especially when constructing dependency or implementation provenance graphs.

### 7.3 Associated types, constants and methods

Associated items are represented through `ItemEnum`:

- `Function(Function)` for associated methods and functions.
- `AssocType { generics, bounds, type_, default_unstable }`.
- `AssocConst { type_, value, default_unstable }`.

The associated-type representation is sufficiently expressive for generic associated types, their bounds, and optional default definitions.

An `AssocType.type_` may be absent in a trait declaration without a default, but is present for an assignment within an implementation. This permits distinguishing a requirement from a provided definition.

### 7.4 The important distinction between item stability and default stability

Version 0.60 introduced `ProvidedDefaultUnstable` for trait functions, associated types and associated constants.

Its `feature` identifies a feature gate needed to use an unstable provided default.

This captures a subtle but consequential possibility: a trait item can itself be stable while its default implementation or default value remains unstable.

For accurate compatibility analysis, the following are separate questions:

1. Is the trait item stable?
2. Can callers use it in a const context?
3. Is the default implementation or value stable?

Conflating them can incorrectly classify an interface as fully usable on stable Rust.

### 7.5 Completeness boundary

The implementation graph can support trait search, implementor inventories, method availability analysis and approximate interface dependency graphs.

It is not a complete trait solver. In particular, the presence of a generic blanket implementation does not establish that an arbitrary concrete type meets its constraints, nor do the reported implementations constitute a closed-world guarantee for all possible downstream types.

## 8. Functions, calling conventions and macros

### 8.1 Function signatures and qualifiers

`Function` is divided into three main parts:

| Component                | Information                                         |
| ------------------------ | --------------------------------------------------- |
| `sig: FunctionSignature` | Inputs, optional explicit output, C variadic status |
| `generics: Generics`     | Type/lifetime/const parameters and constraints      |
| `header: FunctionHeader` | Constness, safety, async status, ABI                |

`FunctionSignature.inputs` is a vector of `(String, Type)` pairs. The string may represent a parameter pattern rather than a valid Rust identifier; treating it as an identifier in code generation would be unsafe.

`output: None` means no explicit output type is specified. This differs from an explicit `-> ()` annotation, even though both describe unit-returning functions.

`Function.has_body` captures whether a function has an implementation, particularly important when interpreting required trait methods versus provided defaults and externally declared functions.

The `header` separates `is_const`, `is_unsafe`, and `is_async`, which are different dimensions of the interface contract.

### 8.2 ABI modeling

`Abi` distinguishes the Rust ABI from C-family, system and platform-specific calling conventions.

Recognized variants include `Rust`, `C`, `Cdecl`, `Stdcall`, `Fastcall`, `Aapcs`, `Win64`, `SysV64`, `System`, and `Other(String)`.

For calling conventions that support it, an `unwind` flag distinguishes forms such as `extern "C"` and `extern "C-unwind"`.

This is useful for FFI interface inventories and detecting signature-level ABI changes. However, the representation does not calculate concrete type layout, field offsets, register assignment, or the safety of an FFI boundary.

### 8.3 Declarative and procedural macros

`ItemEnum` distinguishes:

- `Macro(String)` — declarative macro definition represented in textual form.
- `ProcMacro(ProcMacro)` — procedural macro declaration.

`ProcMacro.kind` distinguishes function-like, attribute, and derive procedural macros. Its `helpers` list represents helper attributes recognized by derive macros.

This is valuable for identifying the interface offered by a macro crate. It does not provide an executable expansion engine, the expanded syntax for every invocation, or a behavioral specification of arbitrary procedural macro implementations.

Similarly, deriving a trait in source can produce additional definitions that rustdoc represents, but a documentation record alone is not a complete account of how every macro-expanded token originated.

## 9. Attributes, visibility, stability and documentation

### 9.1 Structured attributes

`Attribute` represents several significant Rust attributes as typed variants:

| Variant                    | Extractable information                                |
| -------------------------- | ------------------------------------------------------ |
| `NonExhaustive`            | Non-exhaustiveness of an API declaration               |
| `MustUse { reason }`       | Use-result requirement and optional rationale          |
| `MacroExport`              | Macro export designation                               |
| `ExportName(String)`       | Explicit exported symbol name                          |
| `LinkSection(String)`      | Linker section designation                             |
| `AutomaticallyDerived`     | Derived-code marker                                    |
| `Repr(AttributeRepr)`      | Representation and alignment attributes                |
| `NoMangle`                 | Symbol-name preservation attribute                     |
| `TargetFeature { enable }` | Per-function target feature declaration                |
| `Other(String)`            | Attributes without dedicated structured representation |

This removes the need to independently parse many common attribute forms.

`AttributeRepr` additionally exposes a representation kind and optional alignment, packing and integer-representation details. It is useful for identifying ABI-sensitive declarations, but is not equivalent to computing actual layout.

A major compatibility caveat concerns `Attribute::Other`: upstream explicitly excludes changes to its textual representation from the `FORMAT_VERSION` compatibility promise. Consumers that parse `Other(String)` must treat its content as less stable than the dedicated typed variants.

The regular `attrs` collection does not duplicate every semantic attribute. Documentation, deprecation, ordinary stability, const stability and unstable defaults have their own dedicated fields.

### 9.2 Visibility is not equivalent to public reachability

`Visibility` has four variants:

- `Public`: explicitly `pub`.
- `Default`: ordinarily private, but with exceptions for public-trait associated items and public-enum variants.
- `Crate`: `pub(crate)`.
- `Restricted { parent: Id, path: String }`: scoped visibility such as `pub(in crate::module)`.

For public API analysis, declaration-level visibility is only one input.

Public reachability also depends on namespace containment, re-export paths and the specific rules governing traits, variants and their members. Re-exported declarations can originate in private modules.

Therefore, an API index based solely on `Item.visibility == Public` would misclassify some declarations and fail to represent every valid public access path.

### 9.3 Stability and deprecation

`Stability` provides a named `feature` and a `StabilityLevel` of `Stable { since }` or `Unstable`.

The item model separates:

- `stability` — ordinary use of the item.
- `const_stability` — use in const contexts.
- `default_unstable` — an unstable provided trait default, where applicable.
- `deprecation` — deprecation metadata including `since` and optional note.

These fields are especially relevant to the Rust standard library's feature-stability system. For ordinary third-party crates, missing stability metadata is normal and must not be interpreted as either an affirmative stable or unstable status.

Also, stability of a name reached through a re-export can depend on the path through which it is accessed, not exclusively on the underlying definition.

### 9.4 Documentation links and source provenance

`Item.docs` contains documentation text when available, and `Item.links` maps resolved intra-documentation references to item IDs.

This makes documentation-linked API discovery possible: references embedded in prose can connect to the same underlying item index as signatures and trait implementations.

`Span` supplies a source file and `(line, column)` positions. Both begin and end coordinates are one-indexed in the current schema. The filename is relative to the path with which rustdoc was invoked.

Source locations are optional, and macro-generated or compiler-synthesized items may not have a straightforward original source span.

Taken together, the fields support a rich reference index combining declarations, signatures, documentation text, source navigation and intra-documentation links. They do not constitute an exact source-preserving parser, because rustdoc may normalize, inline, omit or synthesize declarations.

## 10. Compilation target, feature availability and configuration scope

### 10.1 Target-specific metadata

The root `Crate.target` contains a target triple and a collection of `TargetFeature` records.

Each `TargetFeature` exposes:

- `name`: feature name.
- `implies_features`: other features implied by this one.
- `unstable_feature_gate`: optional gate required to enable the feature.
- `globally_enabled`: whether the feature is enabled for the compilation session.

At the declaration level, `Attribute::TargetFeature { enable }` records target features requested through attributes such as `#[target_feature(enable = "avx2")]`.

This provides two complementary perspectives: features available for a target and features requested by particular declarations.

The metadata can inform CPU-feature inventories, platform-specific API references and FFI analysis. It does not establish that a machine executing the code supports a particular instruction set.

### 10.2 JSON output is a compilation-context projection

A rustdoc JSON document represents the API observed under the compilation and documentation configuration used to produce it.

That context can include:

- The target triple and target features.
- Cargo feature selection.
- Conditional compilation through `cfg`.
- Compiler and rustdoc version.
- Availability of unstable language features.
- Private-item inclusion and documentation-hiding behavior.
- Dependencies selected and compiled for the target.

This creates an important difference between the documented API for one configuration and the union of APIs available across all supported configurations.

For instance, a function compiled only for a particular operating system may not appear in the JSON generated for another target. No analysis of the resulting `ItemEnum` values can reconstruct an item that was excluded before documentation generation.

`includes_private` indicates whether private declarations were requested, but it does not certify that all source-level declarations and generated constructs have been preserved.

For configuration-complete inventories, multiple rustdoc runs with independently established build configurations may be necessary. Combining those outputs then introduces cross-document identity and provenance questions.

## 11. Data ingestion, serialization and performance

### 11.1 Generating and consuming rustdoc JSON

The upstream-documented generation command is:

`cargo +nightly rustdoc -- --output-format json -Z unstable-options`

The produced JSON can be deserialized directly into `rustdoc_types::Crate` using `serde_json`.

`rustdoc-types` itself includes Serde serialization and deserialization support. `serde_json` is not a required dependency of the published crate; consumers requiring JSON parsing supply it separately.

The basic data path is:

Rust source + compilation configuration

rustc / rustdoc

Name resolution, semantic analysis, documentation processing

Versioned rustdoc JSON

Serde + rustdoc-types

Typed declarations, references and metadata

Consumer-defined analysis and indexes

The library does not provide a higher-level query engine or a built-in persistent symbol graph. Its role is to provide the typed foundation from which those structures can be derived.

### 11.2 Optional `rustc-hash` feature

The `rustc-hash` feature replaces the crate's standard hash maps with `rustc_hash::FxHashMap`.

The intent is faster hash operations during deserialization and repeated item lookups, particularly for large documents.

The upstream documentation cites a `cargo-semver-checks` benchmark using approximately 500 MB of `aws_sdk_ec2` JSON, reporting roughly a 3% runtime improvement.

That result is workload-specific. The benefit depends on how much overall work involves hashing and map access rather than JSON parsing, allocating, traversing types or performing downstream computation.

`FxHashMap` also uses a fast, noncryptographic hashing strategy and may experience more collisions under some workloads. Its availability does not establish that it will improve every application.

### 11.3 Optional `rkyv_0_8` feature

The `rkyv_0_8` feature derives `rkyv` 0.8's `Archive`, `Serialize` and `Deserialize` traits for the library's data types.

It also makes archived representations such as `ArchivedId` available.

This enables a materially different data-processing model:

- Convert the typed representation into an archived binary representation.
- Persist or reuse the archive.
- Access archived fields and collections without eagerly reconstructing every owned Rust value.
- Deserialize selected values when owned data is required.

The distinction is important: rkyv does not directly make the original JSON zero-copy. Its zero-copy advantages apply to data represented in the rkyv archive format.

This capability is especially relevant when a large, relatively static API dataset must be queried repeatedly. The initial JSON-to-archive conversion has a cost, which may be justified by subsequent reads and selective access.

Archive validation, schema compatibility and the lifetime of backing bytes are independent considerations. `rustdoc-types` supplies archive-compatible types, not a complete cache management system.

### 11.4 Data representation tradeoffs

| Representation                  | Strength                                             | Principal constraint                                          |
| ------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------- |
| JSON file                       | Interchange, inspection, broad tooling compatibility | Text parsing and potentially substantial allocations          |
| Owned `Crate`                   | Native typed traversal and mutable processing        | Materializes the object graph in memory                       |
| Owned `Crate` with `rustc-hash` | Potentially faster map-intensive work                | Workload-dependent gain and different collision behavior      |
| rkyv archive                    | Repeated reads and selective archived access         | Requires archive creation and compatible archive handling     |
| Derived application index       | Search, graph queries, persistent stable keys        | Consumer must define its own identity and normalization rules |

## 12. Versioning, schema evolution and compatibility

### 12.1 Format versions are operationally significant

`rustdoc-types 0.61.0` defines `FORMAT_VERSION = 61`.

The project's changelog states that the package version was deliberately aligned with the JSON format version beginning with crate release 0.46.0. This is a project convention, not an inherent relationship between Cargo semantic versions and arbitrary JSON schemas.

The version carried inside a JSON document remains the authoritative signal for the format of that particular artifact.

The unstable output format creates two independent compatibility questions:

1. Can the selected `rustdoc-types` release deserialize the document?
2. Can the consumer's interpretation of the fields produce the intended semantic result?

Successful deserialization is not sufficient evidence of semantic compatibility. Fields may be omitted by the producer, textual representations may vary, or the build configuration may differ from an earlier extraction.

### 12.2 Recent significant changes

| Version | Relevant changes                                                                                       |
| ------- | ------------------------------------------------------------------------------------------------------ |
| 0.54.0  | `Item.attrs` changed from strings to structured `Attribute` values, including `Other`                  |
| 0.57.0  | `ExternalCrate.path` added for stronger dependency artifact resolution                                 |
| 0.57.1  | `ItemEnum::item_kind()` added                                                                          |
| 0.58.0  | `Item.stability` added                                                                                 |
| 0.59.0  | `Item.const_stability` added                                                                           |
| 0.60.0  | `default_unstable` added to functions and associated type/constant representations                     |
| 0.61.0  | Format version advanced to 61; the published changelog does not yet describe specific semantic changes |

### 12.3 Compatibility boundaries for durable consumers

For tools retaining or comparing JSON across releases, the following distinctions matter:

| Issue                            | Consequence                                                       |
| -------------------------------- | ----------------------------------------------------------------- |
| Different `format_version`       | Typed deserialization may fail or silently omit newer information |
| Changed numeric `Id` assignments | IDs cannot establish cross-build identity                         |
| Different compiler or rustdoc    | Different normalization, extraction or generated representation   |
| Different features or target     | Different observed API surface                                    |
| Re-export inlining               | Structural location may differ from original source hierarchy     |
| `Attribute::Other`               | Textual representation is explicitly less stable than the schema  |
| Different crate artifact paths   | Provenance paths may not be portable across machines              |
| Different package versions       | A name alone may identify distinct external declarations          |

For incompatible formats, handling the document with a schema-compatible crate version or an explicit conversion layer is more reliable than assuming the latest definitions deserialize all historical outputs.

A version preflight can inspect the top-level `format_version` before converting the complete document into `rustdoc_types::Crate`. This matters because a typed deserialization error may occur before the application has access to that field.

### 13.2 Capability combinations

The library's features support several general architectural patterns.

Public API and type-dependency graph: Starting from `Crate.index`, a consumer can connect module containment, trait implementations, type references, generic bounds, associated items and documentation links. External references can be enriched through `paths` and `external_crates`. This removes much of the need for custom Rust syntax parsing merely to discover API-level relationships.

Compatibility analysis: Comparing two independently generated representations can identify changes in declarations, signatures, bounds, visibility, trait defaults, stability and metadata. The difficult remaining work is semantic identity matching, normalization and determining whether a change is actually breaking for downstream callers.

Documentation-aware semantic search: Documentation text and intra-documentation links can be combined with declaration kinds, typed signatures, trait relationships and source locations to create searches that understand more than textual proximity. The search engine and index design remain external.

FFI and platform API inventories: Function ABI, safety qualifiers, `repr`, target features and platform-specific declarations can be extracted into a structured reference. ABI safety or layout verification requires additional compiler or platform-aware analysis.

Large-scale API corpora: Downloadable rustdoc JSON, optional faster hashing and archived representations can support repeated analysis of many crate versions. Durable identity, provenance, version dispatch and cross-document joins are not supplied by the crate itself.

### 13.3 Limitations that affect interpretation

The most important limitations are not missing convenience APIs but fundamental distinctions in the available information:

| Information needed          | What `rustdoc-types` provides                           | What remains outside its scope                                      |
| --------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------- |
| Public declarations         | Documented and referenced item graph                    | Every valid public access path under all configurations             |
| Type relationships          | Structured types and generic constraints                | Complete type normalization, inference and trait solving            |
| Implementation availability | Explicit, blanket, negative and synthetic impl metadata | Closed-world proof of implementability for arbitrary types          |
| Exact source structure      | Optional spans and some textual expressions             | Lossless token stream, syntax trivia and macro expansion provenance |
| Documentation references    | Documentation text and resolved intra-doc links         | Full source-level reference and call graph                          |
| Cross-build identity        | Document-local IDs and path metadata                    | Stable global symbol identities                                     |
| Conditional APIs            | Output for a particular compilation context             | All target/feature combinations                                     |
| Runtime behavior            | Signatures, qualifiers and declarations                 | Function bodies, control flow and execution semantics               |
| Binary compatibility        | ABI, representation attributes and target information   | Complete concrete layouts and ABI verification                      |

These boundaries make `rustdoc-types` an excellent foundation for API-level semantic structure, but not a substitute for source-oriented analysis when control flow, local bindings, macro behavior or full compiler semantics are required.

## Overall architectural significance

`rustdoc-types` occupies a useful middle ground between raw source parsing and direct compiler-internal integration. It offers access to a substantial amount of compiler-resolved Rust API structure through a comparatively small, serializable and strongly typed library.

Its particularly valuable capabilities are reference-based identity, structural type and generic representations, trait/implementation relationships, explicit information about stripped declarations, path-aware external references, and increasingly detailed stability metadata.

The main architectural opportunity is to build higher-level, documentation-aware API analysis using existing compiler-derived structure rather than reproducing that structure through custom parsing and name-resolution logic.

The principal tradeoff is that this structure reflects the documented API under a particular build configuration, not the entirety of Rust's source syntax, compiler semantics or possible program behavior. The most reliable consumers preserve that distinction throughout identity management, cross-crate resolution, compatibility analysis and long-term storage.
