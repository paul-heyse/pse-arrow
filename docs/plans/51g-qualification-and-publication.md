# Plan 51g: Qualification and publication

## Completion meaning

**Proposed:** establish the assembled behavior of the selected workbenches, close bounded inquiries
with honest outcomes, complete relevant zero-target checks and publish enduring contracts before
retiring resolved planning material. The [coordinator](51-engineering-workspaces-and-evidence.md)
is the single owner of package state, O01–O21 dispositions and I01–I11 inquiry outcomes.

Plan authoring and document checks implement none of these packages. Interface-checked source
assessment settles the storage/payload design without claiming newly Tested behavior. Package
unit tests establish their named scope; assembled consumer journeys establish composition;
performance claims require named measurements. Acceptance of an ADR alone is not implementation
acceptance. No database success qualifies a numerical result.

The base delivery includes the selected project/research/evidence/closure/exchange capabilities.
SC06/LC05/DL03/DL04 each require a bounded decision. No-adopt with a supported alternative and
observable trigger can satisfy that inquiry; positive adoption requires explicit selection and
the actual integrated supported behavior before its package closes. Do not leave a hidden browser,
crypto, acquisition or collaboration obligation under a completed base-series label.

## Verification rhythm and representative scope

Implementing packages compile affected code and run targeted unit tests with their changed
behavior, deleting provably replaced code/callers/tests/fixtures in the same change. Use repository
recipes and explicit Arrow force-validation for every actual Arrow-consuming correctness closure.
Generated declarations are regenerated as part of their change. Do not run scope-end static and
integrated suites after every package, or repeatedly rerun them after documentation-only edits.

Once all selected functional scope is implemented and targeted tests pass, select the relevant
assembled integration/component/native solver/Python journeys once. Representative studies use
the smallest declared population exposing the behavior: a few independently meaningful branches,
points, outcomes and conflicts. Do not couple functional acceptance to production-scale lane,
point or parameter counts. A full upstream DST/benchmark campaign or hundreds of cleanup cases
is not required merely because the production configuration allows it.

| Assembled journey | Required observable distinction |
| --- | --- |
| Project branch/draft/merge/undo | Fork exact closure, save invalid text, admit a fix, distinguish value/structure changes, reject overlapping merge and moved head, publish an explicit resolution, retain an old run after undo. |
| Measurement to downstream study | Original measurement → versioned calibration/selection → existing qualified fit → explicit parameter source publication → study. Check physical validity and original fitted cells; retain independent uncertainty qualifiers. |
| Scientific cohort and lazy result | Select real mixed outcomes and source context, preserve missing members, refuse incompatible KPI comparison and access selected original protected detail without eager unrelated decoding. |
| Evidence investigation | Query a complete-failing and interrupted/unreported authentic invocation offline, import twice, reject partial generation, report stale/missing sources and open one linked plus one standalone diagnostic. |
| Comparable measurement history | Preserve actual cohort conditions and censored/failed samples; unavailable Criterion-to-invocation association stays unavailable rather than becoming fabricated causal evidence. |
| Study observation | Disconnect/reconnect with available history and unavailable prefix; show catch-up/gap/current snapshot; observer exit leaves science running while explicit cancel retains its own semantics. |
| Portable project | Export selected closure, inspect independently, import under fresh authority, edit and request a supported study; unsupported provider/missing payload refuses execution without inferred repair or new qualification. |
| Lifecycle and recovery | Explain protection/retention, reject stale release, retain active borrowers, inspect incomplete disposable recovery closure and fail closed; distinguish index rebuild from canonical recovery. |

These compose source-review demonstrations without maintaining a second scenario registry.
Use actual public Rust/Python/CLI entry sequences and source owners. Lower-level repository
success alone cannot close a public workflow. Missing selected support is repaired through the
owning package rather than narrowing acceptance after a failure.

## Work packages

<a id="Q01"></a>
### Q01 — Actual consumer and inquiry reconciliation

Reconcile all new public entrypoints, source/payload producers, imported projection owners,
selection/effect/lifetime users and replaced mechanisms against 51a–51f. Confirm that every
opportunity has its promised delivery or declared design/inquiry disposition and that existing
Plan32/40/49 ownership is preserved. Inspect the real CLI/Python/runtime path, generated registry
consumers and offline database-unavailable sequence, not only internal helpers.

Update the coordinator from implementation evidence. Resolve bounded inquiries or obtain newly
required selection before adding dependent scope. Confirm no parallel model, schema, terminal,
resource authority, backend facade or automatic migration path has survived accidentally. Remove
replaced code/fixtures when their actual consumer migration and targeted tests are complete.
This is ordinary integration reconciliation, not an automatic new diagnostic/completion audit.

<a id="Q02"></a>
### Q02 — Composed functional qualification

Run the relevant journeys above through supported default/native/Python/offline contexts. Select
changed tests using current recipes and qualification guide; use linked scientific providers only
where the behavior depends on them. Include actual wrong-authority, uncertainty-after-effect,
stale-generation, released-payload and provisional-stream-failure paths in their targeted owners.
No static source review or metadata-only fixture substitutes for the numerical fitting/study
journey when that integrated scientific capability is claimed.

Completion records commands, modes, selected scope, zero failure baseline and actual results with
the repository evidence vocabulary. Distinguish not-run contexts from failures and targeted
success from full scope. Repair failures in line with the target rather than weaken physical
admission, force-validation, exact membership or original outcome meaning. New measurements are
required only for claims being made; absence of a speed claim does not block functional capability.

<a id="Q03"></a>
### Q03 — Scope-end static and manual checks

After functional scope, run `just hygiene`, address every error/warning against zero and rerun
failing recipes. Include relevant governance, documentation, native-boundary and feature/powerset
checks from the repository qualification guide. Changes to dependencies/features must preserve
the single Arrow/Parquet/object_store/DataFusion family and pinned resolution. Type/lint/generation
checks cover new Python facades, host adapters, query bindings and CLI/tooling as applicable.

Use the documented checkout environment and existing workstation concurrency/capacity settings;
do not introduce a special low-job or arbitrary memory policy for this series. Bare ad hoc heavy
commands still use `scripts/pse-env`. Run `just ready` only for its documented environment-change
or environment-shaped-failure conditions. Root runs `just turn-end` when ending changed turns.

Completion reports actual failed checks and repairs, not a "no worse than before" baseline.
Documentation-only final edits need their mechanical checks, not repeated product qualification.
Checks are scope evidence, not new commit/merge/push gates.

<a id="Q04"></a>
### Q04 — Enduring publication and later plan reconciliation

After implementation and qualification, move enduring project/research/evidence/closure operations,
support limits, formats and operator workflows to their native architecture/API/dev-guide owners.
Use required ADR/design routes for actual new meanings and authoritative-design amendments, with
the collection revision row; accepted ADRs are not rewritten casually. Publish real CLI usage,
offline/service-unavailable inspection and recovery limits. Update qualification scope with exact
evidence and explicitly unmeasured benefits.

**Only after implementing the new series**, reconcile existing plan documents and their index
against delivered overlap, especially Plans32/40/49 and completed Plan50's preserved boundaries.
Do not mark an older plan complete because one capability overlaps, reopen completed work merely
to add a derived consumer or overwrite independent remaining obligations. Follow native status
owners and repair inbound links when completed plans/reviews retire under ADR-0096. The user's
current authoring request excludes all such existing-plan edits.

Close this series only when its package/inquiry and opportunity tables agree with actual support,
required qualification and enduring owners. Record an Outcome with what was built, a mistake
made/corrected and deliberate deviations, using Proposed/Interface-checked/Implemented/Tested/
Measured distinctions and named conditions. Then perform lifecycle retirement preflight; Git
history is the archive. Do not fabricate an implementation Outcome during document authoring.
