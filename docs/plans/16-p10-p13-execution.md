# Plan 16 P10 through P13 execution

Implements the user-approved result, reuse, publication and consolidation scope of
[Plan 16](16-data-model-architecture.md). Preserve concurrent checkout changes.

## Decisions

The registry owns durable vocabulary. Completion owns result qualification and
lineage; Arrow and Python project that same immutable product. Observation cannot
change scientific or publication outcomes. Program validity, cache retention,
storage retention and native worker lifetime have independent controls.

Compatibility covers the complete semantic contract and independently compiled
consumer expectations. Unsupported historical formats return typed migration
requirements; no legacy runtime or automatic migration is in scope. Immutable
attempt member locations precede a conditional control-last commit. Public tickets
permit read-only settlement without repeating materialization. Writers initialize
local retention coordination; readers only acquire existing ownership.

Use pinned library contracts and existing owners. Runtime fixture discovery uses
libtest-mimic after targeted discovery/filter/failure controls. Library-enrichment
is not used. P14-P18, release and other-platform qualification remain separate.

## Execution order

1. P10: typed completion projection, full lineage, attributable diagnostics,
   generated public capability projection and bounded completed-plan observations.
2. P11: semantic identity audit, native reconfiguration, immutable product sharing,
   checked dynamic rebinding, distinct cache invalidation, retiring flights and
   resource-based Salsa rotation.
3. P12: complete semantic contract, explicit compatibility, immutable attempt
   publication, public settlement and read-only retention ownership.
4. P13: compact compiled expectations, authoritative enums, shared obligations,
   shared grammar/traversal, typed settings and runtime fixture discovery.
5. Scoped integrated/default/native/Python qualification, then formatting, lint,
   governance, generated equivalence, documentation and architecture checks.

## Execution rhythm

During functional work use touched compilation and targeted functional units with
force validation. Regenerate declarations with the repository generator. Delete
displaced code and callers after replacement units pass. Run no integrated or
nonfunctional gates until all four packets' functional scope is implemented.
