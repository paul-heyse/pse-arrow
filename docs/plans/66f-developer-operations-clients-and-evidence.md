# Developer operations, clients and evidence

## Remaining target and foundations

Plan66 is the sole go-forward target. This companion owns remaining native developer operations,
independent-host and code-intelligence consumers, engineering/reference clients, retained developer
evidence and exact rerun changes. It actions I08, CR03/CR04 and consumer portions of I04–I06.
The [coordinator](66-integrated-simulation-target.md) owns combined scope;
[B](66b-contracts-generation-and-interpretation.md) owns reusable correspondence and interpretation,
[C](66c-preparation-execution-and-service-lifecycles.md) execution/settlement,
[E](66e-protected-data-and-result-delivery.md) protected scientific data and delivery, and
[L](66l-required-population-and-assembled-acceptance.md) assembled acceptance.

**Interface-checked:** main `66341514d` already supplies the independent native host, native
correctness/fixture routes, exact post-list aggregate prerequisite assessment, retained original
file/directory evidence mechanisms and descriptor-guided bounded schema search/inspection. These
are implemented prerequisites; their enclosing package labels do not authorize rebuilding them.
The selected Rustdoc/Serde bridge is deliberately retained. Source-owned developer report and
diagnostic projections are partially delivered; generated availability, full finite caller
cutover and assembled interpretation/authority acceptance remain distinct obligations.

The target is one usable developer/client workflow: discover supported operations, obtain exact
conditional prerequisites, prepare explicitly, list/check/rustdoc/test under the intended native
mode, retain the original result and selected artifacts, inspect through an independent reader,
and rerun exact failed identities under current listing. Product science remains Rust-owned;
Python is only the isolated scientific-reference/tool dependency.

## Native actions, prerequisites and truthful results

Extend the existing native action owners rather than introduce a second runner. Listing discovers
the selected test population; its exact prerequisites may differ from pre-list conditional
requirements. Aggregate all missing post-list prerequisites before workload effects, using the
existing `fixtures::{InputState, Readiness}`, `FixtureError` and report `FixturePending` owners.
Preparation remains explicit. Listing/setup failure, no matches, test assertion failure, successful
expected refusal, interrupted capture and cleanup failure are different results, even when the
outer process exits successfully.

The typed action/report must preserve selected target/test identity, invocation/mode/features,
fixture/provider provenance, source/dependency commitments and original result class. A failed
test may contain useful scientific output; a passing test may intentionally prove native refusal.
Neither a process code nor a generated verdict field confers scientific usability. Current product
adoption remains with A/E's governing native context; F publishes accurate observations and native
developer verdicts from their actual owner.

Reuse an identical invocation's runtime capsule/build capture without treating fixture preparation
as a build identity or minting a new original result. Selection, target, feature/profile/native
mode and source changes invalidate their actual dependents. Current test listing is authoritative
for a rerun; historical names are selection evidence, not permission to execute an absent or
changed test. Keep interruption, independent teardown attempts and original failures visible.

## Original evidence and exact rerun

Retain the native original report plus selected raw files/directory manifests. Compact envelopes
retain their declared 64 MiB boundary; larger captures use staged original files, not duplicated
JSON arrays. Apply source-owned one-way projections for report/evidence/manifest observations,
with original interpretation, dependency commitments and explicit omissions. There is no inverse
observation-to-verdict/adoption constructor. Preserve the original native JSON presentation where
it is still an actual retained-format consumer; replacing a passive presentation does not require
changing its native result semantics.

An open inode is not a general artifact retention lease or snapshot. E owns protected data custody
and result delivery; F owns which developer bytes were selected, their interpretation, original
commitments and lifecycle. For selected evidence, retain before publication, verify commitments
before interpretation, and expose missing, changed or incomplete capture as an explicit outcome.
Directory observations preserve ordering/path policy, selected omissions and file failures without
inventing complete-directory custody. Do not resurrect completed retention mechanisms as a new
archive framework.

Implement E05's sequential verified-member delivery at the existing native
`crates/pse-host/src/test_workflow/execute/evidence/opened.rs::OpenedFile` owner and migrate the
developer offline/report clients to it. Reuse `with_reader`/`copy_verified`: hash the actual
transferred chunks, retain descriptor custody, detect growth and check before/after identity and
the original complete commitment. Preserve strict `read_range` for inspection; repeated tiny
whole-verified ranges are not the bulk delivery path. Emitted chunks are provisional until EOF
and final whole-member agreement produce a completion receipt. Publish a destination only after
its promised complete/sync contract. Cancellation, slow/escaped consumers, sink error, truncation,
mutation and final sync failure preserve partial extent and independent release/cleanup errors;
none can turn a prefix into whole-member success. Bound live chunks and preserve the compact
boundary, original directory manifest-last/no-replace publication and unknown durability behavior.
E owns the common contract and scientific/project consumers; F implements the shared native
opened-file integration and its developer callers once, without a parallel chunk service.

Exact failed rerun consumes the original report inventory and original result identities, resolves
them against the current native listing, reports unavailable/changed selections explicitly, and
produces a new original invocation/result. It never relabels old evidence as a fresh run. Cover
changed target/features, missing/renamed tests, no matches, expected-refusal success, interrupted
capture and multiple independent teardown errors. A historical report remains readable even when
rerun or current adoption is unavailable.

## Independent host, code intelligence and client realization

The independent host remains product-free. Migrate its selected configuration, request, fact,
diagnostic, path/test identity, graph/investigation and schema consumer families onto source-owned
contracts where those meanings cross a boundary. Keep native hook/guard decisions fallible; raw
and adjusted paths, unavailable facts and unknown alternatives retain meaning. Do not import
`pse-runtime` into the host to share an adapter. Existing lightweight descriptor search/count is a
prerequisite, not a new search rewrite.

Make semantic change an actual `schema compare` capability using
`pse_contract_proto::compare_descriptors` in `crates/pse-host/src/schema/compare.rs`, as specified
by B02 and [CR03](../plan_improvement_reviews/plan64-65-contracts-and-runtime-analysis-2026-11-06.md#CR03).
Present structural/Buf and semantic results separately, preserving unknown coverage and exact
original-world limits. The CLI and structured report expose policy, native-rule changes and
adoption consequences without pretending that wire compatibility implies scientific equivalence.
Product normalization, when needed, is an explicitly prepared product-owner request; passive
comparison/discovery never starts a database, compiler or scientific service.

Deliver the complete approved generated Rust engineering-client workflow: contract discovery and
constraint explanation, exact-parent typed add/replace/delete/retain edits, preparation, submission,
progress/status, cancellation and protected product readback. Retain original operation/run/attempt
identity through reconnect and lost ACK. Complete the actual declared-case, steady Study and
simulation/fit/horizon consumers with original physics, failed siblings and truthful partial output;
an interface-linked client is not live acceptance. Scientific companions own their required native
physics and derivative checks, while F owns the client-visible transaction and evidence journey.

Use Buffa0.9.2 generated messages/views and maintained validator0.7.2 rules from the same source
world. Connectrpc0.9.1 generated typed clients preserve `Stream::message` distinctions between
`Some`, terminal `None` and `Err`; a valid prefix plus terminal failure is partial, not successful
completion. Structured `ErrorDetail::from_message` / `with_detail` preserves actual typed remote
diagnostics, unknown/malformed details and local error sources separately. Support limits match
C's binary-gRPC HTTP/2 Unix service. For external interoperability choose a tool actually supporting
that socket/protocol/descriptor shape, such as a verified grpcurl/protoset or Buf curl invocation;
do not silently add browser/JSON/Connect support to make an example run. A Tonic-backed tool and
another Tonic-backed client are not fully independent protocol evidence merely by different names.

Separately driven reference/tool consumers use explicit versioned request/result files and original
scientific-reference environment. They do not become a required Python product layer, share
candidate math implementations, or skip a missing/wrong parity provider. Native/reference errors
retain structured classes and exact input/output identities. B owns mechanical mappings; each
actual consumer owns its command and interpretation.

small semantic folds need not move into SQL. Release analytical views with acquired evidence.
An answer carries literal original evidence attribution and never grants rerun, preparation,
present cancellation control, scientific usability or a new native verdict. See
[DRE05](../plan_improvement_reviews/plan64-65-data-results-and-evidence-analysis-2026-11-06.md#DRE05)
and E07 for selected composition and exact query contracts.

## Verification, decisions and completion

Implementation is active, with selected original-evidence and semantic comparison changes
integrated and bounded receiving recorded above and at the coordinator. Implementation uses targeted
native routes with explicit fixture preparation and Arrow `force_validate` where consumed. Default
independent-host, generated Rust client and engineering-service receiving closures are distinct
checks. Independent readers and protocol clients must inspect original bytes/outcomes, not copies
produced by the same helper under test. Measure any claimed serialization/capture benefit across
producer, encoding, transport/storage, reader and release with declared retention/compression.

No new rule waiver is introduced. Metadata/hashing/commit or Python-boundary changes require the
coordinator's applicable decision route before implementation. Existing isolated reference and
clean-room constraints remain binding. Completion requires the complete selected caller population
migrated, replaced maps/routes/tests/fixtures removed, all required failure outcomes truthful and
the relevant L acceptance complete. Pending verification of an implemented mechanism schedules
acceptance of that mechanism; it does not replan its implementation.
