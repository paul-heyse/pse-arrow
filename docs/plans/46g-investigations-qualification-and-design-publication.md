### I16: current realization decision

**Interface-checked, 2026-10-18:** exact selected Symbolica 3.0.1
`evaluate/backend.rs`, `evaluate/export.rs` and `evaluate/evaluator.rs` were inspected
with the Symbolica/faer capability skill and current Context7 documentation. The skill's
3.0.0 index is discovery only where it differs from the selected 3.0.1 source.
Multiple-expression evaluation and mathematical Taylor vectorization do not establish
hardware SIMD. The JIT constructor remains synchronous; its settings do not expose the
needed construction stop/join route or establish the repository's generic ISA contract.
SIMD C++ export uses xsimd/packed buffers. Packing homogeneous arithmetic does not itself
preserve ordered source guards, failure attribution, provider effects and cancellation
across the current per-occurrence consumers. No changed premise defeats Plan45's
retained Never-inline Second-Taylor refusal control in `library/admission.rs`.

**Decision:** retain interpreted and explicitly selected conservative scalar C++
realizations. This inquiry adds no unqualified SIMD/JIT backend or generic batching
platform. Existing scalar C++ export disables inline assembly, fast math, FP contraction
and host-native targeting; those flags and private worker ownership stay unchanged.
Reopen for an actual homogeneous pure multi-point consumer with material arithmetic
cost, prepared ordered guard/attribution boundaries, finite packed scratch, and a
library realization with generic arithmetic and construction interruption. Then compare
complete preparation plus repeated requested Value/First/weighted/Second work against
the current route, including divergent/invalid lanes and drain. No SIMD speedup or
whole-operation lack of benefit was measured here.

### I18: bounded device feasibility decision

**Interface-checked, 2026-10-18:** Symbolica 3.0.1 CUDA export has reusable device
parameter/output allocations, but each exported evaluation copies all batch inputs to
the device, launches, synchronizes and copies all outputs back. The current authored
consumer binds one adaptive native callback or occurrence at a time and retains guards,
providers, solver history and original assessment on the CPU. Export availability does
not supply a resident end-to-end solver, device derivative/guard execution, asynchronous
cancellation, or a qualified batch consumer. Existing host solver factors are not
device objects merely because their library families offer other GPU bindings.

**Decision:** retain CPU production execution. No production GPU/precision/ISA change,
device campaign or speculative backend is introduced. A numerical crossover was not
measured and cannot be inferred from host hardware: the present consumer would pay
transfer and synchronization per callback. Reopen for an actual large homogeneous pure
population or resident linear operation whose measured CPU arithmetic dominates gather,
guards and transfer, with its complete requested derivative products. The follow-up
must name batch layout/size, host-device byte traffic, precision/generic-equivalence
decision, finite device/host residency, failure attribution and stop/drain. Compare one
short complete population before any longer device campaign. This completes bounded
feasibility scope without claiming GPU execution is universally inefficient.
