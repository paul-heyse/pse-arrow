# Scope and shared contracts

## Target and assessed foundations

**Proposed:** settle the scope and consumed meanings needed by Plan64 without creating a universal simulator IR or moving legitimate runtime binding into the compiler. The [coordinator](64-process-simulator-target.md) owns accepted RC decisions, source baseline `1acd8c83c`, finding correspondence and independent plan boundaries. This companion owns A01–A04 state.

The existing parented source/declaration model, semantic flow selection, prepared closure obligations and completion APIs are suitable starting owners. `prepare_declared` is Solve-only, while declared diagnostics can inspect another selected subject without executing it. Target profile names do not establish numerical implementations. Source scope, semantic instance, active task, numerical realization and resulting evidence must remain distinguishable in the public contract.

## A01 — Route the confirmed scope decisions

Use the finite population selected by 64h rather than an unbounded promise of every possible upstream model configuration. Preserve the IDAES2.13.0 reference and clean-room boundary; examples and compatibility populations have separate exact revisions. Distinguish released process behavior, supplemental non-process obligations, intentional scientific improvements and beyond-release extensions. Reconcile the obsolete exclusions and retired parity/product descriptions in `docs/relationship-to-idaes.md` with the current source and affected architecture scope owners.

RC02 is descriptive reconciliation with the native product, not permission to restore a Python runtime. Inspect the current accepted decision lineage; supersede immutable ADRs only where their actual decisions change. Use the existing design route and blueprint revision row for enduring architecture. Do not create one ADR per imported concept. These implementation changes are scheduled here, not performed by plan publication.

Acceptance is a coherent scope statement and exact reference population with no contradictory public exclusions, plus a recorded route for every actual decision change. Imported Notion adoption and accepted repository decisions retain their distinct authority.

## A02 — Shared task, identity and outcome meaning

Reconcile the execution-plan catalog row with the execution narrative: the semantic hash associates the question; reusable symbolic structure, evaluator bindings, numeric factors, starts, attempts and results have their own consumed dependencies. Required method settings cannot collide, but unrelated submission values must not invalidate all structural artifacts. Reuse current dependency owners; do not add a second cache.

Reconcile Analysis-result ownership in both owning lists and the hierarchy narrative. An analysis-only outcome can have zero numerical members. A point-derived product identifies its actual member/reference point, assumptions and coverage. The latter consumes producer permission and local validity; structural diagnosis consumes the applicability and evidence of its analysis operation. Never fabricate a candidate or require a successful square solve to diagnose an underdetermined model.

Define the supported task-to-operation mapping at the existing workflow owner. First delivery exposes native supported Solve/initialization/structural inspection and only the derived products selected in C05. Unsupported mandatory inequalities, representative-set requests, branch requirements, certificates or derivative orders receive attributable refusal. Optional unavailable products stay unavailable. Later 64g extends mappings; this is not a universal dispatch enum.

Acceptance pairs compatible value-only reuse with a changed required method that cannot reuse an incompatible artifact, and pairs zero-state analysis with a point-based request whose missing point is refused. Record reconstruction limits for values, diagnostics, sensitivities and duals; do not promise lossless inverse mappings after aggregation, relaxation or discretization.

## A03 — Focused foundation assessment and extension decisions

Read `modeling.rs::with_declarations/prepare_flow`, `modeling/declared.rs`, `modeling/cases.rs::lower_closure_requirements`, specialized process state/closure owners, source deltas and exact completion/result consumers. C01 uses typed declaration editing first, with explicit immutable parent revisions; source text remains a separate input/review representation. Do not maintain two synchronized editable authorities.

For F04, demonstrate a specific duplicate semantic interpretation or missing consumed distinction before prescribing a refactor. Current closure endpoint/context/lineage and compiler annotations are counterevidence to a blanket migration. If existing contracts suffice, record that conclusion and let B/C proceed; if a consumer exposes a gap, identify its owner, all affected consumers and a revealing convention/allowance change before extending it once. Numeric values and effective numerical policy remain legitimate late inputs.

Use a contrasting material/representation or equipment composition case to challenge adequacy, not a census of every catalog noun. Keep molecular/molar seed assumptions scoped; exact chemistry, empirical characterization, populations, physical inventory and observation/accounting are not interchangeable. Defer generic changes unless the selected counterexample requires them. A registry row or schema field alone does not establish executable behavior.

## A04 — Resolve inherited prerequisite scope

DA-062 records tolerant ordinary bound acceptance versus strict checks on other routes; distinguish physical domains/sign guards and fixed specifications before changing any interval rule. Read current conditional/initialization/causal and original quality paths. The decision output is either a concrete shared ordinary-interval correction with explicit consumers and tests, evidence of a resolved discrepancy, or a route-specific limitation blocking only the affected claimed scope.

DA-063 records a pending capture gate crossing unrelated renewal/cancellation. Inspect current canonical study publication, worker liveness and recovery. A correction must isolate unrelated liveness without losing complete selector membership or recovery fencing; freezing only currently matching rows is not an acceptable shortcut. Identify one existing owning packet or a bounded repair owner before depended-on persisted-study qualification.

These inquiries can run independently. They do not require broad numerical campaigns or a second diagnostic account. Their outcome must identify which C/E/G/H consumers are actually constrained. The coordinator owns their relation to the source diagnoses; it cannot close a broader finding from one narrow route.

## Verification and handoff

**Proposed:** owner-local contract/rejection checks and actual affected compile checks during implementation. Numeric discrimination uses a finite representable ordinary-bound deviation within tolerance plus a strict hard-domain countercontrol. Capture discrimination uses two unrelated runs and a stalled capture with original complete membership and authenticated recovery preserved. Do not infer physical drain from a cancellation request or passing observer.

No implementation or product qualification is claimed by this document. A01/A02 supply decisions and routed contracts; A03 supplies usable foundation conclusions; A04 supplies the exact prerequisite or limitation consumed by later acceptance. Different readiness products are not interchangeable.
