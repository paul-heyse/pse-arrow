# Plan 50f: Preparation explanations and reproducers

## Purpose and assessed foundations

Deliver O18–O20: explain an edit's actual preparation work, compare generated mathematical and
relational execution, and extract a supported executable diagnostic case from complete evidence.
The [coordinator](50-codex-effectiveness-and-diagnostics.md#package-state) owns progress and
inquiry outcomes. **Interface-checked:** `bb61ae3f5`; **Proposed:** design/acceptance below.

Existing observations already include selected Salsa executions/validations/waits/discards,
an exclusive retention census, evaluator/instruction/storage facts, actual logical plan graphs,
physical text and partition metrics. Existing analysis/frozen tables publish source-linked
`engine.actual_policy`, `engine.lifetime` and `engine.operator_metric`. Extend those facts and
their comparison, not another metric reader or dependency authority.

Two important gaps require owner changes before consumers: physical topology is currently
bounded text with metric-local node ordinals, and frozen source context often contains IPC/source
objects rather than the authored text accepted by `diagnose_documents`. Neither can be repaired
by guessing structure in frontend tooling. This focused assessment schedules those foundations
with the consumers that need them.

## Comparison and reproduction contracts

Comparisons consume already observed copies with source revision/generation, scope/loss and
actual subject identity. They do not construct new evaluators, run queries, inspect Salsa memory
or execute science. Stable semantic correspondence must be established; local keys/ordinals and
opaque debug strings are orientation only. Ambiguous/unmapped/unmatched populations remain visible.
Expose conclusions and source-linked facts through existing inspection/analysis/statement owners
and catalogue projections where needed.

Reproducer extraction is a separate offline transformation. It checks recorded completeness,
source-codec slots, settings/coordinates and predicate shape, then writes a new request/driver
without store lookup, reconstruction, preparation or scientific execution. It cannot establish
actual runtime executable/provider premises. The later explicit runner establishes a fresh
operation and deadline before reconstruction/admission. Original attribution/outcome is retained
independently; describing old failure
does not reproduce it. A complete numerical point representation cannot reproduce a transaction
race or cancellation schedule without that execution family's actual conditions.

## Packages

<a id="F01"></a>

### F01 — Semantic edit/preparation explanation

Have query/input owners publish safe labels where they know authored entity, occurrence, body
or root identity. Associate a Salsa event only through an exact generation-scoped mapping;
unmapped events remain unmapped. Do not label every nested event with the outer caller's subject
or format `DatabaseKeyIndex` under an attached database when that can expose authored inputs.

Salsa0.28.5 `ingredient_debug_name` may orient a reader but its string is not a stable semantic
key. Across observations use query family plus known semantic subject, not database-local opaque
keys. Derived mappings reset with workspace generation and are attribution, not another invalidation
or reuse authority.

Begin with a tracked entity/occurrence/root family and a memo-validation event, then extend the
same contract across supported selected preparation families. Compare unchanged, source-only,
value-only and structural edits; show root-wide obligations separately from fragment reuse.
An execution event is not a proved cache-miss cause or shared-wait duration. Source edits and
semantic input changes have different meanings.

Use existing `observe_retention` only at exclusive maintenance: `memory_usage(&mut self)` can
cancel/drain clones. Passive comparisons read the last copied census and its freshness. Acceptance
uses independent edit expectations and clean recomputation for behavior equivalence, without
requiring a universal speed claim or a new event per primitive operation. Include successful
semantic labeling as a positive control; all-unmapped events do not deliver this explanation.

<a id="F02"></a>

### F02 — Mathematical and relational before/after analysis

Consume `CompiledOrderCensus`, `EvaluatorFacts` and assembly observations keyed by actual body,
product/order/coordinate demand and source correspondence. Explain added derivative components,
regions, input/output crossings, controls/providers and frame/worker storage. Optional selected
instruction exports use the existing Symbolica instruction facts; passive inspection constructs
no evaluator. Static instruction counts are neither branch frequency nor time.

First extend `pse-engine::session::observation` with a compact structured physical node/ordered-edge
view produced from the actual plan using the same capture-local numbering as metric collection.
Preserve native text, capture scope, truncation and unavailable plans. Do not parse `one_line()`
text into authoritative topology, and do not add another graph service or persistence authority.
Version any affected public observation/document through the existing catalogue route.

Then compare actual logical/physical operators, partitions, expansion/filtering, available spill/
memory and rules. Match nodes across runs only when operator/semantic context gives a unique
correspondence; node3 in one snapshot is not node3 in another. Repeated/shared nodes can remain
ambiguous. Full graph isomorphism and all-path enumeration are unnecessary. Re-running EXPLAIN
ANALYZE is new work, not a way to inspect the old execution.

Consume 49g TOOL08 for canonical blockers/source/consumer graphs when its response and real
consumer are delivered. Keep that graph's edge roles/revision/continuation distinct from
DataFusion and numerical dependency. It is a separately schedulable consumer, not a prerequisite
for this package's math/engine comparison.

Acceptance includes changed derivative demand, a changed operator/partition, ambiguous repeated
nodes and off/truncated/partial observations, including meaningful positive correspondence;
all-unmatched nodes do not qualify comparison delivery. Existing source-linked metric analysis remains
available and is reused; replaced flat client stitching is deleted after migration. No winner
is inferred from representation counts or graph connectivity alone.

<a id="F03"></a>

### F03 — Supported executable extraction and strict failure predicate

Resolve I07 on one complete recorded source/constructor and one actual-text numerical failure.
There are two input routes:

- Actual original text documents can form a selected `DiagnosticExecutionRequest` using existing
  `diagnose_documents` behavior.
- Frozen `ReviewContext.sources` can contain `ReplayPhysicalSource` IPC bytes,
  `ReplaySourceObject` payloads/references, provider descriptors and constructor facts. Offline
  extraction checks recorded completeness and non-executable codec structure only. The emitted
  runner uses `ReplaySourceDocument::reconstruct`, constructor reconstruction and physical source
  admission through their existing owners, after establishing its fresh operation and deadline.
  Those calls perform preparation/admission and do not belong in extraction. Do not cast descriptive
  review context into a replay document or invent document text from arbitrary bytes.

Extract only supported complete recorded representations. Runtime reconstruction validates the
actual executable/provider/build premises and preserves their existing refusals, including failures
before a run handle exists; extraction reports recorded gaps without pretending to verify runtime
availability offline. A descriptor does not locate a factory;
compatible rebinding must be explicit. State required provider/native environment before running.
No implicit store hydration fills a missing source, and an exported pack must not automatically
follow original absolute paths or execute payloads.

The output is a readable small request/driver with exact selected source/settings/coordinate
meaning, supported execution family and an explicit new-run command. Reuse owned serialization
and schema, never another loader of scientific defaults. Model reduction is not selected.

Define a typed predicate from a selected typed original diagnostic or an explicitly supplied
predicate: relevant code, stage/rule, selected source/validity lineage and necessary observed
conditions. `ReviewContextDocument.failure` can be only a string; never parse that text to invent
typed code/stage/lineage. A runnable extraction can still be useful when original-failure comparison
is unavailable. Declare tolerances only where that
comparison needs them; a broad exception class or matching message is insufficient. After explicit
execution report original failure reproduced, related diagnostic reproduced, not reproduced or
reproduction unavailable. Original outcome and new scientific qualification remain independent.

Acceptance exercises actual text, supported frozen objects/IPC through reconstruction, missing
provider/reference, changed executable premise, text-only original failure and a failure of another
family. Verify extraction performs no reconstruction/admission and runner failures retain the new
operation/deadline even before run creation. A numerical
diagnostic cannot claim reproduction of readiness/cancellation scheduling merely by failing.

### F04 — Small diagnostic and extraction controls

Add direct fixtures at existing observation, analysis, reconstruction and command owners for
stale checkpoints, incomplete source recording, worker exit, refused/missing captures, partial
engine execution, retained resources and busy native joins. Test report/explanation/codec behavior
without creating unrelated models, stores or scientific campaigns. Give new source/subject
distinctions independent expected facts rather than producer-derived assertions alone.

Coordinate with Plan40e assembled diagnostic acceptance and 49h's representative qualification.
Share actual applicable evidence, not a duplicate campaign or mutable status table. The canceled
large native sweep remains closed. G02 selects the new composed workflows once these controls
and actual feature consumers exist.

## Dependencies, verification and sources

F01/F02 proceed independently of profiling; they consume Plan49c/d's actual producers and the
current observation boundary. F03 depends on its codec/reconstruction proof, not all of 50e.
C01/C03 supplies run/artifact projection; product hooks follow TOOL05's dependency direction.
Source recording/export already exists; novel extraction is executable transformation with
explicit follow-on execution, not another generic pack export.

**Proposed:** targeted compiler/math/engine/runtime/Python controls with explicit correctness
validation where Arrow is consumed, plus the supported real source/reproducer examples. 50g
owns composed qualification and scope-end checks. Quantitative speed/memory claims need their
own actual measurement; a useful explanation is not a benchmark result.

`pse-math::{execution,assembly_observation,library}`, `pse-engine::session::observation`,

[Symbolica evaluation](https://symbolica.io/docs/numerical_evaluation),
