# Reusable and predictable mathematical preparation

Inspected baseline `7d89d16f`, 2026-11-09, preserving parallel codegen/operations changes. **Interface-checked** denotes current source and contract inspection; all target directions below are **Proposed**. No build, product test, health check or performance experiment was run. Standard: core3.4, efficient architecture heuristics1.0, process-simulator1.5 and repository binding, especially AP-04/AP-07, H2/H4/H6/H8/H12/H14–H17, PS-06/07/09–12. This is a functional value assessment, not renewed implementation acceptance or an audit.

## O01 — One shared preparation owner from definitions to demanded products

**User value.** A developer adding a residual, selected derivative action or repeated study product should compose one admitted mathematical definition and request its useful products; they should not create another miniature preparation pipeline. A case value edit should reuse compatible preparation, while a changed guard, layout or provider contract should invalidate exactly the affected product. Operators gain predictable failure attribution and no partially prepared result after cancellation.

**Current evidence.** `pse-math/src/library.rs::exact_evaluator` already gives Symbolica aliases and multiple outputs with direct translation. `library/admission.rs::ScalarCache::prepare` keys expressions, ordered parameters, definitions and optimization options; scalar preparation is explicitly shared across interpreted/native Value selections. `execution.rs::LocalPartials` retains local first/second partials as definitions; `typed_partial.rs` already uses native replacement, differentiation and rebinding. This is a substantial existing foundation. There is no evidence here for replacing it with an additional generic cache.

**Bounded target.** Extend the existing mathematical-product owner to preserve named local definitions and demand-specific derivative products across the actual remaining consuming paths. Keep native visitors/replacement/collection and prepared transformation programs as implementation choices within that owner. Adopt an operation-shaped interface for original ordered axes and requested outputs/actions, carrying original source checks and effects, rather than making each consumer flatten/reconstruct or independently optimize the same definitions. Delete flattening, duplicate partial construction and duplicated inspection only in consumers actually moved to the shared product. Reuse keys must retain complete semantics, not textual or numerical equality.

**Alternatives and judgment.** Native `Transformer` and alias discovery are preferable to a new application rewrite engine where an actual reusable mathematical pass exists. They are not a reason to wrap every existing `replace_map` callback in another abstraction. One larger joint evaluator is preferable for an inseparable operation; retained smaller products are preferable when demand or lifetime differs. A globally fused model would prepare unrequested work and obscure independent invalidation. Recommend the existing region/demand owner as the integration foundation, with physical grouping permitted to change inside it; do not preserve each current stage merely because it exists.

**Delivery evidence.** Use a repeated definition chain/diamond with reordered selected outputs and independent expected `Jv`/`Hv`, then one actual fitting/solver caller. Verify that compatible repeats avoid the identified construction, changed guards/layouts invalidate, and a finite weighted result is not refused merely because an unrequested intermediate second derivative overflows. Include cancellation with no retained partial success. Source inspection can establish deleted passes; no universal speed measurement is needed.

**Overlap.** Plan66 D01/D02/D05 owns already selected sharing and remaining caller retirement. This recommendation consolidates those consequences rather than schedules a competing program. More general cross-consumer product reuse is an extension only where an actual residual repeated construction remains.

## Selective native composition of independently reusable programs

**Functional change.** A property/constitutive program can be prepared independently, consumed alone, and connected into residual/response programs without recreating symbolic expressions and Horner work.

**Complete alternatives.** Compare (a) one joint symbolic build, (b) retained modules called by the host, and (c) supplier composition. Use (a) when there is no independent reuse; (b) where modular invalidation dominates and cross-module sharing is small; recommend (c) for a named pure reusable chain whose consumers currently repeat symbolic construction. This is a bounded selection criterion, not a family-wide composer requirement.

Maintained `merge` concatenates outputs, checks parameter count but not meaning, and requires `Eq + Hash`. Tagged3.0.2 `EvaluatorComposer` can wire outputs to subsequent inputs and finish with pruning/CSE/CPE without repeated symbolic Horner search. Its advantage is native mathematical program composition, not removal of physical contracts. Retained non-inline bodies can prevent `vectorize`; real specialization must follow rebuilding passes. Use exact composition before numerical conversion when required by the coefficient bounds, and select derivative demand before choosing inlining.

**Delete/retain.** Delete application-side expression reconstruction and redundant optimizer preparation for migrated module chains. Retain ordered maps and dependencies; a fallible provider cannot be pruned like pure arithmetic. Do not add another evaluator DAG/cache alongside the existing authoritative product owner.

**Prerequisite and rule impact.** The current release candidate lacks locally consumed bounded packing/roots/transfer/provenance additions. Any release move must retain their contracts through a scoped supplier rebase, not replace the supplier merely to obtain a convenience API. A substantial preparation/identity contract change follows the decision route; routine new API use does not itself require an ADR. Plan66 composition remains a candidate, not required completion scope.

**Delivery evidence.** One independently consumed module used both alone and in a response chain; original coordinates, incompatible parameter order, changed module, canceled composition, lazy guards and direct numerical expectations. Discriminate retained-module invalidation against composed-product reuse. No timing campaign is a prerequisite.

## O06 — Supplier-owned construction controls

**User value.** Large admitted scientific products should either construct successfully or refuse/cancel before uncontrolled growth, with reliable diagnostics that survive a supplier upgrade. Less supplier-private arithmetic in application admission reduces maintenance and allows useful operations to grow without repeatedly recreating internal cost knowledge.

**Current evidence.** `bounded_evaluator` derives Taylor expansion/storage bounds before calling `vectorize(Dualizer)` and reconciles the realized product afterward. `native_compiled.rs::export_bound` models the supported scalar exporter before `export_cpp_str`; compiled export explicitly chooses `InlineASM::None`. `library.rs::AbortBinding` handles a build-bound callback, later per-call thread-local rebinding, and cancellation observed during successful optimizer truncation. These controls fill real gaps; deleting them against the old APIs would regress behavior.

**Target recommendation.** Prefer supplier-owned checked vectorization/export entry points reporting operation-specific extents and accepting explicit per-operation control, with the application providing its existing admitted work/backing and original cancellation authority. Make the supplier own bounds tied to its algorithm and retain application-owned scientific policy and resource leases. The end state removes re-derived private expansion/export formulae and callback rebinding machinery only after the checked replacements cover their callers. Keep public `get_byte_size`, instruction facts, counts and extents for actual product inspection; those are not predictions of an unbuilt product.

**Alternatives.** Retaining maintained mirrors is the safe near-term realization and remains appropriate until an equivalent checked supplier route exists. A community RSS/time budget is an optional backstop, not a substitute: process-wide post-hoc polling is neither deterministic operation admission nor reservation before allocation. Serializing/reimporting an evaluator just to reset callbacks is extra reconstruction and can lose receiving guarantees. Process isolation alone does not establish the requested mathematical construction bound. Prefer a small maintained supplier API over a new general application budgeting framework.

**Evidence and scope.** Compare the actual before/after caller with one-unit-short allowance, interruption during optimization/vectorization/export, successful-but-truncated supplier outcomes, and no partial publication/retention. Preserve both pre-operation refusal and realized-size reconciliation. This is not a new workstation memory/CPU cap or demand for a benchmark. Broader operation-control APIs may change blueprint§14.3 contracts and require the appropriate design/decision route; no approved scope changes follow from this review.

## O07 — Transfer the product the receiver actually needs

**Functional change.** A cold receiving process can continue numerical execution or later symbolic work from qualified producer-owned derived mathematics, rather than repeat expensive construction, while preserving original scientific authority and honest refusal.

**Current evidence.** `execution/transfer.rs` restores the supplier checked f64 interpreter through `F64ProgramView::inspect/restore_with`; its module explicitly separates numerical-template correspondence from model/source authority. Guarded sealed restore has tests and pending real receiver work. Plan66 D02 describes packed inspection without coefficient materialization or symbol registration, destination compatibility, original receipts and copy-only restrictions. These are different products, not two competing codecs for one authority.

**Recommended target.** Keep one explicitly qualified numerical-only transfer profile for consumers that need execution only. For a receiver needing derivatives/class evidence afterward, qualify producer-sealed normalized guarded mathematical stages with original recipe/proof custody, rather than trying to infer a symbolic body from numerical instructions. Publish only after receiving checks; budget subsequent new symbolic work independently. Delete repeated symbolic replay for successfully migrated consumers and retire the superseded production encoding when the replacement is qualified; do not add a permanent dual-reader/fallback ladder.

**Alternatives and countercase.** Typed recipe replay remains the coherent alternative where sealed restore cannot prove custody or save meaningful construction. A general Atom state import remaps/registers and normalizes and has allocation/global-state implications; 3.0.2 structured instruction import validates numerical programs after structure allocation and creates a new layout. Neither is a bounded symbolic receiver by itself. Text is still suitable for infrequent human mathematical exchange. Names, canonical strings and matching packed bytes do not replace semantic identity.

**Delivery evidence.** A cold receiver after producer retirement, one large scientific recipe, then one guarded symbolic consumer. Include foreign/reordered symbols, coefficient extents, unsupported attributes/flags, missing/extra receipts, incompatible layout, cancellation and refusal before registration. Verify original-coordinate numerical/derivative results independently. This is Plan66 I01/D02/C04 overlap, not a new competing work owner.

## O12 — Coherent build, memory and runtime boundaries

A numerical-only owner could use Numerica directly to remove Symbolica reach, but changing import spelling in `pse-math` does not change its Atom/evaluator dependency closure. No current source fact establishes a worthwhile new crate split. Recommend preserving the narrow math integration and opt-in native codegen while improving operation-shaped reuse above. Only propose a new direct-companion boundary when actual dependency-unit evidence and a genuine independently reusable numerical owner establish its benefit. Fixed hyperdual codegen can increase monomorphization; dynamic shape sharing is already present. Less local code is not evidence of a smaller Rust build.

`TermStreamer` is a useful future large-additive research operation, but not the default route for shared Helmholtz graphs or global GCD/factorization. Its threshold controls spilling rather than complete admission, and serialization/global merging adds work. Recommend in-memory factorized/shared representations for present preparation; introduce streaming for an actual additive workload whose output semantics tolerate term-local transformation followed by explicit normalization. Polynomial thread-local contexts/compaction are targeted ownership optimizations, not grounds for a new application-wide scheduler/cache. Keep report/presentation rendering at an actual consumer and choose lossless state separately from human formatting.
