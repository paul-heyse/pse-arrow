## Types

### proptest-derive/derived-ast-strategies
- **Need it serves:** Generate structurally valid AST values for property tests, without
  hand-writing a `Strategy` per type, and keep the generator in step with type definitions.
- **Recognizable code shapes:**
  - Hand-written `impl proptest::arbitrary::Arbitrary for T` blocks whose bodies enumerate
    every variant with `prop_oneof!`.
  - A generator file that must be edited whenever an enum gains a variant.
- **Mechanisms and APIs:**
  - `#[derive(Arbitrary)]` on structs and enums.
  - Modifiers:
    - `#[proptest(strategy = "expr")]` and `#[proptest(value = "expr")]` for fields and
      variants.
    - `#[proptest(weight = N)]` and `#[proptest(skip)]` for variants.
    - `#[proptest(filter = "pred")]` for rejection sampling.
    - `#[proptest(params = "T")]` for a custom parameter type.
    - `#[proptest(regex = "...")]` for `String` and `Vec<u8>` fields.
    - `no_params` and `no_bound`.
  - The derive composes with hand-written strategies through `strategy =`.
- **Obligations discharged:**
  - Variant enumeration and field composition.
  - Compile-time coverage: a new variant is generated by default unless explicitly skipped.
- **Residual caller obligations:**
  - Domain validity: renderable names, finite numbers, precedence-safe shapes and valid unit
    products. These become `strategy =` or `filter` attributes.
  - Recursion depth and size control.
  - Span defaults.
- **Semantic conditions:**
  - `filter` uses rejection sampling, which the documentation warns is inefficient and
    interferes with shrinking.
  - Derived strategies shrink by structure.
- **Version / build conditions:** 0.9.0 requires Rust 1.88 or newer.
- **Limits and negative results:**
  - The modifiers page does not document recursive-type support. Whether a recursive `Expr`
    enum derives without a manual `prop_recursive` wrapper is unverified.
  - The `arbitrary` crate (`Unstructured` bytes to value) is a different model, aimed at
    fuzzers. It does not replace proptest strategies with shrinking.
- **Evidence:** Interface-checked: modifiers page and crates.io metadata. Recursive support:
  unsettled.

## Current applicability

### [CBO-037](../../../library_leverage/codebase/authoring-and-identity.md#cbo-037) — Grammar facts maintained in several hand-written forms (AST generator form)
- **Types:** `proptest-derive/derived-ast-strategies`.
- **Realization:** Upgrade route `proptest-derive =0.9.0`, a dev-only or feature-gated
  addition beside the installed `proptest` 1.11.0.
- **Conclusion:** Unsettled. The generator is mostly domain-validity strategy:
  - representable unit products through `UnitProduct::from_factors`;
  - finite literals;
  - renderable paths.
  A derive would turn those into per-field `strategy =` attributes on the AST types. That
  moves the code rather than removing it, unless recursion derives cleanly.
- **What it would discharge / what remains local:**
  - Discharged: enumeration of plain variants and the guarantee that a new variant is
    covered by default.
  - Remains local: every domain-constrained leaf strategy and recursion bounds.
- **Prerequisites, configuration or extension:** Derive attributes on the production AST
  types, gated behind the existing feature so production builds are unaffected.
- **Semantic gaps against the CBO's preservation constraints:**
  - Canonical render text depends on generating only canonical shapes. Unconstrained
    derived variants could produce non-canonical ASTs that fail round trips for legitimate
    reasons.
- **Unsettled premises and what would settle them:**
  - Recursive-enum support at 0.9.0. Reading `proptest-derive` 0.9.0 source or tests, or a
    small scratch probe deriving `Arbitrary` for a recursive enum, would settle it.
- **Evidence:** Interface-checked (docs); application Proposed.
