# Integrated exact domains: extraction, elimination and certificates

Inspected 2026-11-09 at source `f6e91eb37`, with user-supplied overviews present. **Interface-checked** below means direct reads of maintained Symbolica 3.0.1 and locked Numerica 3.0.1 source, not a compile or numerical experiment. Research directions are **Proposed**. This deepens the existing exact-algebra and Numerica addendum accounts without adopting a new solver or refreshing every older finding.

## One pipeline, several genuinely different coefficient domains

Symbolica's `AtomCore::system_to_matrix` is a higher-level conversion than a scalar coefficient visitor. The inspected `solve.rs::system_to_matrix_impl` converts each equation to an exact rational polynomial, treats the selected unknowns as polynomial variables, rejects monomials whose total unknown degree exceeds one, extracts the coefficients and negative constant term, unifies the remaining variable maps, then constructs `Matrix<RationalPolynomialField<Z,E>>` and its RHS. Remaining indeterminates are parameters in the coefficient field. This can replace a caller's symbolic affine extraction plus matrix assembly; it is not simply a direct `Matrix<Q>` constructor.

That distinction determines what composes next. `Matrix<Q>` operates on scalar rational values. The returned rational-polynomial field preserves symbolic parameter dependence. Generic Numerica `Matrix<F>` algorithms use `F`'s operations, so the high-level matrix object does not require a competing expression engine. Numerica `solve` is available over a field; its inspected implementation augments a single-vector RHS, row-reduces leading unknown columns, checks inconsistent remaining rows, back-substitutes, and reports underdetermination with its reduced augmented matrix. The exact algebraic result therefore remains in the selected coefficient field. Choosing a domain and variable map is part of the mathematical operation, not storage metadata to discard during transfer.

Matrix entry mapping is an integration seam, but `map` applies an arbitrary caller closure; it establishes no homomorphism, parameter specialization validity, or preservation of nonzero denominators. Entrywise `derivative` delegates to the coefficient domain's `Derivable` implementation. It does not differentiate through a solve or supply implicit sensitivities by itself.

## Fraction-free algorithms require a deliberate domain decision

Locked `Matrix<F: EuclideanDomain>::partial_row_reduce_fraction_free` strips pivot-row content with GCD/exact division and scales elimination using GCD-related factors. It is not merely ordinary Gaussian elimination with fewer allocations. `solve_fraction_free` accepts a single-vector RHS, performs consistency/rank checks, and finally uses `try_div` to establish that the answer remains in the original domain. A mathematically rational solution need not be an integer-domain solution: `2x=1` must not silently become a successful integer solve.

Content/primitive normalization can reduce exact coefficient growth, and matrix augmentation/splitting preserve the algorithm's structural intent. However, the rational-polynomial field produced by `system_to_matrix` already allows denominators. To investigate an integral-polynomial or integer fraction-free route, specify how denominators are cleared, which parameter values make that clearing invalid, and how the original equations are checked afterward. A wrapper that converts fields repeatedly without these semantics would add machinery rather than remove it. Field elimination, fraction-free elimination and modular reconstruction are complete alternative computations with different domains and verification requirements.

## A named current consumer: affine evidence and coefficients

`class_evidence.rs::prove_affine` discovers candidate global coordinates with native symbol discovery, differentiates with respect to each candidate, requires each derivative to be constant, converts it to an `AffineRow` numerical entry, substitutes zero for those coordinates to obtain the constant, and retains coordinate mapping and bounded work. This is a concrete inquiry for higher-level extraction: can one native parameter-aware matrix extraction serve the current affine evidence and a future exact elimination consumer, rather than rebuilding coefficients by separate operations?

The countercase is equally concrete. Current affine evidence is sparse, candidate-driven and bound to original global coordinates; it rejects unmapped residual symbols and produces the numerical consumer's actual row format. A global matrix conversion can allocate/work across many irrelevant variables and retain symbolic parameters the current numerical row does not need. Compare complete extraction, coordinate mapping, original guards, finite conversion and demanded rows. Do not replace it merely because both paths can produce coefficients.

`coefficients.rs` already reuses request-local exact objective expressions and performs `expand().to_polynomial_in_vars::<u16>` before extracting degree-at-most-two coefficients. A useful additional direction is sharing an operation-shaped exact polynomial/matrix product with another genuine consumer; the current request-local objective reuse is not missing adoption. The numerical projection's final coefficient conversion remains necessary, while repeated expansion or reconversion would need an actual second caller before being described as present duplication.

## A narrower current seam: exact Schur updates

`convexity.rs::ldlt` deliberately owns sparse symmetric pivot selection, cancellation, work accounting, zero/negative diagonal classification and Gram factors. It computes multipliers `a_ip/d` once per pivot, then forms each product with `a_jp` and subtracts it from the exact accumulator. Numerica's `RingOps::sub_mul_assign` can express that local arithmetic update without replacing the certificate algorithm.

The locked rational implementation provides an important limit: it delegates directly to the underlying ring only when the accumulator and both multiplicands all have denominator one; otherwise it computes multiplication followed by subtraction. A non-dyadic Schur complement is explicitly exercised by current convexity controls. Consequently this seam may simplify integration, but does not establish a general fused or allocation-saving rational update. `Ring::sub_mul_assign_many` has a generic loop default. Integer `Z` overrides it with a multiprecision-aware chain and also supplies owned exact division. Merely changing the rational call spelling cannot inherit integer-only specialization after division has produced fractions. A genuinely integral/fraction-free Schur design would be a different complete certificate computation and needs its own witness/pivot semantics, not a low-level substitution.

## Follow supplier dispatch before adopting kernels directly

`Ring::kernels` defaults to an empty capability object; specialised kernels are optional accelerators under the domain's mathematical operations. Maintained Symbolica already queries polynomial kernels in homogeneous multiplication and geometric-sequence kernels during factorization sampling. The homogeneous route screens degree/layout/work shape before dispatch. The factorization route queries once, attempts the specialized sequence sum/advance, and falls back to generic ring operations when unavailable. Resultant paths already consume `exact_div_owned`; specialised rational polynomial division clears denominators and uses integer arithmetic internally.

This is existing integration across Symbolica and Numerica, not a gap requiring application code to reproduce those inner loops. A kernel's `None` is an unsupported specialised request, not proof that the mathematical operation has no result. New direct kernel use becomes interesting only for a named caller outside these high-level supplier paths, or evidence that the supplier misses useful dispatch for that caller's supported shape.

## Functional hypotheses and discriminators

- **Parameter-aware affine block preprocessing:** extract an authored linear sub-block into its exact parameter coefficient field, eliminate selected unknowns, retain conditions and recover original coordinates, then prepare the remaining numerical system. Useful new functionality; no current generic block eliminator was established by this scoped read. Next choose a real small block with parameter degeneracy and compare original equations at both ordinary and exceptional parameter values.
- **Exact conservation/consistency diagnostic:** construct a small exact coefficient matrix and use rank, underdetermination and residual relations to explain redundant accounting equations before numerical solving. Keep domain-specific conservation authority separate from matrix rank, and keep graph structural deficiency distinct from coefficient-dependent rank. Next specify the authored coefficient domain and a diagnostic that changes when parameters specialize.
- **Shared coefficient-domain product:** reuse a qualified polynomial/matrix extraction for class evidence, coefficient export or exact diagnostics where their definitions and coordinate scope coincide. Countercase: sparse selected evidence whose current derivative-based extraction avoids most work. Next trace two actual consumers and their allocation lifetimes before adding retained backing.

No new product mechanism, test suite or quantitative speed claim follows from these hypotheses. Source contracts settle their availability and limitations; targeted exact arithmetic/compile probes become useful only for a selected consumer with an unresolved integration condition.

## Simple exact trial points are a separate useful composition

Numerica `Rational::round_in_interval` is not restricted to reporting or approximate model reconstruction. It can choose a simple **exact** trial point in a rational search bracket without changing model coefficients. That is a legitimate additional discovery direction. The inspected root refiner in `implicit_cubic.rs` currently takes exact rational midpoints, evaluates the polynomial exactly, and updates the appropriate endpoint. Its admission proof derives both iteration count and integer-limb extent from successive halving.

However, the locked simplifier documents the **closed** interval `[l,u]`. Upstream `rounding` tests explicitly return the lower endpoint for `[1,1.2]` and `[2,3]`; a root iteration that substitutes this value without screening can make no progress. The implementation uses continued fractions and does not supply a halfway contraction guarantee or the current root refiner's admitted step/limb bound. It also does not use the receiver rational's value in its interval search. Thus replacing every midpoint is a poor fit for the current proven bisection loop.

Retain a lower-priority hypothesis for a new exact candidate-search operation, or a bounded interior-central-subinterval strategy that preserves sufficient bracket contraction. Its discriminator is whether simpler trial arithmetic actually avoids consequential coefficient growth while preserving the complete original work/admission bound; a generic endpoint screen and retry alone would add a fallback ladder without establishing that value. Source inspection settles endpoint/no-progress risk, so no runtime probe was needed. Source: locked Numerica `domains/rational.rs::round_in_interval` and its `rounding` tests; local `implicit_cubic.rs` bracket admission and midpoint loop.
