Realizations considered: installed `surrealdb-syn` 3.3.4, `surrealdb-sql` 3.3.4 and `surrealdb-types` 3.3.4. ## Types

### surrealdb-syn/parse-validate
- **Need it serves:** check that generated or hand-written SurrealQL parses under the exact server grammar, and inspect its statement structure, without running a server.
- **Recognizable code shapes:**
  - Generators that emit SurrealQL text with no syntax check until install time.
  - Ad hoc string checks (`starts_with("DEFINE")`) on generated catalogs.
- **Mechanisms and APIs:**
  - Grammar entry points:
    - `surrealdb_syn::parse(&str) -> Result<Ast, ParseError>` for whole scripts;
    - `expr`, `block`, `idiom`, `value`, `record_id`, `kind_for_definition`, `expr_for_definition`, `block_for_definition`, `duration`, `datetime`.
  - `parse_with_settings` with `ParserSettings::from_config` or `all_features` for capability-matched grammar.
  - The resulting `surrealdb_sql::ast::{Ast, TopLevelExpr}` and `Expr::Define(DefineStatement::{Table, Field, Index, Event, Function, Param, …})` can be pattern-matched.
- **Obligations discharged:**
  - Exact-grammar syntax validation, at the same version as the server crates.
  - Structural classification of statements.
- **Residual caller obligations:**
  - Semantic validation (types, references, permissions), which belongs to core lowering and a live server.
  - Choosing parser settings that match the server's enabled capabilities.
  - Keeping the parser version in step with the server.
- **Semantic conditions:**
  - Parse-only. The AST carries no storage-format guarantee.
  - `all_features` accepts syntax that a capability-restricted server may refuse.
- **Version / build conditions:** must match the server version exactly. The crates are internal, with no SemVer, and "free to change … even between patch versions".
- **Limits and negative results:** it does not lower or plan, so it cannot detect unknown functions or tables. The equivalent of the `surreal validate` CLI is available, but only as a whole-server binary.
- **Evidence:** Interface-checked: `surrealdb-syn-3.3.4/src/lib.rs` public functions and existing call sites (`xtask` parse-only validator, maintenance `parse_definitions`).

### surrealdb-sql/ast-render
- **Need it serves:** build or rewrite SurrealQL as a typed tree and render it to text, instead of splicing strings.
- **Recognizable code shapes:**
  - `format!`/`push_str` assembly of `DEFINE …` statements.
  - `.replace("__X__", …)` over raw SurrealQL.
  - Hand-quoted identifiers.
- **Mechanisms and APIs:**
  - AST node types in `surrealdb_sql::{statements, ast, expression, …}` implement `surrealdb_types::ToSql`.
  - `to_sql()` renders single-line output; `to_sql_pretty()` renders indented output (`SqlFormat::Indented`). `fmt_sql(&mut String, SqlFormat)` is also available.
  - `surrealdb_types::Value` and its parts also implement `ToSql`, which renders literal values with correct quoting.
  - A practical pattern is to parse a template with `surrealdb_syn`, mutate fields of the typed tree and render with `to_sql()`. One existing consumer normalises `DefineKind` and ids this way before comparing.
- **Obligations discharged:**
  - Correct quoting and escaping of identifiers and literals.
  - Structural edits without placeholder collisions.
  - A canonical rendering suitable for comparison.
- **Residual caller obligations:**
  - Constructing nodes by hand is verbose and tied to internal field layouts.
  - Rendered formatting is the library's own: it is not the author's layout and comments are lost. Byte-determinism holds for a fixed version only.
  - The escape helpers (`EscapeSqonIdent`, `EscapeObjectKey`, `EscapeRecordKey`) are in `surrealdb_types::utils::escape`, and `utils` is `pub(crate)`. They are reachable only indirectly, by rendering a typed node.
- **Semantic conditions:**
  - Round-trip fidelity of parse then render is covered upstream by `fmt_roundtrip_test.rs` in core. That is upstream evidence, not a guarantee across versions.
  - Rendering normalises spelling (keywords, number formats), so generated bytes would change when the crate version moves.
- **Version / build conditions:**
  - The `surrealdb-sql` crate docs say: "an internal implementation detail of SurrealDB with no stability guarantee. It is scheduled for deletion once the greenfield parser reaches parity … its API surface should not grow."
  - Every patch bump may break a builder written against it.
- **Limits and negative results:**
  - It is unsuitable as a durable statement-builder API.
  - For validation and comparison it is serviceable at a pinned version.
  - No public, stable SurrealQL builder exists in `surrealdb` 3.3.4. Search scope: the SDK `opt`/`method` modules, which expose bindings and typed methods but no statement AST builder.
- **Evidence:** Interface-checked: `surrealdb-sql-3.3.4/src/lib.rs` stability section; `surrealdb-types-3.3.4/src/sql.rs` (`ToSql`, `SqlFormat`); `src/lib.rs` (`pub(crate) mod utils`; only `utils::either` is re-exported).

## Current applicability

### [CBO-046](../../../library_leverage/codebase/registry-generation-and-python-boundary.md#cbo-046) — SurrealQL and Python emitted through string templates (SurrealQL side)
- **Types:** `surrealdb-syn/parse-validate` and `surrealdb-sql/ast-render`. Constants are covered by `surrealql/define-param-constants` in `surrealql-server-constructs.md`.
- **Realization:** installed pins 3.3.4, already in the lockfile, and already used by `xtask`'s `surrealql-tools` feature and by `pse-operations`'s `canonical-maintenance` feature.
- **Conclusion:**
  - Fits as generation-time validation. The parser could check every generated SurrealQL output, catalog and embedded scripts alike, at codegen time.
  - Ruled out here as a rendering or builder substrate. The AST crate is explicitly unstable and scheduled for deletion, and rendering would normalise the authored text, which costs the readable raw-SurrealQL counter-argument.
- **What it would discharge / what remains local:**
  - Validation would catch placeholder collisions and unescaped values that produce syntax errors.
  - Validation would not catch semantically wrong substitutions that remain valid syntax, such as a wrong integer.
  - Rendering of values could use `surrealdb_types::Value::to_sql()`, which is public and stable to the SDK's SemVer level, for any non-integer literal ever spliced. The present placeholders are integers and SurrealQL fragments; integers carry no escaping risk.
- **Prerequisites, configuration or extension:**
  - Wiring a parse step into the generator or `codegen-check`.
  - Choosing parser settings consistent with the server's capability profile (`all_features` versus `from_config`).
  - Accepting that the codegen crate then depends on the server grammar crate.
- **Semantic gaps against the CBO's preservation constraints:**
  - Byte-deterministic output is unaffected by validation.
  - It would be lost to library normalisation if rendering were adopted.
- **Unsettled premises and what would settle them:** whether a validation hop is wanted at codegen, given that maintenance activation already parses the catalog with the same crate. This is a design choice, not a library question.
- **Evidence:** Interface-checked. Proposed.
