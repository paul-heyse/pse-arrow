# Unified state management and persistence

**Architectural fitness: Revise. Behavioral adequacy: scoped failures; comprehensive scientific adequacy unresolved. Overall decision: Revise.**

The simulator needs one coherent account of state across authoring, preparation, execution, publication, restart and retirement. That account does not require one representation, one cache, one process or one universal state service. The current design has substantial foundations worth retaining: immutable authored revisions; explicit physical and numerical admission; complete selected dependencies; separate semantic, artifact and execution identities; attempt-private native work; a common allocation pool; short guarded database operations; and closed scientific results with exact lineage. SurrealDB can remain the canonical durable substrate while Salsa, mathematical libraries, native workspaces and operation-shaped Arrow representations perform their different jobs.

The weaknesses are at the joins between these responsibilities. A changed value binding retains the previous complete binding owner, so a latest-only consumer accumulates obsolete state. Optional mathematical retention can occupy the pool needed to construct the next useful product, while admission waits for a release that it does not cause. Source inventory consumers discard selection and bulk intent, and source protection receipts do not consistently have an owner that survives caller abandonment through cleanup. The public Rust composition boundary accepts independently valid resource owners without establishing that they belong to the same deployment. Host readiness and recovery checks also conflate states or equivalence scopes that their decisions need to distinguish. Cross-process cancellation correctly revokes scientific writes but lacks a reachable terminal-settlement path when that revocation interrupts export. These are several independent causes, not evidence that all state should move into the database or that one new coordinator should own every lifetime.

The preferred target is to preserve scoped semantic authorities and give each complete operation an explicit, sufficiently narrow ownership and validity contract. Stable structure should retain its actual allocations; changing bindings should retain only their own additional allocations. Disposable retention should yield when useful work needs the same capacity. Source acquisition should preserve useful selection and grouped retrieval through the existing native boundary. Cancellation should leave the cleanup or native completion owner responsible until its actual effects settle. Host observation, artifact association and mutable service state should remain different facts, including in acceptance oracles.

The recent campaign failures are useful leads. They do not establish a common cause or qualify these remedies. No numerical speedup, capacity increase, corruption, leaked native thread or stale scientific result is claimed by this review.

## 2. Responsibilities and the governing state model

The runtime is the composition root connecting semantic science, active resources and canonical effects. These authorities should collaborate through exact products and operations while retaining different reasons for change.

| Responsibility | Authoritative meaning and operation | Derived state and effect owner | Context needed for a local change |
|---|---|---|---|
| Authored model and physical context | Typed declarations, immutable revision, quantities/conventions, prerequisites, case roles and selected scientific policy | Modeling/quantity/compiler owners; admitted physical context retains original checked rows | Typed declarations and physical/provider context; native solve not needed for pure admission |
| Selected source validity | Positive objects, absent names, set membership, interpretations and exact current revision | `CanonicalStore`, `SelectedRead`, dependency receipts; source protection is current effect authority | Isolated native store for transaction behavior; pure dependency controls for semantic equality |
| Immutable mathematics and preparation | Complete semantic bodies, demanded support, structural views, values and attribution | Salsa local generation; compiler-issued products; mathematical library allocations; shared service retention | Compiler/library inputs and cancellation; no durable transaction during mathematical construction |
| Attempt execution | Actual bound problem, provider capabilities, numerical policy, start and branch permissions | Native session/worker, job ticket, CPU permits, allocation leases and supervisor | Real consumed native capability for integration; independently supplied policy facts for pure decisions |
| Scientific completion | Candidate evidence, original residual/domain/closure assessment, partiality and usability | `Completion`, reports and exact request/start lineage | Typed outcomes and original assessment products; exporters do not select scientific policy |
| Durable visibility and reachability | Exact run/attempt/manifests, immutable operation settlement, roots, protected reads and explicit retirement | Canonical guarded operations, staging and cleanup owners | Real emitted transactions for conflict/recovery evidence; no rerun of science to repair storage |
| Host/service authority | Actual service invocation, process start, cgroup/host allocation, database incarnation, receiving artifacts and maintenance phase | Service supervisor and host/native-operation owners | Controlled host observations; artifact bytes and association checked separately from mutable lifecycle facts |
| Python presentation and buffers | Typed authoring, execution handles and physical results; escaped copied bytes have independent memory lifetime | Process-owned resource service, Rust workflow, Arrow allocation owners and signal bridge | The current imported native artifact for boundary qualification; no Python numerical callbacks |

The scientific model is substantially adequate in the inspected scope. Definition, specialization, case, numerical policy, prepared mathematics, native layout, actual start, attempt, candidate permission and scientific result are distinct, and their operations consume those definitions. The registry is an authority for declared schema and wire meaning, not a substitute for scientific admission. `PhysicalContext::same_sources` does more than compare a physical digest; it also checks actual owners and support rows. `SelectedRead` records absence and membership as well as positive objects. Completion binds the start actually used and retains native status separately from physical qualification. These are governing contracts, not merely domain-named output records.

The operational model is less complete. A reusable allocation's ownership is too broad after rebinding; a resource budget does not establish the affiliation of independently supplied owners; readiness uses one Boolean for observations with different implications; recovery equality treats location and mutable lifecycle fields as immutable identity. The corrections below require these consequential distinctions at their actual decision boundaries. They do not require a universal registry or serializable state machine for every function.

## 3. Contracts, physical meaning and validity

| State/operation | Validity and equivalence | Current enforcement and limit |
|---|---|---|
| Authored/source identity | Scientific identity and exact canonical revision are different; names, pointers and row positions are not scientific keys | Versioned projections and registry codecs; exact protected selection rechecks current authority |
| Reusable semantic product | Substitutable mathematics under complete structural, physical/provider, interpretation and producer premises | Compiler-issued products, complete dependency receipts and explicit replay admission; receiving context does not partition pure body meaning |
| Active binding | Current values, fixed/free roles, bounds, derived parameters and attribution over shared structure | Rebind checks consumed values and frozen assumptions; allocation ancestry currently over-retains obsolete bindings (F01) |
| Attempt/session | Mutable native evaluators/factors belong to admitted work; cancellation request is not completion | Supervisor retains ticket, CPU and memory through native/TLS join; separate public waiter lifetime |
| Durable result | Closed membership, exact attempt and completion; a readable stored payload is not proof of scientific usability | Staging, freeze/reconcile and controlled terminal admission; exact `ResultRead` retains its read owner |
| Memory retention | Cache presence is disposable and does not confer validity, history or attempt authority | Finite retained-entry limits and pool leases; explicit clear fences mathematical late fills; pressure cooperation is incomplete (F02) |
| Source protection | A current exact database lease, distinct from copied immutable data and dependency receipts | Server expiry/reclamation checks preserve safety; several source operations lack abandonment cleanup ownership (F04) |
| Receiving/service state | Content identity, installation association, deployed interpretation and current liveness are distinct | Production checks retain many distinctions; harness equality and readiness decisions flatten them (F06, F08) |

Identity should remain explicit at each scope. `pse-ids` uses role/version-framed BLAKE3 preimages for semantic and durable identities; concatenation ambiguities and role confusion are not delegated to a fast bucket hash. Process-local prehashes, including `BasisKey`'s FxHasher hint, select buckets while complete equality remains authoritative. A faster local hash such as xxhash can serve that bucket role without replacing durable or semantic identity. Allocation addresses and local component identifiers retain their actual Arc owners; they are neither portable semantic keys nor durable compatibility promises. Pure body equivalence, producer qualification, the exact receiving context and fresh publication acknowledgement are four different permissions. A retained body or preparation cannot replace the other three. These are preservation constraints for ownership/pressure/invalidation changes, not a recommendation to replace durable hashes or evidence that hashing dominates preparation.

| Physical element | Dimension/unit and basis | Reference/convention/envelope | Authority consumed by state operations |
|---|---|---|---|
| Parameter, bound, specification and start | Declared quantity and canonical numerical scale; explicit fixed/free and start roles | Point/difference, basis and datum belong to admitted quantity meanings; changing a numeric value creates a new numerical state | Physical context, case binding, frozen-value checks and actual-start lineage |
| Equation/output/provider description | Physical input/output types and demanded derivative order | Authored guards, property/applicability context and provider configuration remain consumed premises | Compiler body admission and original candidate assessment |
| Dynamic state/time and samples | Declared state/time quantities and explicit clock conversion | Differential/algebraic role, mode/event and requested versus actual coverage remain separate | Dynamic preparation/completion contracts; a stored prefix does not become a full trajectory |
| Fit observation/parameter | Declared observed-output correspondence, weights and parameter quantities | Statistical and derivative validity conditions are not supplied by persistence | Fit preparation and completion; no new statistical qualification here |
| Stored scientific value | Original semantic coordinate, physical meaning and finite authoritative value representation | Missingness, diagnostic exceptional values, terminal class and usability are separate | Generated typed results, completion and exact result manifests |

**Well-posedness:** explicit case roles and selected structural products precede contextual class/capability admission; numerical topology is not inferred from storage or flowsheet traversal order. `prepare_resolved` validates values and frozen assumptions, consumes structural/class facts, and resolves normalization/tolerances. Original-model assessment and completion remain distinct from native termination. These source routes support the state-boundary design, but this review does not establish all structural rejection, derivative, dynamic index or physical-envelope behaviors. Cached structure cannot authorize a new numerical state without its required checks.

## 5. Complete operations and preservation constraints

A selected preparation protects current source, acquires sufficient immutable records, validates dependencies, completes reusable pure products, binds current attribution/values, and separately settles eligible persistence. Canonical transactions should cover guards and visibility rather than native construction. The current grouped source path already precharges selected decode ownership, reads bounded blocks and performs closing manifest/digest validation. The correction is to make consumers use this path with their actual intent, not to create another store or trust unchecked cached bytes.

A native job acquires a population ticket, then coordinated CPU/memory admission, constructs private workers, executes library-owned numerical operations, assesses the original scientific problem, and joins native destruction before releasing its active owners. `Flights` retains a retiring key when the last waiter departs; another requester cannot start duplicate work before completion. The mathematical cache's explicit clear fences late insertion without invalidating active values. These are useful strengths. F01/F02 concern which allocations remain live and when disposable references yield, not removal of those drain or accounting guarantees.

Scientific completion is captured before durable recording. Staging errors and persistence failures remain visible even if native values were useful. Exact readers use a frozen manifest rather than late staging; copied decoded arrays can outlive a read lease because they own their bytes. Root reachability, active-attempt authority and explicit source/result/analysis retirement are different from memory eviction. Maintenance/restore use their own closed authority incarnation. F09 identifies a missing composition: truthful cancelled lifecycle settlement must remain possible when scientific export is deliberately interrupted, with unavailable scientific completion. No correction should infer a committed result from a socket closing, a solver status, cache presence or an absent analysis header.

| Scientific stage | Formulation/derivative/scaling contract | Class, status and post-solve meaning | State-specific assessment and limit |
|---|---|---|---|
| Semantic/structural preparation | Authored guards, physical/provider contracts, demanded order, structural literals and normalized coordinates | No solver status; checked semantic product is not a solved result | Stable validity can be reused under complete premises; no new numerical qualification |
| Bound algebraic execution | Current values/roles/bounds, resolved normalization/tolerances and actual provider derivative capabilities | Class-specific native admission; typed native termination remains separate from quality/usability | Worker/session is mutable and attempt-owned; original residual/domain/closure assessment remains required for each candidate |
| Initialization/recycle composition | Scoped overlays and declared start/strategy; compatible structure/programs may persist | Each attempted step retains its own outcome; committed stage meaning is explicit | Rebind owner must not accumulate obsolete values merely to keep stable structure alive (F01); no convergence-controller reimplementation recommended |
| Dynamics/fitting | Same authored model with explicit analysis/experiment context, clock/coverage and derivative request | Actual endpoint/coverage and statistical validity remain original completion obligations | Retained trajectories, factors and experiment products require their own actual lifetimes; full algorithms not requalified here |
| Publication/result projection | Carries original completion, physical identities, start lineage and coverage | Exports cannot upgrade native status or partiality | Request-owned encoding/transport and database lease are separate from science and copied-array ownership |

## 7. Findings and corrective direction

### <a id="f01"></a>F01 — Rebinding retains obsolete binding ancestry

**Principles/scenarios:** AP-07, DP-10/DP-19/DP-20, PS-11; S01/S02. **Priority:** high for sustained edits/continuation. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`math/products.rs::own_rebind` passes `structure.owner.clone()` into `own_binding`. That owner stores both `_parents: vec![parent]` and `_payload: Arc::new(prepared.clone())`. `SharedAllocation::with_owner` in `pse-math/src/lib.rs` also preserves earlier accounting anchors. Consequently each changed rebind retains the previous binding's allocations and lease as well as stable structure. `math/modeling.rs::rebind_scoped` reaches this path for changed products. `math/initialization.rs::Blocks::attempt` repeatedly rebinds and overwrites `self.bound[index]`; replacing the latest handle does not break the ancestry retained by its owner.

A consumer retaining only the latest changed preparation therefore retains earlier bindings it no longer needs. This is allocation lifetime amplification, not an uncharged allocator leak or a claim that mathematical results change. An unchanged rebind appropriately returns shared state directly.

**Correction:** own stable structural/evaluator components independently and attach only the current binding's new allocations and wrapper to the returned preparation. Reuse the existing component/allocation machinery; do not merely move the predecessor chain elsewhere. Escaped aliases, original attribution and intentionally retained report evidence must continue to keep their actual bytes charged. A retained earlier report is a legitimate case; a latest-only edit is not a reason to retain every earlier whole preparation.

**Verification:** exercise repeated changed bindings with only the newest handle retained, alongside a control retaining earlier aliases/reports. Check original outputs against fresh preparation and pool ownership after dropping each class of consumer. Required state should follow live components/current bindings, rather than iteration history. No measured byte slope or speedup is claimed now.

### <a id="f02"></a>F02 — Disposable retention does not yield to useful-work admission

**Principles/scenarios:** AP-07, DP-10/DP-20; S02. **Priority:** high when preparation churn meets the pool limit. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`MathService::new` creates two independently limited caches, `entries` and `modeling_cache`, each using `MathPolicy::artifact_bytes`. Products retain pool-backed allocation leases. `ResourceBudget::validate` checks native cache policy and positive math controls but does not establish that these mathematical retention policies and the next construction can coexist. `jobs.rs::reserve_entry` and `admitted` retry `try_grow` and wait for `released`; `MathService::reserve` and portable scratch admission can refuse immediately. These miss paths do not evict service-owned idle mathematical entries. Cache capacity eviction occurs when products are inserted, which is too late if constructing that product cannot obtain memory.

There is a source-established reachable condition: useful work fits the finite pool without old disposable entries, but idle cache leases leave insufficient room, and no live consumer is about to release them. Admission then waits until its deadline or refuses even though dropping disposable references could permit progress. The current four-GiB fixture and its allocation failure do not isolate cache occupancy and are not proof that this was that failure's cause. The issue also exists independently of F01; cache eviction cannot repair ancestry retained by a live latest binding.

**Correction:** coordinate disposable retention and construction admission through the existing pool/retention owner. On actual pressure, drop fitting service-owned cache references and retry under the original clock, or use an explicitly coherent retention/headroom policy. Preserve active aliases, retiring flights, native/TLS drain and exact validity. Simpler reduced or disabled retention is a viable baseline when its recomputation tradeoff fits; a new budget or general scheduling framework is not required. Do not evict or invalidate useful active mathematics merely to make a command pass.

**Verification:** use controlled key churn where each useful operation fits, retain no external aliases to old entries, and distinguish cache-owned from active/flight-owned allocations. The next miss should make progress after disposable release. A control with genuinely live owners must remain honestly constrained. Later timing compares complete cold/warm operations without a minimum-gain prerequisite.

### <a id="f03"></a>F03 — Inventory consumers discard selection and grouped retrieval intent

**Principles/scenarios:** AP-07, DP-10/DP-13; S03. **Priority:** high for repeated preparation/conformance. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`workflow/modeling/canonical.rs::declaration_inventory` pages membership and calls `selected_object` sequentially for each declaration; `fit_declarations` does the same for each fit. Each scalar object path crosses extent and payload/manifest acquisition boundaries. The same module already implements `selected_objects`: grouped headers, precharged decoded owners, bounded block retrieval and final validation. Complete inventory is legitimate for full package coverage; per-object remote coordination is incidental.

`workflow/modeling/conformance.rs::conform` also unconditionally calls `self.declarations().await` before `policy.fixtures.tests`. `ModelingFixtureSelection::Selected` explicitly assesses no package coverage, yet it hydrates unrelated declarations before selecting the named tests. This is the same lost operation-intent problem at a wider scope. No claim is made that every selected scientific preparation does this, or that these crossings alone caused the current 20-second native-entry timeouts.

**Correction:** preserve explicit selected fixture IDs through exact logical resolution/kind validation and fetch their necessary scientific closure through existing selection owners. Keep full package coverage complete, but group its necessary inventory through the existing batch path. Complete fit inventory can use the same grouped acquisition. Preserve absent/invalid selection errors, deterministic report order, exact protection, extents, whole-object digest and closing admission. A legitimate fixture depending on declarations outside its display selection must still acquire those dependencies; output filtering is not permission to omit required inputs.

**Verification:** compare selected and complete reports against fresh admitted inputs, including an unknown selected ID, non-test ID, cross-declaration dependency and malformed block. Observe remote operation shape at different declaration counts; confirm that selected work is independent of unrelated inventory and that complete inventory uses grouped retrieval. No new cache or second source representation is needed.

### <a id="f04"></a>F04 — Source protections have incomplete abandonment ownership

**Principles/scenarios:** AP-05/AP-07, DP-19/DP-20; S04. **Priority:** medium; prerequisite for economical interruption. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`SourceRevision::open`, declaration/fit inventories and several other source methods acquire a 3,600-second protection and explicitly release it after awaited work. `ProtectedSelection` and `SelectedRead` are cloneable receipts without a release owner. Dropping the outer future between acquisition and the release statement skips that statement; the remote pin can remain until server expiry. `conform`'s initial declaration inventory additionally accepts no cancellation argument and precedes its fixture cancellation loop.

The existing selected preparation wrapper cooperatively drains a child selection on token cancellation, and `ResultRead::ReadOwner`/`PhysicalOwner` retain executor-bound final-drop release. These are useful contrasting mechanisms, not proof that arbitrary outer-future abandonment of every source path is covered. Expiry and guarded reads preserve safety; this finding does not claim indefinite authority, stale read acceptance or numerical work after all charges vanish. Repeated cancelled reads can nevertheless retain source reachability and bookkeeping far beyond their useful operation lifetime.

**Correction:** give protected source acquisition a scoped completion/cleanup owner that survives caller abandonment through the submitted work's necessary drain and release. Share receipt semantics separately from cleanup responsibility. Capture the executor where needed; preserve explicit awaited release/settlement when the caller remains, and finite server expiry as a shutdown/failure backstop. Release must not precede a surviving follower's required use or a submitted consumer's authority settlement.

**Verification:** drop/cancel after acquisition, during grouped read and during preparation/publication; retain a surviving follower as a control. Observe exact protection retirement and native/store drain, with executor shutdown separately scoped. Do not count local future drop or socket closure as remote-effect completion.

### <a id="f05"></a>F05 — Public runtime composition does not enforce deployment affiliation

**Principles/scenarios:** AP-02/AP-05, DP-03/DP-20; S05. **Priority:** high for the public resource contract. **Diagnosis: Interface-checked and Implemented. Remedy: Proposed.**

`workflow::Runtime::from_shared` accepts a `SharedRuntime`, `EngineFactory`, registry and canonical deployment independently and returns `Self` without validating resource affiliation. Operations/math use the supplied `shared` pool; engine validation/query/physical loading use the supplied factory's pool and extensions. `EngineFactory::new/from_builder` can legally originate from another `SharedRuntime`. Pairing factory B with shared runtime A is expressible through the public API and splits one workflow across independently accounted memory/CPU/cache owners. `EngineFactory::pool` and `native_state` already expose the facts needed to inspect the binding.

The inspected Python constructor and worker composition pass aligned owners. No wrong Python allocation was observed, and independently configurable direct engine factories are not themselves a defect. The defect is accepting their unchecked combination into the higher-level workflow's one-deployment guarantee.

**Correction:** make the workflow composition boundary construct or validate the supplied factory against the actual shared pool and consumed cache/CPU owners, with a typed refusal for mismatch. Preserve custom planners/functions/profiles that legitimately vary within that deployment. Related durable operation injection should be assessed for the same store/pool affiliation, without assuming that a downstream refusal already proves safe composition. A fallible constructor or an owned deployment-bound assembly is sufficient; no singleton or process-global state service is required.

**Verification:** aligned custom factories compose successfully; a factory from a second shared runtime is rejected before admission, source loads or native dispatch. Confirm reported allocations, query execution and numerical work all consume the intended owners. The remedy must not reject a harmless query-scoped partition/profile change that preserves those owners.

### <a id="f06"></a>F06 — Recovery oracles conflate artifact, association and mutable lifecycle identity

**Principles/scenarios:** AP-04/AP-06, DP-02/DP-04/DP-23; S06. **Priority:** high for trustworthy recovery acceptance. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`scripts/tests/canonical_recovery_check.py::journey` compares complete `primary_receiver` dictionaries after setup and restore. `surreal_server.py::publish_generation` produces absolute state-root paths to frozen worker/supervisor artifacts. `reroot_restored` deliberately relocates state-owned paths under the new root. The artifacts can remain identical while those legitimate association paths differ. Raw dictionary equality therefore rejects a legal copy/restore before it establishes scientific recovery behavior.

The harness's `recovery_identity` excludes only `resources`, `admission` and `accepting_writes`; its snapshot is taken before `server.start`. Service materialization legitimately writes `restart_qualified` and `unit_materialized`. Comparing the broad snapshots after that state transition mixes immutable configuration with mutable lifecycle observations.

**Correction:** define the actual expected equivalences at the recovery owner: unchanged artifact manifest/content and execution profile; explicitly rerooted owned associations; preserved or freshly established interpreter/permission/ABI facts as required; deliberate service/database incarnation and lifecycle transitions. Both setup and restore controls consume that meaning. Do not simply remove fields until equality passes or ignore exact host/profile admission. An external interpreter replacement is a revealing legitimate non-equivalence that must still refuse where consumed.

**Verification:** pure controls for allowed root relocation versus changed bytes/profile/interpreter/permissions, plus the real current restore/reopen journey. Use fresh current internal fixtures; no legacy analysis/result compatibility path is required. This finding blocks confidence in the oracle, not evidence that the database restored corrupt science.

### <a id="f07"></a>F07 — Lifecycle test oracles do not establish the phase they assert

**Principles/scenarios:** AP-06, DP-21/DP-23; S07. **Priority:** high for interpreting the active campaign. **Diagnosis: Implemented/source-inspected; historical failure observations have their original conditions. Remedy: Proposed.**

`derivative_worker_keeps_submitted_scope_in_actual_nested_factory_and_late_exit` starts a 100-ms absolute scope before admission, delays provider creation by 150 ms, and accepts only `ProviderError::Deadline` while requiring its cancellation flag to remain unset. `jobs.rs::admitted` legitimately observes that enclosing deadline, requests cancellation, joins the native thread and returns a typed time limit. The test does not establish a phase/order that makes its narrower subtype and unchanged flag the only correct outcome.

The `FixtureProbe` conformance tests start a 20-second wait while the operation still performs full source inventory/preparation. The probe records actual native entry and fixture completion. A snapshot with no entries and no recorded refusals cannot distinguish slow source acquisition, pending admission, a pre-fixture error or an actual native-dispatch defect. The recent four such timeout failures are therefore not four demonstrated missing-worker defects. Conversely, their uncertainty does not excuse the product route from examination.

Two additional assertions have the same problem at different boundaries. `generic_documents_prepare_revisions_and_cancel_without_poisoning` drops three caller preparations and requires the common pool reservation to decrease. `workflow/modeling/preparation.rs::prepare_selected` explicitly retains a `PreparedBasis` with descriptions and product owners in `modeling_cache` before returning a bound shared preparation. Caller drop does not establish final allocation-owner release. The failure therefore does not establish a leak; useful finite retention must not be removed solely to satisfy this assertion. This ownership-oracle issue is distinct from F01's obsolete ancestry and F02's pressure/progress policy.

`canonical_study_expired_claim_recovers_without_scientific_rerun` requests a one-microsecond lease and unwraps the claim before testing recovery. The authoritative generator `surreal_studies.rs::claim` deliberately checks the claimed lease after its point/operation writes and before returning. A lease that expires before transaction completion must refuse. The fixture has not established the committed-then-expired premise it claims to recover. The retained `lease expired before commit` diagnostic is consistent with this correct fence, not proof of failed recovery.

**Correction:** separate the actual contracts being tested. Use an established phase/controlled boundary for provider-specific deadline propagation; preserve the production operation's original clock and truthful timeout/drain behavior. Have end-to-end entry tests retain operation completion/errors and sufficient phase evidence to identify where work stopped, while local admission/native-lifetime controls exercise their bounded responsibility. This requires focused test synchronization/observations, not a new production tracing system, longer healthy-command timeouts or weakened lifecycle invariants.

**Verification:** legitimate admission expiry, entered-provider expiry, user cancellation and late native teardown are distinguishable and correctly classified. Ownership controls distinguish caller-only state, finite retained cache references, eviction/clear and escaped aliases; charges disappear only after the actual final owner releases. Recovery controls first establish an acknowledged claim, then its expiry through a controlled clock/barrier or bounded lifetime and state observation; expiry-before-commit must still refuse. A deliberate native-entry omission still fails; a real earlier refusal is reported as that refusal. Corrected current tests must exercise real science where scientific output is claimed rather than use obsolete internal results as an oracle.

### <a id="f08"></a>F08 — Readiness uncertainty can acquire unnecessary service-wide exclusion

**Principles/scenarios:** AP-04/AP-07, DP-02/DP-19/DP-20; S08. **Priority:** medium for concurrent host admission. **Diagnosis: Implemented/source-inspected. Remedy: Proposed.**

`surreal_server.py::owns_listener` returns `False` for both observed ownership mismatch and broad observation failures, including `OSError`, invalid/unavailable metadata, `SupervisorError` and host admission errors. `ready` collapses listener/protocol readiness to a Boolean. `scripts/test_resources.py::register` calls `start` when that Boolean is false. `start` acquires `lifecycle_reservation` before `_start` checks whether the service is active and healthy. While the reservation exists, `context_admission` refuses all new borrowers.

An unavailable ownership observation can therefore trigger a service-wide lifecycle exclusion even when startup was not established as necessary. Concurrent callers can also encounter a separate live startup owner rather than share its completion. This is avoidable failure/coordination amplification; the ownership checks themselves must remain strict. The fixed descriptor-enumeration race is useful narrow protection but cannot establish that every unknown observation now implies definite absence. No causal attribution to the current captured failures is made.

**Correction:** let the existing lifecycle owner distinguish verified readiness, definite actionable absence/unhealthiness, unavailable observation and startup in progress. Unknown observation should retain its diagnostic/refusal or retry observation under the original clock, not invent permission to change lifecycle. Demand startup should have one owned completion that other compatible callers can observe, preserving admission closure during actual changes. Do not restart an uncertain active server automatically, discard its allocation, weaken listening-socket proof or accept protocol readiness from another process.

**Verification:** inject unavailable process/systemd observations while a healthy service has borrowers; no new lifecycle action follows solely from unknown observation. Concurrent legitimate startup requests share one owner, and genuine wrong invocation/cgroup/socket still refuses. Actual effects remain under existing lifecycle reservation and drain authority.

### <a id="f09"></a>F09 — Cancellation revocation cannot settle an interrupted scientific export

**Principles/scenarios:** AP-04/AP-05, DP-19/DP-22, G5; S11. **Priority:** high for ordinary durable cancellation. **Diagnosis: Implemented/source-inspected, with a matching retained worker failure; assembled causality and native stop latency remain limited. Remedy: Proposed.**

`StudyHandle::cancel` revokes the guarded study header. The generated execution fence then correctly refuses renewal, append and close from the old writer. `DurableAttempt::finish` waits for stream completion, classifies lost heartbeat or ingestion failure as infrastructure, and calls `terminate` with `tables_complete = ingestion.is_ok()`. `terminate` can recover the exact closed attempt and discover that the study cancellation has cancelled the run. Nevertheless, its unconditional incomplete-export check returns an error before reconciliation/sealing whenever `tables_complete` is false.

The later `settled_cancellation` exception in `finish` requires an acknowledged, closed, terminal Cancelled attempt with the exact run/attempt key, manifest and matching cancelled completion. That exception cannot settle this path because the previous check prevented the required terminal/manifest. `record_study_attempt` immediately propagates the retained record error; the worker drains its lanes and exits unsuccessfully instead of concluding the ordinary cancellation. Correct revocation and native drain do not by themselves supply terminal lifecycle settlement.

The retained `cross_process_cancel_stops_scip` failure reports renewal/append/close refusal followed by `study.record_study_attempt.retained_result` and worker exit 1, matching this composition gap. The test's mark-start-plus-five-seconds wait does not prove actual SCIP entry, stop latency, the eventual retained attempt state or a native leak. Its `native_started` point fact records assignment/dispatch authorization; actual native entry and actual join need distinct observations. Those claims remain unestablished.

**Correction:** separate truthful operational cancellation settlement from complete scientific export. Reuse the exact closed-attempt recovery/reconciliation authority after actual drain, or supply an explicit equivalent branch in the existing termination owner. `Operations::recover` already reconciles frozen membership and seals a Cancelled/Failed lifecycle with `StoredCompletion.completion = None`; it demonstrates that the distinction can preserve current semantics. Retain the original ingestion diagnostic, exact attempt identity and readback acknowledgement. The worker concludes only after the appropriate exact attempt and point are settled. Genuine unrelated transport failures and unacknowledged settlement remain errors; rendered diagnostic strings must not decide cancellation.

**Verification:** cancel before/after native entry, during stream/table export and after actual join; old scientific writes continue to refuse and native owners really drain. Interrupted/incomplete exports settle the exact attempt/point Cancelled without inventing scientific completion, usable success, seeds or activation. Cancellation racing an already-complete export or arriving after an acknowledged terminal preserves the existing truthful completion/manifest and terminal semantics; it must not erase valid settled data unconditionally. Unknown final writes settle through immutable receipts rather than science rerun. A frozen prefix may be retained as observations but cannot become a complete scientific result. This remedy does not relax the fence or accept unsuccessful worker exit as successful cancellation.

## 8. Library fit and integration cost

The existing division is preferable to an all-purpose state framework. SurrealDB/RocksDB supplies durable indexed records and transactions; the application supplies exact scientific operations, phantom/conflict premises, operation identity and retirement meaning. Salsa supplies local pure incremental preparation, not canonical persistence or native handles. DataFusion supplies caches and a common memory-pool integration; application ownership should connect disposable retention to useful-work admission without rebuilding a generic cache implementation. Mathematical and native libraries own expression/evaluation/numerical machinery; the simulator owns physics, selected policy, starts and independent completion.

Grouped source acquisition already exists, so F03 calls for reuse rather than another query abstraction. Component allocation sharing already exists, so F01 calls for correct parent selection rather than a new allocator. The current native supervisor/flight design purchases a real guarantee that ordinary waiter cancellation does not erase actual work or its charge. Replacing it with a convenient cache or task primitive is justified only if that complete consumed guarantee survives.

The loaded capability skills support these integration roles at the repository's selected releases. No dependency upgrade or newly proposed third-party API is selected by this review. Actual optimizer and backend behavior remain version-specific; a library's name does not establish a query plan, absent-record conflict guarantee or remote abort. Replacing SurrealDB would need a demonstrated contract or workload advantage and a complete alternative for roots, guards, selection, codec and recovery, not merely fewer application types.
