# Implementation friction and Codex effectiveness

## 1. Assessment, scope and evidence

**Decision: Revise the inspected architecture.** The implementation interval contains useful corrections, and its failed or incomplete qualification is reported honestly. The remaining problems concern where assurance, preparation and resource ownership live: the worker bypasses an existing owned startup operation; macro I/O assurance is invalidated by unrelated caller bytes; deployment preparation can destroy another role's current compilation evidence; and local source selection repeatedly scans the complete revision even on a warm path. Retained-source replay also discards established immutable admission and reconstructs it through the external-document route. Nested build output is withheld from the existing live diagnostic consumer. These are distinct causes. They do not warrant replacing the numerical stack or relaxing scientific checks.

**Architectural fitness: G9 fails. Behavioral adequacy: the scoped resource/lifecycle contract needs revision, and current assembled scientific adequacy remains unresolved.** No new falsely accepted scientific result was established by this review. A byte association failure establishes an association failure; it does not establish invalid physics. ## 2. Responsibilities and the important boundaries

The recent work reinforces a sound decomposition. An admitted local model owns immutable authored objects, physical context and provider premises. Selection owns exact positive and negative lexical dependencies. Preparation and numerical execution consume that selection. Original-space assessment decides whether a newly computed state is usable. Recording owns acknowledgements, manifests and durable history; closing it does not silently convert durable execution into ephemeral success. Build provenance and deployed-code compatibility are separate from those scientific responsibilities.

These boundaries should remain. ## 3. Contracts and preserved guarantees

Four distinctions constrain every correction:

1. **Scientific identity, deployment compatibility and artifact association differ.** Relevant consumed inputs can support a selective producer identity. Exact loaded artifact plus runtime prerequisites can support a deliberately narrower deployment-local compatibility guarantee. Neither is a scientific oracle. The full-byte association currently selected by the strict campaign must remain exact unless a separately accepted contract explicitly changes it.
2. **Immutable source validity differs from receiving permission.** A retained admitted source may carry established structural validity. Moving it to another runtime can still require receiver-context, callable-provider, physical-interpretation and resource-owner checks. An external document remains untrusted even when its hashes are internally consistent.
3. **An unchanged program differs from a fresh numerical state.** Carrying valid structural or macro-I/O evidence forward cannot replace independent residual, bounds, domain, derivative-support and closure checks for a new solve state.
4. **An observation allowance differs from retained output.** The enlarged strict namespace allowance bounds temporary observation work. Python retains its startup lease through recording connection/open and then drops it; it is not a permanent Runtime charge. A proposed shorter scratch lifetime must still retain the smaller result and its actual ownership, and must drain the native observation before releasing its work allowance.

The relevant physical semantics are deliberately narrow:

## 7. Findings and corrective contracts

### <a id="f01"></a>F01 — Worker deployment startup bypasses the owned observation operation

**Priority: high. Implemented diagnosis; Proposed correction. AP-01/AP-02/AP-05/AP-07, DP-19/DP-20; G5/G9; S04.**

`xtask/src/bin/support/deployment.rs::open` performs `observe_deployment`, unbounded `std::fs::read(receipt)` and `verify_receipt_artifact` synchronously in its startup future. Those unscoped helpers use no-op checkpoints. Only the later receipt-free local-admission branch installs `StartupInterrupt` and calls the owned local operation. The strict branch never calls `MathService::observe_deployment_runtime`. `pse-worker::main` completes `runtime()` before `serve()` installs its ordinary Ctrl-C listener.

The Python recording integration uses the existing runtime operation, which preflights receipt extent, reserves observation work including the strict namespace allowance, checkpoints the original deadline/cancellation, and joins native work before returning its lease. This is a decisive conforming counterexample. The worker's configured host/process scope still protects the machine and ordinary process termination releases kernel resources; neither supplies per-operation preflight/accounting or the cooperative cancellation contract. A strict worker receipt can therefore consume substantial reading, JSON and namespace work before its runtime budget can refuse it, and cannot follow the existing startup cancellation path. No worker OOM or corrupt solution is claimed.

**Corrective contract.** The executable supplies the actual loaded role, selected receipt and one startup cancellation/deadline owner to a common observation operation. That owner decides admission, performs complete observation and produces outer attestation plus optional qualified producer only after success. Worker/Python retain their actual role and loading-specific checks. Establish the signal owner before observation, and release scratch only after native drain. Keep store connection/open as a separately effectful composition step rather than hiding it in observation. No new crate or universal deployment service is needed.

**Alternatives and preservation.** Reuse the existing runtime operation, or extract a smaller common owned operation if its current coupling is unsuitable. A process-wide cap alone leaves the mismatch. Preserve malformed/unknown receipt rejection, full actual artifact/current-input verification, strict-versus-local distinction, original stop cause and authenticated ownership. The Python temporary lease need not become a new finding: shortening its retention through connection setup is a compatible local refinement, with no demonstrated permanent budget leak.

**Closure evidence.** Inspect both composition roots and exercise actual strict worker startup with cancellation/deadline during observation, insufficient reservation and malformed/large receipt. Show no producer minted on refusal and no work charge released before the actual observation drains. A helper unit test alone cannot close the worker integration.

### <a id="f02"></a>F02 — Macro external-I/O assurance is invalidated by the complete caller-source closure

**Priority: medium. Implemented diagnosis; Proposed correction. AP-06/AP-07, DP-09/DP-16/DP-23; G9; S02.**

`producer_identity.rs::macro_caller_input_basis` finds transitive consumers, adds their dependency closures, and hashes every actual consumed source and compiler environment line under their unit keys. `capture` requires that complete basis to appear in `reviewed_callers` for Paste/Pest. The consumed bytes already participate in the actual scientific unit identity. The caller grant additionally establishes the separate external-I/O exclusions: reachable Paste environment segments and Pest grammar selection, preferred-path absence and actual compiler consumption.

The distinction is meaningful, but the physical grant is broader than that assurance's changing premises. The interval repeatedly reconstructs runtime/worker/Python caller bases after source changes and records that no new macro argument or external input channel appeared. The catalog's accumulated role-specific grants and rationale, and the six refreshed exact grants in `0733b22ae`, are observable manifestations. The observed episodes preserve a particularly revealing comment-only move in a cfg-test source that changed the caller bases without changing reached macro input channels. Changing an unrelated test body or runtime statement can require another manual I/O-completeness reconciliation although the macro owner's qualified behavior and supplied external-input channels have not changed. Ordinary unqualified runs remain available; the demonstrated burden is strict qualification/development change locality, not a claim that every value edit launches a compiler review.

**Corrective contract.** Separate compiler-consumed code identity from assurance about executable input channels. Let the macro integration consume a qualified owner/helper contract and a sound binding of the actual invocation channels it can use. Reopen the I/O assertion when those channels, their selecting arguments/generated emitters, executable closure, feature context or grammar presence/bytes change. Continue changing the scientific code identity when arbitrary consumed code changes. Unknown dynamic channels still refuse strict eligibility.

The exact narrower binding is a design decision, not an already proven optimization. A syntactic search for `Env` or `grammar` is insufficient: a legitimate generated macro can change a channel under unchanged immediate caller text. Closure must include such suppliers or constrain their execution. One viable alternative is to retain the selective scientific producer contract and improve channel evidence. The simpler one-host alternative is to use the existing exact artifact/deployment-local compatibility guarantee for ordinary persisted preparation and reserve selective cross-build producer equivalence for a named consumer that needs it. This intentionally loses cross-build reuse; it does not authorize accepting unknown code or skipping fresh numerical checks. Plan creation must choose the guarantee rather than silently weakening a hash.

**Closure evidence.** An unrelated caller-body change should alter code identity without reopening unchanged I/O assurance; a generated environment selector, new grammar shadow or changed feature must reopen it or refuse. If no sound narrower channel binding is adopted, document the retained strict cost and deliberately select the simpler supported local guarantee. A larger grant allowlist would leave the cause intact.

### <a id="f03"></a>F03 — Role capture and installation share a mutable preparation/evidence lifetime

**Priority: medium. Implemented diagnosis; Proposed correction. AP-02/AP-03/AP-06/AP-07, DP-19/DP-23; G9; S03.**

`producer_identity.rs::run` refreshes selected executor package-name families through Cargo cleaning for each selected capture. The source explicitly records that the clean invalidates all versions of those families in the selected profile. `producer_deployment.py::capture` runs runtime, worker and Python sequentially; qualification installs Python first, and later capture independently rebuilds its role before exact installed association. Actual build evidence snapshots useful selected build-script output text, but compiler dep-info association/review still consults paths in the mutable build tree.

The observed interval exposes the failure unit: Python refresh removed a worker-only compiler dependency file, requiring a fresh worker capture/review immediately before another refresh. The final worker diagnostic log records the fresh package-family cleanup; root observations at 20:23–20:25 UTC show the recapture/final-setup continuation. Separately, an installed/raw Python association failed; complete ELF inspection confined one observed difference to numeric LLVM symbol suffixes, and a supported installer observation later reproduced the exact authorized RPATH transformation. The historical suffix cause remains unproved. These facts do not establish that current installation is corrupt, nor that exact-byte association should be relaxed.

The remaining structural problem is that one role's preparation may remove the facts another role still needs, while installation and capture independently choose/build realizations that must later agree. Serial scheduling makes the race deterministic but does not give completed evidence its required lifetime. A single operator does not need a distributed protocol; it does need completed role evidence to survive the next local preparation step.

**Corrective contract.** One local deployment preparation owner selects effective role compiler/native/PyO3 configuration before effects, owns each actual role build and its compiler-consumed evidence, and carries completed evidence independently of future build-tree cleanup. Installation consumes the selected Python build realization and records its authorized transformation; it should not independently rediscover a different effective producer. Final association still observes the actual loaded installed module. Failure/retry reuses protected completed facts only while their recorded source, configuration, native and absence premises hold.

Viable realizations include immutable owned copies of role-consumed evidence plus artifacts, or a staged generation where executor refresh is coordinated over the actual selected contexts and completed outputs remain protected. This is a bounded operation contract, not a demand for a new registry, permanent build service or custom Cargo scheduler. Retain a fresh executor obligation wherever it establishes a real unobserved input; merely turning refresh off would not preserve that assurance. Avoid a blanket clean, loosening source checks or normalizing ELF symbols.

**Closure evidence.** Complete worker capture, prepare/install Python, then independently reconstruct the worker association without needing a missing mutable dep-info path. Retry an association step without silently changing its compilation context. Reproduce the final Python bytes through the declared installation transformation and observe imported bytes independently. Numeric suffix causality need not be invented to establish this corrected operation.

### <a id="f04"></a>F04 — Exact local inventory premises use whole-revision scans on warm preparation

**Priority: high for the interactive target. Implemented diagnosis; Proposed correction. AP-07, DP-10; G9; S01/S06/S07.**

`AdmittedModelRevision` indexes objects by logical identity only. `LocalSourcePremises::inventory` and `matches` implement each Scope, Kind, Name and References query by filtering `source.objects.values()`. The end-of-iterator check scans to exhaustion even for an empty result, correctly proving no extra member. `select_local` generates these queries for lexical resolution, imports and suppliers. `checked_selection` repeats them for each cache candidate, and `prepare_selected_basis` immediately calls `matches` again against the same immutable revision.

For N source objects and Q queried inventories, one premise pass examines Q complete N-object inventories, including unrelated declarations. Candidate checks and the immediate second check multiply that work. This is source-established work amplification, not a measured latency claim. The complete package can legitimately need one admission inventory; an exact name or retained namespace premise need not rescan that entire package on every warm preparation. The source already supplies the preservation opportunity: unchanged objects retain their Arcs when `AdmittedModelRevision::apply` makes a new revision, and logical lookup uses the map directly.

**Corrective contract.** The admitted immutable revision owns exact operation-shaped membership access for scope, kind/name and reverse references. Selection consumes exact ordered members or sufficient immutable membership witnesses from that owner; a premise-preserving step carries that checked relation rather than reconstructing it immediately. Update affected memberships on edits, with complete addition/deletion/absence semantics. Indexes are derived and allocation-accounted, not independently editable authorities. A simple set of maps is viable; no database, graph engine or generalized query layer follows from this finding. This removes repeated query-by-complete-revision scans, not every whole-source operation: `apply` still clones the logical-object map once per revision, and indexes add update/copy maintenance. A persistent map is a separate choice only if representative edit workloads warrant it. Initial full admission remains legitimate.

Preserve the revealing controls `local_exact_premises_reject_payload_collision_and_new_shadow` and `complete_namespace_inventory_resolves_nearer_names_without_leaf_or_import_probes`: a changed payload under a deliberately unchanged correspondence key and a newly introduced nearer name must still refuse stale reuse. Pointer identity may prove an unchanged immutable owner; a digest alone cannot replace the exact guarantee. Full scans remain legitimate for genuinely full-source work and for an independent verification oracle.

**Closure evidence.** Trace warm selection and preparation to the owned inventory access path; show that unrelated source growth does not multiply every exact query by the complete revision. Exercise positive/absent names, deletions, nearer shadows, kind/reference changes and payload/key collision controls. Measure end-to-end interaction only if claiming a quantitative improvement. A cache wrapped around the same repeated full scan without a valid immutable lifetime would not settle the cause.

### <a id="f05"></a>F05 — Retained in-process source replay loses its established admission at receiver rebinding

**Priority: medium. Implemented diagnosis; Proposed correction. AP-02/AP-07, DP-10/DP-23; G9; S05.**

`ScientificReplay::reconstruct_sources` walks the source for each modeling step. `ModelingPackage::reconstruct_replay_source` exports the complete already-admitted closure into `ReplaySourceDocument` and invokes its public reconstruction route. `Runtime::admit_replay_source` then rechecks payload hashes, decodes declarations, rebuilds lexical/reference structure and reapplies source admission. Within that external validator, each declaration and data member also searches the document object vector linearly. Repeated source positions can repeat admission; their output positions may be intentional and must remain stable.

For a supplied transport document, these checks establish necessary facts: internally consistent hashes do not prove lexical completeness or callable-provider compatibility. For the retained immutable Rust package, the source-body/closure validity is already owned and has not become untrusted merely because the publication owner closed or the receiver differs. What can change is receiver compatibility, provider execution context, interpretation and allocation ownership. The current route does not express that narrower operation. Ordinary in-process rerun retaining its original source is a healthy counterexample; this finding concerns explicit source rebinding, not every replay or solve.

**Corrective contract.** Distinguish rebinding an owned admitted source from importing a supplied document. Rebinding consumes its immutable closure and established validity plus the target's actual physical/provider/interpretation/validation and resource context; it produces an admitted receiver-local package without fabricating durable origin. Revalidate the properties whose premises changed and reuse source validity whose premises did not. Admit each identical retained closure once per receiving operation while preserving the original step-to-source positional mapping. External reconstruction keeps complete independent supplied-body validation; its logical/member searches can use a temporary exact index rather than repeated vector scans.

A smaller alternative is to leave transport admission intact, add the internal owned-source binding operation, and add no persistent replay cache. Reject this shortcut when a receiver's validation rules differ in a way the old admission does not establish; re-admit the affected property or fall back to complete admission. Never transfer a source receipt/acquisition permission based on content equality. After rebinding, each fresh solve still performs its original scientific checks and records its actual numerical dependencies.

**Closure evidence.** The durable-close/local-receiver journey retains exact source, callable and original solve identity, creates a fresh run with explicit ephemeral durability and no canonical keys, and does not reparse unchanged admitted declarations. A malformed external document, changed executable provider or incompatible physical/validation context still refuses or obtains required new admission. Preserve per-step output ordering even if unique closure admission is shared. This control closes the logical publication owner; it does not establish physical server-loss/restart recovery. The related per-member `parsed.encoded_data` search in `canonical/reload.rs` is a bounded lookup analogue, not an independently established dominant hotspot.

### <a id="f06"></a>F06 — The nested production build withholds diagnostics from the existing live consumer

**Priority: medium. Implemented diagnosis; Proposed correction. AP-06, DP-21; G9; S09.**

`producer_identity.rs::run` uses `Command::output()` for the entire selected Cargo production build, and writes actual-build evidence afterward. The outer role log receives the preceding cleanup text, then cannot receive Cargo stdout/stderr while the child compiles. The ordinary validation runner already reports gate start/end and supports live log consumption; it cannot display bytes buffered inside its nested child. Visible session observations at 17:36–17:37 UTC and later role captures repeatedly tail the capture log and inspect processes/disk while the expensive operation remains active. This establishes current diagnostic opacity and repeated investigation, not a measured amount of wasted time.

The defect is independent of F03: preserving completed compilation evidence does not reveal an active child's diagnostics, and streaming diagnostics does not preserve evidence that the next role deletes. A quiet link can legitimately take time, so absence of output must not be reinterpreted as a hung process or a new timeout policy.

**Corrective contract.** The capture owner emits its stage and forwards child diagnostics into the existing log as they occur, while preserving the exact raw JSON stream needed by current evidence parsing. Keep stdout evidence distinct from human diagnostics; retain actual child status, refusal and cancellation/drain outcomes. Expose graph/config preparation, refresh, build and verification transitions without inventing percentages or requiring a new dashboard, runner, scheduler or permanent event store. Existing capture logs and result readers are sufficient consumers.

The simplest alternative is inheriting or forwarding stderr while retaining the exact stdout evidence; a fuller streaming tee is justified only by the current consumers. A revealing child-output fixture emits a diagnostic, waits under test control, and proves that the outer reader sees it before child exit while final JSON/status remain identical. Inspect actual capture composition after the change. Time/token savings remain unmeasured. No rule relaxation is required.

## 8. Library fit and the machinery that should remain

## 9. Compatible alternatives and tradeoffs

The simplest conforming direction is to preserve current semantic owners and change their physical operation boundaries: a common admitted startup operation, owned role preparation evidence, exact revision membership access, and a trusted internal source-rebinding operation. These corrections compose. They do not require a second production numerical path, a new service or a universal evidence framework.

F02 carries a separate choice. Keeping selective cross-build producer equivalence requires sound channel-scoped assurance. Selecting exact deployment-local compatibility instead reduces what is promised and the associated preparation obligations, while retaining actual loaded-code/native/configuration compatibility. That alternative is especially credible for this workstation; it cannot be called an equivalent implementation of the stronger selective guarantee. It also does not remove F01, F04 or F05.

Keeping the current mechanism is safer than an unsound shortcut, but is not an architectural acceptance argument. Blind grant reuse, a hash-only inventory, accepting matching machine-code sections as full byte association, or skipping receiving-provider checks all erase useful guarantees. Conversely, repeatedly proving unchanged immutable facts does not strengthen new-state scientific assurance. The proposed benefit is removal of identified scans, repeated admission and cross-role recovery obligations. Latency, throughput, memory savings and convergence improvement remain unmeasured.

The defects have different prerequisites. F01 can consume the existing owned operation independently. F04 needs exact revision membership semantics before callers stop scanning. F05 needs a receiving-context compatibility contract before retained source admission is carried across owners. F03 needs an explicit effective preparation/artifact/evidence lifetime; F02's guarantee decision can simplify its scope but need not block ownership repair. Consequence priority is not an implementation schedule.
