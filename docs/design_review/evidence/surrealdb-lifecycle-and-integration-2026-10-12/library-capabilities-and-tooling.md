# SurrealDB lifecycle and tooling capability research

Supporting evidence for the [principal SurrealDB lifecycle review](../../reviews/design_review_surrealdb-lifecycle-and-integration_2026-10-12.md). The principal owns the reconciled judgment and final finding identifiers; local labels below identify bounded assessments only.

Research only, 2026-10-12. Baseline: coordinator reports commit `677394474a543c884a8a21d1a2626a6820ff834e`; present source inspected without mutation. Read both simulation-state and code-intelligence papers as leads. No installations, services, runtime probes, tests, commits, or product changes. Research was read-only; the coordinator published this supporting document. The maintainer subsequently selected the SurrealKit 1.0 beta line as target tooling; beta.6 is the exact assessed release. Integration remains Proposed. Other hypotheses below support coordinator decisions; they do not establish the final lifecycle taxonomy.

## Baseline and authority

- `Cargo.toml`: SDK `=3.3.0` from `vendor/surrealdb`, only `protocol-ws` and `rustls`; not embedded or gRPC.
- `vendor/surrealdb/PATCH.md`: optional finite native WS lifecycle, request clocks/cancellation/dispatch tracking and bounded replay. Normal requests do not use streaming cancellation; disconnect proves physical driver closure, not server abort. Any replacement must preserve these consumed contracts.
- `scripts/surreal_server.py`: `rocksdb://…?sync=every&versioned=false`. `docs/dev/surreal-substrate.md` separates application selection, explicit initialization, service readiness, and recovery qualification.
- Registry lowering in `crates/pse-codegen/src/codegen/surreal.rs`, exported by `codegen/mod.rs`, owns generated DDL and digest. `crates/pse-schema/src/catalog/substrate.rs` owns substrate declarations. SurrealKit may consume generated SQL; authoring a parallel schema or deriving Rust contract authority from a live DB would conflict with current source ownership.
- Generated `surreal.surql` contains bytes, string identities, typed relation endpoints, explicit guard functions and `FOR UPDATE`; search found no `REFERENCE`, `ASYNC`, or `CHANGEFEED`. This is current integration coverage, not a claim that the DB lacks them. Retention and publication already exist in `canonical_retention.rs`, `canonical_result_retention.rs`, `canonical_staging.rs`, and generated functions.

Context7 resolved/query docs for SurrealDB, SurrealKit, testcontainers modules/core, systemd, Tokio before primary-source follow-up. Skill baseline: `neo4j-surrealdb` SurrealDB GUIDE and reviewed real-time brief, recorded 2026-10-05 probes at 3.3.0. Those existing observations are not fresh product tests. Live docs are moving main: explicit 3.3.1 additions must not be transferred to 3.3.0.

## Selected beta capabilities and integration evidence

The following beta.6 contracts are **Interface-checked**, from the pinned [migration guide](https://github.com/surrealdb/surrealkit/blob/v1.0.0-beta.6/MIGRATING.md) and [test runner](https://github.com/surrealdb/surrealkit/blob/v1.0.0-beta.6/crates/surrealkit/src/tester/runner.rs), not executed here:

- `schema_from` chooses sync, rollout replay or both. Suite selection overrides CLI then defaults; absent selection uses sync. Both expands into separate jobs. Rollout jobs initialize empty databases using `run_up` with newest completion and refuse an empty rollout chain. This offers a concrete seam for testing the generated target through both installation routes.
- If any rollout job exists, sync is enabled and parity is enabled (default), the runner first compares schema descriptions from separately built sync/replay databases. It records comparison failure in the test report; fail-fast can prevent subsequent suite execution. Definition parity does not establish data migration, behavior, restart safety, scientific correctness or authenticated disposal. The sync builder uses the default module, so full sync command targeting does not automatically transfer to this testing route.
- Beta.6 plans freeze changed SQL beside each manifest with SHA256 checks; ordered catch-up applies that frozen SQL rather than today's schema folder. Missing/changed files, order and fork checks are useful reproducibility safeguards. Commit/ship the frozen files; older unfrozen manifests have different behavior. Incremental catalog reconciliation and readback improve interrupted-completion recovery.
- SDK3.3 and Rust1.95 are explicit beta.6 build requirements. Connection/sign-in has a default finite deadline; rollout-step SQL needs an explicit query timeout if desired. These tooling clocks do not provide the production patch's submitted-effect settlement or physical-drain guarantees.

Target the beta's declarative tests and frozen rollout artifacts under existing schema, selected-store and fixture owners. Generated-DDL parser/entity-tracking fidelity, exact command dispatch, failure-evidence retention, cleanup acknowledgment and lost-lock effect fencing remain integration work. No second schema authority, new shared deployment requirement or installation is implied by this review.

## Additional leads from code-intelligence paper

1. **LIGHTWEIGHT relations — defer/adapt narrowly.** [3.3.0 scanner](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/core/src/kvs/lightweight.rs), [3.3.0 tests](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/core/src/kvs/tests/lightweight_test.rs) and [table docs](https://surrealdb.com/docs/reference/query-language/statements/define/table) establish record-less endpoint pairs, idempotent canonical identity and enforced endpoints. They cannot retain properties, indexes/events, changefeeds/live, or an independent receipt record; nonempty REMOVE TABLE is rejected. Current analysis relationships carry source/target/kind/other fields and schema contracts, so wholesale conversion would lose meaning. A pure connectivity-only relation may remove edge records and unique-index maintenance. Table scans can walk endpoint adjacency, so compact storage is not an automatic faster lifecycle scan.
2. **INLINE caches — adapt only for actual graph/reference reads.** Same table docs and [3.3.0 inline tests](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/core/src/kvs/tests/inline_cache_test.rs): caches live on vertex tables; transactional writes maintain them. Caps0–256; overflow falls back to scans and remains there until cap changes; each write rewrites the cache value. This can remove small-neighborhood scans, but does not speed arbitrary string-ID joins or opaque payload traversal. Requires targeted access-shape evidence, not a broad cache mandate.
3. **EXPLAIN/INFO — adopt diagnostic use as hypothesis.** [official EXPLAIN](https://surrealdb.com/docs/reference/query-language/statements/explain), pinned parser/executor source coverage in installed surrealdb-core3.3.0. Standalone EXPLAIN ANALYZE FORMAT JSON supplies execution details; ANALYZE executes the statement, so restrict probes to reads or controlled fixtures. Diagnostic JSON is not a stable production interchange schema. Useful for expiration candidate selection, retention joins, index choice and neighborhood amplification; not proof of whole-operation performance.
4. **SurrealQL functions vs Surrealism — keep current function direction; defer WASM.** [DEFINE FUNCTION](https://surrealdb.com/docs/reference/query-language/statements/define/function) and [DEFINE MODULE](https://surrealdb.com/docs/reference/query-language/statements/define/module), [3.3.0 module implementation](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/core/src/legacy/expr/statements/define/module.rs). Functions can compose database work in caller transactions; current generated `fn::pse_execution_v1::*` already realize this placement. Surrealism is experimental and introduces module build/runtime/permission/serialization work. No lifecycle operation has yet been identified that needs custom WASM beyond current functions. It is not evidence for moving native scientific execution into DB.
5. **Search/vector/GQL/Postgres layers — defer for this lifecycle review.** No concrete lifecycle need was found in the papers/current selected paths requiring a second query dialect, lexical ranking, ANN or PostgreSQL wire. Skill3.3.0 GQL catalog explicitly records a subset, not general Cypher compatibility. Adding frontends does not simplify protection/publication. This is task-fit judgment, not library absence or a rejection of future domain retrieval use.

## Corrections to both papers

- Ground SurrealKit integration in a concrete migration/harness comparison. The maintainer selected the beta target; assess beta.6 advantages and obligations rather than falling back to stable0.7. Do not transfer moving-main functionality blindly.
- Explicitly disclose best-effort SurrealKit cleanup and lock-renewal fencing gap. Automatically disposed is too strong for accepted test results. Owning evidence/cleanup remains necessary.
- ASYNC at-least-once attempts are not eventual successful effects. Surface finite retries, maintenance dependence, external-side-effect duplication and the3.3.1 retry-budget change.
- Reference actions can remove simple structural checks but cannot see string/byte dependencies, prove restart completeness or replace all concurrent lease protection.
- Database disappearance from catalog and physical disk-space reclamation are different outcomes. COMPACT and REMOVE acknowledgment do not establish returned capacity.
- gRPC3.3 support is real; current WS feature/profile is different. Provisional rows require finality handling, and buffering restores memory costs. Streaming is a capability lead, not a measured memory improvement.
- Current VERSION is disabled. Default historical retention0 means unlimited when versioning is enabled; record expiration remains independent.
- Native bytes/chunks/metadata and reusable SurrealQL functions are already integrated directions. Do not propose rebuilding existing lifecycle mechanisms under paper terminology.
- Lightweight edges cannot model attributed lifecycle edges wholesale; inline caches trade reads for writes and have precise overflow semantics.
- The second paper's targeting warning remains consequential: beta.6 seed/test paths do not inherit sync's full matrix merely because flags parse. Confirm exact command/source before multi-target use.
- Both papers' final taxonomy remains a proposal. Scope records and recovery obligations need domain justification, not six buckets because a paper lists six.

## Remaining questions and evidence limits

- Which exact persisted relationships can move to typed REFERENCE without losing provenance, policy conditions, selected-reader obligations or multi-store identity? Qualify publish/reclaim and new-reference/delete races on3.3.0 RocksDB before deleting guards.
- Does SurrealKit beta.6 parser/sync fully preserve this generated DDL (functions, enums, assertions, permissions, enforced endpoints, schema digest, initial identity)? Source allows disabling entity tracking for arbitrary SQL; that fallback may eliminate the proposed pruning value.
- Which existing migration/test code can selected SurrealKit beta capabilities replace, and which adapters must retain metadata ownership, patched transport and failure semantics? Existing current-profile fixture capacity is the comparator.
- What operation is too large for current protected chunk/page retrieval, and can real streaming preserve finality/cancellation under the patch's original-clock contract? No representative memory or throughput measurements performed here.
- Are logical exports sufficient for the intended recovery objective, or must exact physical snapshot metadata/history/files be preserved? Existing substrate recovery guide separates these; no backup/power-loss guarantee established by library docs.
- Need verified operational physical-reaper status/returned-space measure if cleanup automation is justified. Source proves deferred mechanism, not measured reclamation latency.
- Negative coverage: no native TTL/user scheduler found in explicit official expiration docs plus3.3.0 DEFINE parser routes; no current integration of REFERENCE/ASYNC/CHANGEFEED in generated canonical DDL. This does not cover arbitrary plugins, cloud Agent Memory schedulers, unreleased engines or every repository workflow.
- Pinned core source/tests and previous skill probes were read, not executed. Testcontainers/SurrealKit source inspected, not installed or run. Product/scientific acceptance, remote deployment, physical power-loss recovery and performance remain unqualified.
