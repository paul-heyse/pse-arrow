## What exists and must survive simplification

scripts/test_resources.py owns fixture/evidence policy; ResourceRecord separates exact process/start/boot, service incarnation/ns/db, runner disposition, drain, manual retention, protected references, borrows, creator borrow, removal owner and cleanup state. resource_phase derives active/cold/disposed from these premises. It is not a bare TTL controller. register starts pinned; record_drain does not prove a passing runner outcome; finalize/resume_projection consumes authenticated frozen terminal identity. A missing ACK remains unknown, not failure or success by inference. Ordinary size, age or apparent orphanhood does not authorize deletion.

eligible refuses creator borrow, pins, non-pass without explicit release, absent drain, unknown kind/ref/borrow state, live borrows/references and populated exact units. Evidence additionally requires a producer-owned verified manifest. remove_report validates retained provenance and exact scratch ownership. reclaim checks drain outside metadata locks, rechecks unchanged ownership under short service admission, claims a cleaner before effects, performs effects outside metadata locks, and settles exact cleanup state afterward. An interrupted effect or expired settlement leaves protective removing/pinned state and exact retry; that conservatism is intentional.

scripts/resource_store.py owns durable metadata, not policy: private no-follow reads, atomic replace, file/directory fsync, invocation→identity→resource lock order; active access marker published before active authority and removed only after departure authority. FileStore.ensure explicitly refuses a fenced-but-unactivated legacy migration. test_resources.py has a real explicit migrate CLI, requiring an explicitly selected PSE_TEST_RESOURCE_STATE; the review must not claim there is no recovery command. Tests test_fenced_unactivated_recovery_refuses_waiting_legacy_writer and test_migration_replace_and_fsync_failures_preserve_fence_order inspect crash boundaries. These tests were READ, not run. The default registry's earlier refusal was a safe unresolved migration state, not evidence that a new authoritative store is required. Do not migrate someone else's live registry as a review probe.

reclaim_reports bounds active candidates (64 visited, at most4 effects, rotating cursor) and uses one clock. It is explicit retry, not an unbounded command-exit sweep. test_closed_service_defers_cleanup_until_same_generation_reopens demonstrates the intended deferred policy (read only). Evidence cleanup bypasses service admission entirely. A closed service refusing database disposal is not automatically a bug: cleanup may not restart/change an owner's service. If introducing scheduled cleanup, preserve that refusal and report defer reasons; a timer is a wake-up mechanism, never deletion authority.

scripts/surreal_server.py owns service/receiver administration. lifecycle_reservation uses short metadata exclusion and exact nonce/PID/start/boot, not an IPC-held flock. context_admission serializes admission, not whole effects. require_borrowers_drained refuses creator borrowers, exact live cleaners and undrained live fixture owners. all_contexts_drained examines unresolved reservations, observer cgroups and workers; dead launcher/empty unrelated cgroup are not sufficient. These controls go beyond what SurrealKit, native foreign references or REMOVE can supply.

backup is explicitly offline: reserve lifecycle, stop/drain selected service, require fresh destination outside live state, copy DB/config/private credentials/retained executable generations/receiver contexts, hash inventory. restore requires validated backup and closed admission; recovery phases preserve source and exact target identity, account cutover, old capability fencing and maintenance acknowledgment. copy_current_database reserves exact export path/nonce/inode, no-follow/private checks, drains maintenance listener and removes only exact owned export. recover_maintenance has explicit accounts/initializing/validated/disposing or cleanup/copy branches, and unknowns remain closed. No online filesystem copy or indiscriminate namespace drop was observed. Logical export/import alone would not preserve the whole operational identity model.

Native server selected database_endpoint is rocksdb://.../database?sync=every&versioned=false. Therefore paper VERSION/time-travel suggestions do not describe enabled current behavior and cannot recover a validated scientific checkpoint. Backend/history changes need their own choice. service server_environment scrubs inherited SURREAL_* and explicitly supplies WS message/write-buffer/session bounds, RocksDB cache/buffers/jobs/subcompactions/log retention, runtime worker counts and credentials. Lack of SDK Config::query_timeout on remote transport is not by itself absence of a deadline; review actual custom request context.

MCP is already integrated for read inspection of the exact existing selected service: mcp_authorization reads no-follow private credentials/readiness, matches live listener/invocation/binary digest/credential identity and releases only existing VIEWER credentials. New stdio `surreal mcp` would create a different embedded owner-access store and should not replace this interface. Domain destructive/admin tools need domain operation permission, not blanket owner-level MCP CRUD. No new agent-skill installation is needed to establish this review.

## Logical deletion versus disk recovery

test_resources.remove_database invokes pinned CLI REMOVE DATABASE IF EXISTS for exact owned disposable name/ns/instance, requires process status0, blank stderr and exact JSON [None]; cleanup=removed records this logical acknowledgment. It has no physical reaper/SST-byte completion witness. Official3.3 docs distinguish immediate catalog removal from delayed key reclamation; compaction and filesystem capacity are later storage effects. This is NOT evidence of a present deletion correctness bug, nor proof that space returns immediately. Target/reporting should name logical disposal separately from physical reclamation pending/observed when capacity decisions consume it. Do not demand a per-object byte ledger or disable safe whole-db disposal. No disk-space performance claim can be made from this review (no measurements). Native reaper knobs/compaction are candidates for churn diagnostics, not deletion authorization.

## Target composition

Favor a coherent operation vocabulary, not a universal lifecycle enum or a second universal metadata store. Distinct owners:
1. Scientific catalog: authored revision identity, retained runs/attempts, explicit seed dependencies, result sets/completion, studies/analysis dependencies and protected-reader leases.
2. Runtime: prepared semantic/numeric products, active native tasks, telemetry, in-process buffers, consumers of exact canonical permissions; copied immutable data can outlive a DB pin under its own memory owner.
3. Operational control plane: service instance, authenticated connections/borrowers, process/cgroup/native drain, admission/recovery/maintenance, executable generations and private credentials.
4. Test/evidence policy: runner terminal outcomes, disposable database ownership, producer-declared scratch versus retained artifacts, explicit release and references.
5. Native engine: catalog transaction semantics, record references, change history, async queues, key reaper and backend compaction.

These are composed at actual operations. Bootstrap/recovery metadata must remain readable while DB is down or fenced; forcing it into the DB it supervises creates a circular recovery dependency. Scientific facts should remain in the canonical scientific authority rather than replicated into JSON lifecycle records. A shared read-only inventory/status facade can expose owner-specific state without becoming deletion authority or copied status ledger.

Taxonomy must distinguish retention intent, reconstructibility, scientific usability, publication/visibility, execution state, live borrower permission, durable dependency/reference, logical retirement and physical storage reclamation. Scratch/recoverable/test/results/reference/audit classes are useful defaults, not sufficient state machines. Successful scientific solve, sealed output, numerical checkpoint, warm-start seed, runner outcome and drained transport are different facts. Neither reference count nor TTL replaces race-safe acquisition/removal order or exact effect settlement.

## Coverage limits / next material questions

### Development dependency observation

`crates/pse-operations/src/study_policy.rs` is effect-free and consumes typed study facts, model/diagnostic identities, petgraph and standard collections. Its direct tests do not need a running server or native scientific execution. Nevertheless, `crates/pse-operations/Cargo.toml` unconditionally selects the SurrealDB SDK/Tokio and dev dependencies `pse-codegen`, `pse-columnar` and Arrow. The `canonical.rs` schema-generator test uses `pse_codegen::codegen::canonical_schema`; the generator depends on `pse-columnar`, which consumes DataFusion common/execution, Parquet/object_store and Arrow. A filtered unit invocation still compiles the crate and its selected-root dev dependencies, including tests outside the filter. Thus runtime test isolation is stronger than compilation isolation. This observation supplies the principal review's development-loop assessment, rather than a timing measurement or automatic demand for another crate. Possible corrections must give production and tests the same actual policy owner, preserve genuine canonical integration, and avoid a test-only copied policy or store-free production Runtime. Earlier lower-generator extraction and direct-owner test migration are real improvements; they do not establish that this remaining policy dependency closure is necessary.

Source and selected tests were read; no fresh runtime/physical measurements. Did not qualify RocksDB churn/compaction, backup/restore under failure, remote deployment, async-event maintenance, connection replay faults or scientific scenarios. Absence of end-to-end coverage is a missing premise for broad implementation acceptance, not an invented new product defect. Existing Plan36 focused passes do not qualify actual managed1000-point sweep; stopped campaign remains stopped. No recommendation to rerun campaign as part of review.

Further design should settle only choices with concrete consequences: source-seed obligation granularity; multi-borrower connection ownership; explicit notification resync; generated schema migration ownership and SurrealKit fit; exact native-reference compatibility with bounded deletion; reclaim pressure diagnostics where disk decisions need them. Fulltext/vector/ISO GQL, hostedAPIs, Wasm functions, SurrealML and cloud control are eligible capabilities but require a simulator-specific consumer before prioritization. Distinct graph-native knowledge discovery does not establish suitability for scientific numerical iteration or state publication.
