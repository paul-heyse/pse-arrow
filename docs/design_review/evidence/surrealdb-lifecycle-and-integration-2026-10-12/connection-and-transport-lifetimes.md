No product or plan files changed during the bounded assessment. A new untracked `docs/surrealdb_white_paper_code_intelligence.md` appeared during investigation and was preserved. The final principal review supplies its own path and the single follow-up owner.

Standard: Core 3.4, Heuristics 1.0, template 3.4, Process-simulator 1.5 and pse-arrow binding. Design tier, target purpose, bounded subsystem. Criteria are the standard and a local-first concurrent workstation simulator supporting edit/re-solve, studies, recycles, dynamics, extension and local tests. ADR-0164 and blueprint §20.5/§20.6 describe current choices; they are not acceptance criteria. Remote deployment is a prospective extension, not a current acceptance obligation.

**Bounded decision: Revise.** The integration has useful finite transport ownership and honest uncertainty semantics. The remaining problem is not that all cancellation is absent or that every timeout is replayed. The supported shutdown/borrowing boundary does not account for durable operations depending on the same connection, and recovery of session restoration is incomplete. A smaller explicit-completion hole also remains for malformed replies without payload ownership. These block AP-02/AP-04/AP-05/AP-07 and hence G9 in this boundary. This review does not claim a numerical/scientific failure or whole-product qualification.

All diagnoses below are **Implemented** source paths and static architectural reasoning, not newly **Tested** reproduction. Corrections and benefits are **Proposed**. No tests, probes, services, formatting, generated outputs or destructive actions were run. Source locations identify the examined version; architecture citations use stable section IDs.

## Responsibility and contract boundary

- `canonical.rs` owns canonical options, local pacing, exact typed operations and operation-level completion checks. `CanonicalStore` clones share `Arc<CanonicalClient>` for ordinary requests and structural activation, `ProblemTurns`, and `ResultReadDrain`.
- `canonical_transport.rs` owns monotonic request clocks, response-allocation propagation, VIEWER → exact USE/probe → owner selection, uncertainty poisoning and SDK lowering. Its `CanonicalClient` owns one `Arc<Surreal<Client>>`, preserving a single application session rather than invoking the SDK's session-creating `Clone`.
- The vendored SDK/engine-api own channel admission, dispatch facts, response-channel lifetime, frame/decoded-value ownership, replay and physical socket shutdown. `scripts/surreal_server.py` configures the matching local server profile and independent server backstops.
- Runtime `Operations` clones the canonical store for claims, renewal, cancellation and publication. Python `NativeRuntime.close` invokes the canonical store's physical disconnect. Native worker destruction, storage-service release, and database effect settlement have separate owners.

Three different completions must stay distinct:

1. **Local memory/transport drain:** actual commands, frames, decoded values, socket halves and their accounted holds have been destroyed or deliberately transferred to a retained consumer. A caller deadline, admission semaphore release, map deletion or channel close is insufficient by itself.
2. **Database effect settlement:** an exact immutable operation is acknowledged or recovered by its original identity/request, or its effect authority is irrevocably fenced. Local socket drain says nothing about a server transaction that was already dispatched.
3. **Service/native release:** actual native work, descendants and service incarnation drain under their authentic owners. Neither a checked query nor `disconnect()` substitutes for it.

The current code understands these distinctions in several places; the corrections must preserve them rather than conflate every wait into one global shutdown.

## What is already fixed and should be preserved

`vendor/surrealdb/PATCH.md` is an accurate lead for substantial existing mechanisms, with the exception noted in CON-03 below.

- `RouteChannelEngine::with_shutdown` supplies 32 application and two control semaphores (`vendor/surrealdb-engine-api/src/lib.rs`); the bounded WS route channel and deferred/backlog capacities are finite (`native.rs`, `mod.rs`). Admission waits and response waits select against the original request interruption. A separate control class can progress while application slots are full. These are connection-local bounds, not an aggregate workstation-memory proof or an SLA.
- `send_request_message` distinguishes before/after `start_send`; the latter retains uncertainty. `maintain_request_lifetimes` retains dispatched correlations after interruption and invalidates the socket after its finite drain window (`mod.rs`, `350`). The native loop drops both split halves before `reset_sessions` releases correlation/admission (`native.rs`). Socket closure still does not establish server abort.
- `PayloadOwnership` separates clearable metadata, actual caller holds and actual driver holds (`vendor/surrealdb-engine-api/src/request.rs`). The response receiver drains queued values on abandonment; response handling drops raw frames before waking the output consumer and joins driver holds under the original clock (`engine-api/lib.rs`, `mod.rs`). This corrects the already-addressed symptom of releasing a byte grant while a late response still owns memory.
- `within_clock` nests minimum deadlines; `operation_scope` does not spawn/detach/drop the enclosing effect owner. Definite typed transaction conflicts alone retry the whole guarded decision; retries release the local turn before backoff. `bounded_query` inspects statement errors and refuses zero completions. Do not report these already-present controls as missing.
- Selection runs under a private VIEWER before restoring the writer. Cached presence is inaccessible after uncertain final authentication. An opaque completed checkpoint compacts only adjacent same-identity auth/USE/auth triples; intervening state, partial transitions and failed acknowledgements remain ordered (`canonical_transport.rs`, `mod.rs`). This is stronger than simply caching the latest namespace and token. A canceled owner transition cannot become reusable because a late acknowledgement arrives.
- Explicit initial catalog DDL uses a fresh unselected administrative session; it never treats missing namespace/database as permission for an ordinary open to create one. Structural activation and schema initialization have longer original clocks; ordinary requests remain shorter. Distinct physical clients therefore have a real role to assess, even though using two eager connections is not the only realization.
- `ResultReadDrain` refuses physical close while protected readers remain, atomically seals protection admission only when live count is zero, tracks cleanup tasks and retains release failures (`canonical_results.rs`). A failed close for a live reader leaves that reader able to finish. Do not remove this refusal to make a close path convenient.

## Scenarios

**CON-S01, composition/interruption:** start a durable simulation or study using a runtime, close the runtime while the supervised attempt remains active, then await its outcome. Native destruction and scientific publication must retain their required dependencies; close must either release only the caller, refuse coherently, or explicitly cancel/join the owned operation before physical teardown.

**CON-S02, mechanism recovery:** reconnect a workstation client after a storage restart; socket IO remains possible but one setup acknowledgement is delayed or never arrives. Individual requests must remain bounded, but subsequent work also needs an explicit session-restoration outcome and recovery route. New work may not run on a partially restored session.

**CON-S03, failure/resource recovery:** a bounded non-payload request receives a malformed RPC response while removed pending metadata is still live in a concurrent-map epoch or snapshot. Completed/refused local ownership must release finite admission independently of metadata reclamation, while preserving unknown database effects.

**CON-S04, ordinary domain extension/local tests:** add a model/result relation or another study composition. It should reuse canonical request, publication and drain contracts; transport auth/session internals stay inside the integration owner. Local request failure tests need a protocol peer, not a native scientific solver or a production database. Existing flatbuffer mock-peer tests demonstrate a credible local testing seam in source; no tests were executed here.

**CON-S05, prospective binding:** add an explicitly supported remote storage deployment. TLS/host identity, credentials, admission selection, clock assumptions and lifecycle capabilities belong to a storage connection/deployment binding. This is not achieved by simply removing the loopback check; current local state/service authority has different meaning. No remote capability is demanded for the present supported scope.

## CON-01 — Physical connection close excludes protected readers but omits durable borrowers

**Priority: high. Foundations AP-01/AP-02/AP-04/AP-05/AP-07; DP-19/DP-20; G9. Scenario CON-S01.**

`CanonicalStore` is cloneable and its clients are shared (`canonical.rs`). `disconnect(&self)` waits for only `result_read_drain.close_and_drain()` before closing both physical clients (`canonical.rs`). Python `NativeRuntime.close` clears caches and calls that method, with no active-run registration, borrowed-capability check, cancellation/join or runtime closed-state transition (`crates/pse-py/src/workflow.rs`).

The missing dependency is concrete: `Runtime::from_shared` builds durable `Operations` from `canonical.store().clone()` (`crates/pse-runtime/src/workflow/mod.rs`); `Heartbeat::spawn` clones `Operations` and renews through `operations.store`, recording failure and canceling the run if renewal fails (`workflow/durable.rs`). The same store is used by durable publication/sealing. `RouteChannelEngine::disconnect` closes the shared sender and both shared admission semaphores (`vendor/surrealdb-engine-api/src/lib.rs`). Separate native drain ownership keeps native memory alive; it does not keep this canonical dependency usable.

**Consequence:** when a durable dependent has no remaining counted protected reader, one close can revoke renewal/export transport for that live dependent. Other cases instead refuse close because source/result protections happen to remain. Protected-reader count consequently becomes an accidental proxy for whether it is safe to stop all persistence work. The same public `CanonicalStore` API permits one alias to invalidate unrelated outstanding mutations or aliases without representing that close authority. This is a lifecycle/modeling defect, not a claim that disconnect itself should settle or abort server effects.

**Corrected operation:** distinguish a borrower's logical release from authoritative physical close. The connection owner must know whether outstanding canonical-dependent operations or readers still require it, close admission atomically with starting authoritative shutdown, and produce either a refusal identifying live dependencies or completion after the owned dependencies are finished. At the runtime boundary choose and state whether `close` means release this caller, refuse live work, or cancel/join its own work. Remaining independently supervised work must keep the canonical capabilities it needs until renewal/publication settles. A short owned activity guard or existing runtime ownership may suffice; no new distributed lease or universal lifecycle framework is required.

**Preserve/counterexample:** a slow reader must retain its existing refusal/finish behavior. A second caller legitimately sharing a prepared runtime must not be canceled merely because the first caller releases its handle. Conversely, a fixture or operator explicitly authorized to close the whole physical owner must still have an actual transport-drain operation. Do not replace the reader check with `Arc::strong_count`: internal clones, optional caches and real dependents have different meanings.

**Distinguishing verification:** deterministic local test showing close-versus-live durable renewal/export, independent borrower release, close/admission race, and eventual physical close. Show both refusal and last-dependent completion, and retain exact uncertain mutation identities. Native science need not be started merely to test the borrower contract; one integrated durable run can establish the consumer wiring.

## CON-02 — Session restoration is ordered but lacks a finite terminal operation contract

**Priority: medium (high for availability of interactive work after reconnect). AP-02/AP-05/AP-07; DP-12/DP-19/DP-20; G9. Scenario CON-S02.**

A `ReplayCursor` carries only awaited ID, index and refreshed flag (`mod.rs`). `run_bounded_router` wraps the call to `replay_session` in five seconds, but `replay_session` only sends the first command and returns before its acknowledgement (`native.rs`, `mod.rs`). The acknowledgement chain continues through `handle_response_with_id`. The maintenance path checks interrupted ordinary `pending_requests` and deferred callers, not replay elapsed time (`mod.rs`). Replay commands have no ordinary pending context and hence never reach the 90-second dispatched-request invalidation rule. Pings are transmitted; this loop does not establish a finite acknowledgement/restoration lifetime.

**Consequence:** if a setup acknowledgement never arrives on an otherwise open transport, callers expire and their deferred requests are discarded, but every later request parks behind the same cursor. Bounded caller refusal is real; recoverable session readiness is not established. Existing `native_sdk_stalled_replay_refuses_cancelled_and_expired_routes` (`canonical_transport_tests.rs`) explicitly disconnects after proving refusal; its source does not establish automatic recovery or a terminal connection state for this condition.

There is a related restoration-outcome ambiguity: `send_replay_command` returns `false` both for exhausted replay and failed setup transmission, clearing the cursor on send failure (`mod.rs`, `1398`). `replay_session` always returns `Ok(())`; the acknowledgement branch treats `false` as permission to flush deferred routes (`mod.rs`). A transport failure normally causes later IO to fail too, but the state machine itself does not distinguish restored from partially restored. Do not depend on a second sink failure as the restoration invariant. This review establishes the ambiguous control path; it does not assert a reproduced wrong-database write.

**Corrected operation:** the transport integration owns one finite restoration operation per socket/session incarnation: the ordered acknowledged setup to restore, deadline/interruption, and explicit ready/failed/disconnected outcomes. Only exhaustion after acknowledged success admits application routes. Missing acknowledgement or send failure must keep routes undispatched, retire or reconnect the physical incarnation as selected, and preserve queued callers' original clocks. This can be a small cursor/state extension with a distinct result, not a second session manager. A finite terminal failure and explicit reconnect/reopen route is a viable simpler policy; automatic retry is not mandatory.

**Preserve/counterexample:** an unusually slow legitimate setup may need an explicit finite restoration budget independent of one short caller. The first caller's cancellation must not cancel a restoration still useful to other callers. Never replay unknown application writes in an attempt to recover setup, and never compact away intervening session variables/auth transitions.

**Distinguishing verification:** mock peer holds a replay acknowledgement while continuing socket/ping traffic, then either acknowledges before the selected restoration bound or never acknowledges. Verify ready versus terminal/reconnecting outcome, no partial-session dispatch, and queued caller expiry under original clocks. A sink that fails one setup send must not cause deferred application dispatch through the same partially restored state.

## CON-03 — Malformed non-payload replies bypass explicit admission completion

**Priority: medium. AP-02/AP-05/AP-07; DP-20; G9. Scenario CON-S03.**

Normal replies call `pending._admission.release()` (`mod.rs`), and socket reset calls it before clearing metadata (`mod.rs`). `handle_parse_error` correctly invalidates the physical socket if any pending request carries a payload owner (`mod.rs`). But its non-payload branch removes a named pending request and sends an error without explicitly releasing admission (`mod.rs`); the unidentifiable-envelope path does the same for every pending request (`mod.rs`).

This is not just an assumption about map implementation. The locked `surrealdb-types==3.3.0` hashmap is a Papaya wrapper: `take` removes and **clones** the retired value; `values`/`to_vec` also clone values (`~/.cargo/registry/src/.../surrealdb-types-3.3.0/src/hashmap.rs`, methods `take`, `values`, `to_vec`). `PendingRequest` clones share `Arc<AdmissionPermit>`. Dropping the local removed clone does not guarantee destruction of the retired map value or another legitimate snapshot. This is the very ownership distinction the patch handles explicitly on normal completion/reset. The failure branch leaves no reachable pending correlation for later reset to release.

**Consequence:** finite application/control slots can remain charged after the malformed response has been delivered and correlation removed, depending on incidental epoch reclamation. Repeated protocol/decoding errors can exhaust the bounded connection even while no live pending requests remain. This is a remaining non-payload symptom; do not reopen the already-fixed payload-owned parse-error drain path.

**Corrected operation:** every terminal removal has an owned, idempotent admission-completion action, independent of map reclamation. For an unreadable response, choose physical invalidation where authentic completion is uncertain; otherwise explicitly release admission after the actual local handler/queue ownership is done. Preserve dispatch uncertainty and do not mark a malformed response as successful scientific or database completion. Consolidating terminal cleanup is useful only if it keeps physical bytes, replay commands and correlation lifetimes distinct. A native single-owner map may remove epoch-retention complexity, but replacing it is not necessary to fix this hole.

**Preserve/counterexample:** payload-owned malformed frames and partially transmitted commands must remain charged until actual physical drain. Releasing the semaphore does not release payload bytes or settle database effects. The correction must not turn a blanket `Drop` into premature release.

**Distinguishing verification:** hold a retired/snapshot pending value, inject both named malformed-response and fully undecodable-response errors for a non-payload request, and assert exact application/control capacity is reusable without forcing epoch collection. Repeat the existing owned-payload malformed-frame case to preserve its stronger drain boundary.

## Library fit and alternatives

The vendored 3.3.0 patch is justified by real consumed gaps, not merely by a preference for a custom driver. The original/request-local clock, before/after-dispatch classification, explicit physical shutdown witness and externally accounted response ownership must live at a boundary that sees actual routes/frames/socket destruction. An outer Tokio timeout and the upstream route `with_capacity` alone cannot establish those facts. Replacing the patch with an outer timeout would regress the implemented contract.

Current official Rust SDK documentation, fetched through Context7, describes `Surreal<C>::clone` as creating an isolated session while sharing its physical connection ([primary documentation](https://github.com/surrealdb/docs.surrealdb.com/blob/main/src/content/reference/rust/concepts/multi-tenancy.mdx)). That supports the importance of the current explicit `Arc<Surreal<Client>>` reuse. It is not evidence that the custom single-session bounded profile should support SDK session cloning or that current docs qualify unpatched 3.3.0 cancellation/drain. Version-specific behavior above is grounded in the actual vendored/locked sources, not old capability-map assertions.

Viable mechanism comparisons:

- **Current narrowly patched native SDK:** preserves library codecs, query builders and ordered session setup. It has the least near-term migration risk for existing typed operations. Keep the explicit patch rationale and reduce exceptional lifecycle paths as the findings are repaired. New model/result families should not touch vendor transport state.
- **Upstream WS SDK plus caller semaphore/timeout:** simpler only in apparent surface. It lacks the consumed local drain/dispatch facts unless upstream adopts equivalent functionality. Revisit on a resolved SDK offering the complete lifecycle contract; absence of a feature in a summary is not proof that every newer SDK lacks it.
- **Dedicated small WS integration using existing RPC/types and Tokio/Tungstenite:** can put the finite single-session actor and lifecycle state in one repository-owned transport module, removing broad SDK builder/engine-api customization. It must still own authentication replay, version negotiation, request correlation and the same byte/response drain. This is a credible replacement-axis experiment, not an established simplification or measured performance improvement. Do not hand-roll codecs or scientific operation logic.
- **HTTP request integration:** request-local selection can avoid a mutable replaying session and is eligible for investigation. It still needs exact value fidelity, response bounds, physical client-buffer lifetime and unknown-write settlement. The examined vendored HTTP engine does not carry the new request-context ownership mechanism; switching protocol is not a free correction. No claim of full HTTP qualification is made.
- **Embedded core:** removes an RPC boundary but changes service/process ownership and concurrent workstation access; it does not automatically replace the selected multi-process storage service. Direct RocksDB opens by every client are not a viable substitute. A single owned local service using an embedded API is a different integration choice requiring version/ABI and operational assessment.

The current 32+2 admissions, 34 routes, 64 replay entries, message/write buffers, five-second IO attempts and 90-second interrupted-request window constitute a selected finite native profile. Their exact values are not capacity evidence. The same profile spans `Config::bounded_requests`, engine-api admission, native router limits and supervisor attached-session settings. Keep a clear construction/validation owner when these knobs change; arbitrary independent user tuning can invalidate the envelope. No new configurable scheduler or mandatory capacity benchmark follows from this bounded assessment.

## Rule impacts and correction relationships

**CON-RC01:** ADR-0164 and blueprint §20.5/§20.6 currently select the minimal pinned SDK/engine-api WebSocket patch and authenticated loopback profile. Repairing CON-01/02/03 inside that integration requires no mechanism rule change. If subsequent design instead selects a dedicated WS/HTTP/embedded integration, amend that specific mechanism choice while retaining exact canonical operation contracts, full value fidelity, original clocks, selection safety and independent drain/effect settlement. Keeping the current rule means implement the corrections in the pinned adapter/patch; it does not justify ignoring them.

**CON-RC02 (only if remote support is selected):** ADR-0164 and `CanonicalStore::connect` currently restrict native WS to loopback and consume local supervisor state. Remote support would need a new explicit storage/deployment binding and corresponding rule amendment. Keeping the rule leaves remote deployment outside supported scope, which is acceptable for this review's local-first target. Do not expand native lifecycle/cgroup assumptions to remote services by analogy.

No license, pin, existing-plan exclusion, fixed process budget or native algorithm rule was used to reject an alternative. No rule change is applied here. The Python `close` documentation describes current behavior, not an authoritative permission to break a live durable dependency; CON-01 requires its public contract to be clarified together with implementation.

CON-01 has the highest consequence and requires the coordinator to settle logical release versus authorized physical close before downstream runtime/Python remedies. CON-02 and CON-03 are independently repairable within the transport owner; neither needs service/native supervision redesign. CON-03 is the smallest repair but does not close CON-01/02. A common terminal-cleanup helper may serve the latter repairs only if it preserves distinct byte drain, session state and effect outcomes. Proposed alternative transports must honor the same contracts rather than erase distinctions to reduce code.
