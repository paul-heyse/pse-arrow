## T01 — Strict capture evidence has a shorter lifetime than its review consumer

**Interface-checked current design gap; observed operational consequence.** The coordinator intentionally held Python capture while the reviewer read runtime/worker dep-info, because fresh capture refreshes those files (R visible commentary at 17:58:31.509 UTC (R)). Later Python refresh nevertheless removed the worker-only `prettyplease` actual `.d`; worker recapture was required (R, 20:23:54.227 UTC commentary; also R, 20:27:56 command). The decisive durable source review is A/`producer-input-review/aligned-runtime-python-macro-caller-source-review.json`, fields `status` and `worker_gap`: the worker review was withheld because the associated `prettyplease-0.3.0/.../build_script_build.d` had been removed by later Python refresh. A/`aligned-worker-macro-caller-source-review.json`, `earlier_gap_resolution`, records regeneration by fresh worker capture and exact independent reconstruction without metadata/package fallback. I, 20:24:48.311 UTC, says it is standing by for fresh worker capture. This is evidence of actual repeated work, without a measured duration attribution.

The producer owner explicitly invokes `cargo clean --profile ... --package <family>` for selected build scripts/proc macros (`xtask/src/producer_identity.rs`); `executor_refresh_packages`/`executor_refresh_families` document family-wide cleanup rather than exact-version cleanup. The `capture`/`artifact_dep_info` operations consume per-unit compiler dep-info from the mutable target namespace. `selected_build_output_observations` preserves raw selected build-script logs and `.d` files found **under build-script OUT_DIR**. It does not preserve every rustc unit's dependency file that later independent caller reconstruction needs. The `run` operation records Cargo stdout/graph and these partial output observations in actual-build evidence. The existing snapshot is useful, but the consumer's needs exceed it.

Consequence: a source review consumes an earlier completed capture yet remains dependent on later build-directory state. The coordinator must stop unrelated subsequent captures or repeat an expensive role build. This crosses a preparation/evidence lifetime boundary (AP-02, AP-06, AP-07; H12/H13/H19/H23). The refusal to grant a caller basis without actual association is healthy; the avoidable cost is losing the association evidence, not the refusal.

**Proposed contract.** A completed strict capture should preserve, in its existing evidence output, the exact per-unit rustc dep-info used for association and the raw caller-input observations needed to independently reproduce its caller basis, including generated inputs that later refresh can remove. The capture owner seals that view while its current source/output consistency checks still hold. An independent reviewer consumes the completed evidence rather than a mutable Cargo namespace. Live deployment/current artifact verification remains separate and must still revalidate current inputs/bytes when making a current-artifact claim. Preserving historical bytes is not permission to transfer them as fresh execution.

Smallest viable implementation is extending the current actual-build evidence and its reader; it does not need a new evidence registry, service, harness, build cache or obligatory report packet. Immutable/revision-addressable source can be referenced with exact identity; volatile generated inputs need owned retained bytes. Do not blindly copy a whole target tree. Preserve explicit failure if a needed input cannot be captured consistently.

Alternative: deliberately review and seal each role before launching the next role. This is a viable immediate work method and uses no new code, but it serializes reviewer/build coordination and remains vulnerable if a later review needs an earlier missing raw observation. Another alternative is isolation in separate checkout-local targets/worktrees; it preserves evidence but duplicates preparation, and is disproportionate for serial work by one coordinator. Native `cargo clean --dry-run --verbose` can explain the invalidation surface before mutation, but does not itself preserve evidence. Current official Cargo docs describe that preview; it was queried through Context7 and then checked against the [Cargo clean command reference](https://doc.rust-lang.org/cargo/commands/cargo-clean.html). No dry run was executed here, and current documentation alone does not establish the pinned Cargo implementation's exact deletion behavior.

A revealing legitimate case is a source edit or generated input change between capture and review: the historical capture may remain reviewable as historical evidence, while current deployment must still refuse until its changed premise is reviewed/captured. A remedy that merely reuses a stored eligibility boolean would be wrong. A meaningful acceptance case captures role A, runs role B's real refresh, then independently reconstructs A's exact caller basis from retained A evidence; changed current inputs must still fail a current claim.

## T02 — Capture output is buffered across the expensive stage

**Interface-checked current diagnostic gap; repeated monitoring observed.** `producer_identity::run` in `xtask/src/producer_identity.rs` uses `Command::output()` for the entire selected production build; Cargo stderr and stdout become available to the outer log after completion. Actual-build evidence is written only then. The visible capture log often contains only the preceding cleanup line while compilation is active. R at 17:36:09.421 UTC polls the tool session and tails the capture log plus disk usage; R at 17:37:25.149 UTC repeats tail/disk/process inspection. The same pattern appears through later runtime, worker and Python captures; R, 20:27:56.138 UTC, gives a representative later poll. Repeated tails, process inspection and disk checks are visible throughout the window. Their overlap does not establish a count of unnecessary commands or measured time lost.

The ordinary validation runner already has a better pattern: gate-start command/log, gate-end status, `checks.json` checkpoints, failure tails and optional live streaming (`validation.execute`, `report_gate`, `checkpoint` and `validation_result.file_observation`). The existing runner and result reader are the natural consumers for this capability. `--live` cannot reveal Cargo output buffered inside the nested producer process.

**Proposed contract.** The producer capture owner should make its current stage visible as work happens: graph/config preparation, executor refresh, build, input/namespace verification and completed/refused capture. Stream Cargo diagnostics to the existing log while retaining exact raw JSON evidence separately. Report a child PID/unit identity where already authenticated, last output/activity time and output destination; never equate quiet output with stalled work or an empty cgroup with completed cleanup. A simple line protocol in the existing log is sufficient. An optional machine-readable stage record can be justified if the existing result reader consumes it; no new runner is implied.

A legitimate long compiler link may remain silent. Progress should state `building; no new diagnostic`, not fabricate percent completion or a timeout failure. Preserve stdout/stderr parse separation and cancellation/drain behavior. Historical accepted output parsing should remain identical; a targeted child-output fixture can distinguish streaming from merely printing the buffered result earlier in a different function. Any claimed time or token savings require measurement; none is claimed here.

Priority is medium: reduced ambiguity and repeated process archaeology, independent of T01. Streaming does not solve evidence destruction, and snapshots do not solve long silent compilation.
