# Product lifecycle and execution inquiry

Supporting inquiry for the [principal review](https://github.com/paul-heyse/pse-arrow/blob/6af92d1dee1ffa0b80dca71e03a63b489f2d940c/docs/design_review/reviews/design_review_implementation-friction-and-codex-effectiveness_2026-10-14.md), not an overall principal verdict or a second disposition ledger. Baseline examined: clean `main` at `d5e8606bb`; change window `945fad591^..d5e8606bb` (2026-10-14 approximately 11:35–16:36 EDT). The root owns publication and finding disposition. This inquiry is read-only; no tests, builds, services or fresh captures were started.

The selected criteria are Core 3.4, Efficient Architecture Heuristics 1.0, ProcessSimulator 1.5 and the pse-arrow binding. The functional target is an interactive simulator, including value edits without structural rebuilding, studies, recycles, dynamics and extensions. Actual environment is the sole operator's local Linux workstation with Codex and the current coordinator model. No portability or multiple agent runtimes are assumed. Existing repository rules explain current choices; they are not architectural acceptance criteria.

Three production patterns deserve correction. Worker startup still bypasses the bounded observation owner used by Python. More broadly, the locally owned source revision has an indexed logical-object map but implements every other lexical access by scanning that complete map, including cache-hit validation. The new disconnected replay control reaches another unnecessary boundary: exporting already admitted local source into a transport document and re-admitting it as if its bytes had crossed a trust boundary. These are distinct causes. The namespace allowance increase and report-clock repair are useful local repairs; they do not establish that their enclosing lifetimes and physical work are optimal.

## P1 — Worker startup bypasses the shared observation lifecycle

**Implemented; source-traced diagnosis.** `deployment::open` in `xtask/src/bin/support/deployment.rs` is the real worker deployment composition. It connects/opens the canonical store, verifies its executable, invokes synchronous `observe_deployment`, reads the selected producer receipt with `std::fs::read`, then invokes synchronous `verify_receipt_artifact`. The strict branch returns its qualified producer without entering the local observation branch. Only the receipt-free local replay branch creates a 60-second startup clock, cancellation source and SIGINT listener and calls `MathService::observe_local_runtime`. Consequently the initial outer observation bypasses the owned job on both branches; all strict receipt work bypasses it as well.

This is exercised by production, not just fixtures: `runtime` in `xtask/src/bin/pse-worker.rs` calls `deployment::open` after building `SharedRuntime`; its `main` creates a Tokio runtime with two worker threads and runs startup via `executor.block_on(runtime(&cli))`. Serving and its cancellation owner only begin later. Synchronous startup runs on the `block_on` driver thread. The two Tokio worker threads can still progress background tasks, so this is **not** a claim that the entire executor is starved. The narrow established fact is that this startup future cannot yield/check its operation deadline or cancellation during those synchronous reads and traversals.

`crates/pse-buildinfo/identity.rs` shows that `observe_deployment` forwards a no-op checkpoint and may scan the complete outer checkout. `verify_receipt_artifact` in that file likewise forwards a no-op checkpoint. `DeploymentAssociation::verify_current_scoped` hashes every selected file and complete namespace. `namespace_digest_scoped` now admits up to 512 MiB of conservatively charged metadata, 262,144 entries and 16 GiB of examined content per namespace. `FileObservation::capture_scoped` streams file bytes in 64 KiB chunks: **16 GiB is examined content, not a 16 GiB resident allocation**. These finite internal limits and the actual process cgroup can still bound failure. What is absent is the shared application-pool reservation, operation clock and cooperative cancel/drain contract for this production route.

The healthy counterexample is Python `NativeRuntime::open_recording`, `crates/pse-py/src/workflow.rs`, which invokes `math.observe_deployment_runtime` under an original startup deadline/cancel source. That helper (`crates/pse-runtime/src/math/portable.rs`) preflights receipt extent, reserves observation plus namespace capacity, uses the completion-owned native job and checks original cancellation/deadline throughout. `MathService::admitted` in `crates/pse-runtime/src/math/jobs.rs` joins the actual native thread before releasing capacity. The source already contains the needed capability; this is consumer composition drift, not a need for another observer framework.

**Consequence and priority.** A real strict producer worker startup can spend substantial file/namespace work outside the application budget and continue until synchronous work returns or the process is externally terminated. A process kill remains possible, and the process cap remains real. The defect is missing controlled startup lifecycle and consistent capacity ownership, not a demonstrated leak, a measured OOM or a false scientific result. It is important because managed studies depend on worker readiness and the reviewed fix expanded an existing namespace limit by orders of magnitude without moving this consumer onto its matching owner.

**Proposed correction.** Create the startup deadline/cancel listener before any expensive deployment observation, then route both worker branches through the existing owned observation operation. Keep actual executable verification and explicit strict-versus-local eligibility semantics. A startup failure must leave no readiness publication and preserve native job ownership until join. Construct/open the store in the order actually required; it need not stay on the critical path before pure deployment observation. Do not create a second scheduler or new resource framework.

**Verification boundary.** Inspect both actual branches after the change, including cancellation while observing outer files, reading receipt bytes and traversing a namespace. A focused real worker startup/interrupt control should establish returned classification and completed native drain, not just success of `namespace_digest` by itself. No such fresh execution was performed here.

**Criteria:** AP-03, AP-05, AP-07; DP-19/DP-20; H17/H21/H23/H25. Scientific PS-G1/PS-G2/PS-G3 are not disproved by this lifecycle finding. No repository rule needs overturning to compose the existing worker with the existing observation owner.

## P2 — Local semantic selection still repeatedly examines unrelated source

**Implemented; source-traced diagnosis.** The immutable authority is `AdmittedModelRevision`, `crates/pse-runtime/src/workflow/modeling/canonical/local.rs`. It owns an `objects: BTreeMap<String, Arc<LocalSourceObject>>` keyed by logical identity. `AdmittedModelRevision::apply` clones that map and preserves unchanged object owners. `LocalSourcePremises::logical` is indexed. All scoped/name/kind/reverse-reference inventory queries, however, are represented by `LocalInventory` and implemented by `LocalSourcePremises::inventory` as `source.objects.values().filter(query.matches)`.

These queries are actual compiler selection operations. `ModelingPackage::select_local` in `crates/pse-runtime/src/workflow/modeling/canonical.rs` resolves scoped names, members, imports and package engineering rules through `inventory`, creates name/namespace demands while traversing new declarations, and requests referenced suppliers by kind. Cold selection therefore performs a complete source-map pass for each such demand, even if the requested bucket is empty or has one member.

The same physical scan survives on the warm path. `LocalSourcePremises::matches` (`crates/pse-runtime/src/workflow/modeling/canonical/local.rs`) checks logical premises through the map, but checks **each** remembered inventory by scanning all source objects again. It runs for each cached selection candidate in `ModelingPackage::checked_selection` (`crates/pse-runtime/src/workflow/modeling/canonical.rs`) and immediately again before basis reuse in `prepare_selected_basis` (`crates/pse-runtime/src/workflow/modeling/preparation.rs`). Proving that no extra member exists causes successful comparisons to exhaust each filtered full-map iterator. With N source objects and Q inventory premises this contains Q full source passes on a matching candidate. This is a structural statement about the code, not a latency measurement. The same immutable exact owner is not given an immediate identity shortcut.

This does not prove structural mathematics is rebuilt; the code specifically reuses selected admissions and prepared bases. It shows that avoiding rebuilding structure still pays unrelated full-inventory work to establish reuse. A large imported library can therefore increase a tiny root's unchanged edit/re-solve preparation work, and additional cached candidates can multiply that proof work. `matches` contains no inner cancellation checkpoint; cancellation is checked before each candidate, so a long comparison delays cooperative interruption.

**Proposed shared correction.** Let the admitted immutable revision own operation-shaped derived access paths for scope/name, scoped kind and reverse references, with exact deterministic member order. Update the affected buckets when source objects are added, removed or replaced, preserving unchanged bucket owners where possible. Both cold selection and premise comparison consume these access paths. An exact same admitted owner can carry its already established premise validity. `CheckedSelection` can retain the exact bound source owner so that unchanged immutable handoffs do not perform the same comparison again. Ordinary BTree maps/vectors and ownership are sufficient; this does not require a graph engine, certificate format or a new dependency.

Preserve all semantic guarantees: added nearer names must invalidate a previous absent-name observation; removed names, kinds and reverse references must change their buckets; equal version strings with different payloads must still refuse; ordering/multiplicity must remain as promised; provider, registry and validation-context changes must not borrow a prior context's validity. Simply skipping membership checks, accepting hashes alone, or caching by root ID would be an invalid remedy. A value-only edit may change a payload without changing membership; the index and comparison must still reflect the affected object's actual bytes and consumed scientific dependencies.

**Analogues and scope.** This is the same missing physical-lookup choice seen in replay transport admission below, but it is broader and more consequential because it reaches ordinary warm preparation. `SourceRevision::open` deliberately reads a full selected source once to establish an owned local closure; that necessary import is not identified as waste. `checked_selection` does preserve explicit positive/negative semantic premises and prepared basis reuse, and the design should keep those strengths. `ModelingPackage::admit_study_points` in `crates/pse-runtime/src/workflow/study.rs` passes one reusable declared-study admission across points; `ModelingPackage::assessment` in `crates/pse-runtime/src/workflow/modeling/assessment.rs` prepares a value-independent observation program, then evaluates each new candidate. These are positive examples of stable preparation and changing numerical state at different lifetimes.

**Verification boundary.** Use the same exact source and a narrow value edit with a large unrelated source inventory. Show that unrelated buckets are not traversed repeatedly, while absence/shadowing/deletion/payload-collision and context-change controls still refuse correctly. Existing root mathematics and new-state original residual/domain/closure checks remain mandatory. No quantitative benefit is claimed without later measurement.

**Criteria:** AP-02/AP-04 are strengthened by keeping one immutable semantic owner; the current execution route violates AP-07 qualitatively for demand-shaped warm preparation. Relevant H5/H9/H12/H13/H18/H19/H28 and PS-11. No rule impact is required for derived local indexes or ownership-preserving validation; they fit current semantic contracts.

## P3 — Disconnected in-process source transfer takes the full external-import route

**Implemented; source-traced work. The remedy remains Proposed.** The new `solve_durable_replay_after_publication_close_requires_explicit_local_receiver` control calls `ScientificReplay::reconstruct_sources` after closing the publication owner (`crates/pse-runtime/src/workflow/modeling/canonical.rs`). That public Rust operation (`crates/pse-runtime/src/workflow/replay.rs`) maps each modeling step's source to `ModelingPackage::reconstruct_replay_source`. The latter reserves a conservative whole-source scratch envelope, clones the complete owned source into a `ReplaySourceDocument`, then calls the document's public reconstruction method (`crates/pse-runtime/src/workflow/modeling/canonical.rs`; `crates/pse-runtime/src/workflow/replay.rs`). This is transport re-admission despite its input still being the original immutable admitted source and its real callable/physical owners.

`Runtime::admit_replay_source` does substantial justified work for **external** documents: actual native/physical/provider comparison (`crates/pse-runtime/src/workflow/modeling/canonical.rs`); object/payload/reference rehashing and duplicate checks; decoding declarations and recomputing lexical dependency meaning; ingress/data/source identity validation; then `AdmittedModelRevision::apply(self, None, &edits)` creates new owned source objects. The existing source and its exported copy remain live while fresh sources are allocated. The 256 MiB reconstruction ceiling is an explicit refusal, not truncation. It can make retained in-process transfer refuse for work whose immutable inputs already exist.

There is also a direct access-path defect in that importer. For every declaration it linearly searches `document.objects` for its logical object; for every data member it repeats a linear search. With D declarations and M objects, that adds D*M candidate comparisons, independent of genuine lexical resolution. Constructing a borrowed logical-object map while validating duplicate logical identities would remove these repeated searches while preserving full external validation. The related repeated-find pattern appears in parsed reload (`crates/pse-runtime/src/workflow/modeling/canonical/reload.rs`) when each changed data document scans `parsed.encoded_data`; this is a bounded second instance, not a proven dominant hotspot. Source ownership is already indexed in `AdmittedModelRevision`, making the lost lookup especially clear.

**Multiplicity distinction.** `ScientificReplay::sources` deliberately returns one positional source per modeling step; constructors encode source indices. Positional output is a valid contract. It does **not** require re-admitting the same exact immutable closure separately for each step. Both `reconstruct_sources` and `document_with_limit` (`crates/pse-runtime/src/workflow/replay.rs`) repeat complete source work for positional duplicates. In-process ordinary `rerun_with_cancel` is a healthy counterexample: it clones each retained package, drops the old engagement and reconstructs original case inputs without exporting/re-importing source (`crates/pse-runtime/src/workflow/replay.rs`). Therefore this is specifically a disconnected receiver/transport export problem, not a claim that every ordinary rerun rebuilds source.

**Proposed correction alternatives.** The smallest change is to index external import lookups and memoize actual admission of each exact repeated closure while preserving positional outputs/source-index mapping. The better in-process boundary is a checked rebind of already admitted immutable source to a compatible receiving caller, with fresh local origin/head and engagement, retained actual providers/physical/validation/allocation owners and explicit ephemeral intent. A truly different deployment, registry, validation interpretation or provider premise still requires actual re-admission or a truthful refusal. Closing publication alone does not mutate admitted bytes or their scientific validity and should not force transport reconstruction. Keep the external document importer and its scientific checks intact. Do not copy a closed caller, durable head or stale publication capability into the new receiver.

Deduplicating portable document sources would change their positional wire contract and needs deliberate versioning or an explicit source-index map; it should not be smuggled into the in-process memo change. An in-process memo can return cheap aliases in the original vector order without changing the format. This inquiry recommends first removing redundant import work and introducing a sufficient compatible-receiver boundary, not committing to a broad replay-format redesign.

**Consequences and priority.** The code demonstrates avoidable whole-source materialization, repeated validation and worst-case quadratic object searches. No measured speedup, observed large-source refusal or whole-scientific qualification is claimed. This is below the direct ordinary preparation path in P2 in frequency, but it is the actual production operation selected by the newly added recovery test. The single small algebraic-root control establishes composition for its named scope; it cannot establish large/multi-step recovery fit.

**Criteria:** AP-02/AP-03/AP-06/AP-07, H5/H9/H12/H16/H18/H19/H24; PS-11 and preservation of PS-10. Indexing and memoization need no rule changes. A checked local rebind changes the implementation's current `reconstruct_sources` promise to route through raw production re-admission (its doc comments and call structure), and needs an explicit receiving-validity contract. No inspected ADR required every already-owned in-process package to be serialized and re-admitted; the principal should not invent such an obstruction. If a current rule is interpreted to require it, list that specific requirement as an RC and retain only indexed/memoized external re-admission if the operator keeps it.

## Repairs and limits that should remain distinct from these findings

The mapping fix in `crates/pse-buildinfo/identity.rs` separates 1 MiB mapping buffers from smaller kernel/environment metadata limits and adds two buffers to the working reservation. Its test (`scientific_process_mapping_extent_preserves_code_checks_and_finite_limit`) retains executable/writable/unknown-code refusal. The prior 128 KiB premise demonstrably failed the scientific Python import set according to the owning Plan38g record. The correction is technically coherent; a finite limit still needs to fit supported imports, and no claim of universal import feasibility follows from the fixture. I found no second production mapping parser using the removed 128 KiB constant in the inspected buildinfo/runtime/Python/worker routes.

The namespace repair correctly keeps full namespace traversal and separately reserves strict Python capacity instead of silently truncating guards. Its broader relevant-input selection, overlapping namespaces and source-versus-installed-artifact assurance are coordinated with the sibling/tooling inquiry, not settled here. The new 512 MiB allowance alone does not remove traversal work.

`startup_observation_job` in `crates/pse-runtime/src/math/portable.rs` returns the full observation preflight envelope as its retained lease, while `StartupDeploymentObservation` contains only outer identity strings/hashes and optional qualified producer identity. In the **actual Python consumer**, the local `startup` in `NativeRuntime::open_recording` survives until `CanonicalStore::connect`, `store.open` and `with_canonical` complete (`crates/pse-py/src/workflow.rs`), then drops. This is **not a lifetime-long Runtime reservation**. It carries roughly 550 MiB plus receipt-envelope reservation through unrelated connection work when a strict receipt is present. `MathService::admitted` already separates temporary work from actual retained result size (`crates/pse-runtime/src/math/jobs.rs`); `observe_local_runtime` already reports actual retained observation bytes (`crates/pse-runtime/src/math/portable.rs`). Releasing temporary namespace/receipt capacity after native join while retaining only the escaped result's actual size is a sensible local follow-up, especially if worker composition reuses this helper. Its severity is bounded: no permanent reservation or actual starvation was demonstrated.

The report-clock repair preserves `None` through `borrow_report`/`reference_report` (`scripts/test_resources.py`), allowing each metadata operation to receive its own five-second bound instead of applying admission's clock to a long evidence read. Explicit caller deadlines still refuse, preserve unresolved borrow and avoid false reference creation. Underlying `borrow` already has the right separate acquire/release operations, which is the healthy primitive the wrapper previously defeated. The other inspected `resource_store.clock` calls in resource registration, lookup/status and composer registration scope short metadata transactions; I did not establish another wrapper spanning an arbitrary user-body lifetime with an invented clock. This is a scoped search result, not whole-tooling certification. Sibling owns the broader tooling analysis.

The cubic `real_interval_route_matches_known_roots_including_near_critical_endpoints` test now uses explicit factorizations, independent root counts and analytic sqrt for a quadratic (`crates/pse-math/src/implicit_cubic.rs`). Production `CubicWorker::solve` still verifies candidate roots against original guards, branch interval and residual. That repair strengthens oracle independence without changing tolerances or acceptance semantics. Searched analogues in math tests and runtime modeling/reuse/recycle/forms/global tests include legitimate cross-route comparisons accompanied by independently known values or original residual checks. No further material self-oracle defect is established by this inquiry; merely using a common runtime is not a finding.

The durable-publication-close test preserves deliberate semantics: a durable runtime refuses before new native dispatch; explicit local receiver construction is visibly ephemeral; new run IDs and original residual checks remain. Keep that separation. Do not repair product friction by silently falling back from durable storage failure to ephemeral execution. Python `ScientificReplay.rerun` currently selects its original runtime, and source receiver reconstruction is not exposed there; this is an observed public-surface limitation, not an independently established requirement for this review to add that API. Runtime close, publication close and physical disconnect are separate; the new test covers logical publication close, not actual physical server loss/restart.
