# Supporting target audit: state, reuse and boundaries

Supporting inquiry for [the principal audit](../../reviews/design_review_efficiency-and-solver-target-audit_2026-10-12.md); the principal owns the integrated verdict and evidence limits.


Independent bounded advice for `design_review_efficiency-and-solver-target_2026-10-12.md`, findings F01–F06/F14 and RC01–RC05/RC08/RC09/RC11. Examined 2026-10-12 at `6c368c88acda548d421b44e8fc4f457c95bcec7e`; the review/evidence directory was untracked and its README edit was present. No repository files changed. This document does not replace the principal review or own dispositions.

Criteria are Core 3.4, Heuristics 1.0 and ProcessSimulator 1.5, with the binding's functional target: edit/re-solve without rebuilding unchanged structure, studies/fitting/sensitivity/optimization, recycles, dynamics from the same definitions, extension, and local compile/test dependencies. ADRs, plans, mechanisms and pins describe the subject and potential rule impacts. They do not decide architectural merit.

## Judgment

The strongest recommendation survives: make admitted immutable model products usable locally, preserve their owners and validity, and move bulk results and analytics onto operation-appropriate representations. That reduces unnecessary coupling for either a single-owner project or independent project writers. Source establishes store coupling and repeated conversion mechanisms; no latency, memory saving or assembled benefit was measured.

The particular combination “one writer per durable log + embedded catalog or manifest log + server only if premise 1” is a **conditional Proposed design**, not the demonstrated unique remedy. The review overstates what follows from immutability, overstates the absence of block consumption, and understates existing compiled validation. Its blanket prerequisite chain is too restrictive. Public visibility, reader lifetime, durable acknowledgement and executable reuse remain material design decisions.

## Per-finding positions

### F01 — retain diagnosis; narrow claims; separate three decisions

**Source facts.** `crates/pse-py/src/workflow.rs::NativeRuntime::new` connects and opens `CanonicalStore` before selecting `Ephemeral`; `crates/pse-runtime/src/workflow/modeling/canonical.rs::ModelingPackage::declaration` admits canonical activity, protects the revision, reads/decodes one declaration, and releases it. `qualified_selected_candidate` consults retained admissions under fresh selection checks. `crates/pse-runtime/src/workflow/run.rs::launch` opens `Staged::open_queued`; durable branches register attempts. These establish externally coupled preparation even for local execution. I did not independently recount the claimed six round trips or all eight validation sites.

`canonical/delta.rs::delta_parent` reads parent membership/declaration/document metadata; `apply_delta_parent` re-resolves all outgoing declaration references. However, it deliberately leaves unrelated inherited data tables unopened and hydrates only changed semantic data suppliers. Replace “complete parent package hydrated” with “complete declaration/metadata population hydrated and references re-resolved; data payload hydration remains selective.” This retains the locality concern without erasing an existing strength.

**Proposed correction.** Distinguish (a) local working authority and immutable preparation, (b) edit/attempt durability, and (c) cross-session publication visibility. None inherently requires the others to change simultaneously. Normal interactive solves can retain automatic durable visibility through a journal and publication sink while computing entirely from a local snapshot. Explicit publication is an option with an API behavior change, not a prerequisite for eliminating canonical reads before each solve.

The review's “journal eagerly, off the solve path, loses no authored input after an API edit” needs an acknowledgement contract. If an edit succeeds before a same-process background append is durable, an immediate native crash can lose it. A successful edit must either await the required committed append, receive an acknowledgement from an independently surviving writer, or explicitly advertise weaker durability. This puts persistence at edit acknowledgement rather than rebuilding structure at solve time. Purely disposable operation should remain a separately stated choice; “journal always” is itself a product policy.

**Capability preservation.** `python/pse/_workflow.py` consumes retained results, promotion, analysis and retirement—not merely publication. Preserve exact revision, start content and typed partial/failed outcomes. “Only published or journaled” is insufficient until the reader knows which journals are discoverable, what terminal ordering selects “latest”, and whether a journal survives owner restart. Do not infer that those APIs may be removed or narrowed because coordination is unnecessary for one computation.

### F02 — retain classification opportunity; reject automatic elimination of lifecycle obligations

**Source facts.** `crates/pse-operations/src/canonical_results.rs::{ReadOwner, CompletionRead, ResultReadDrain, ResultReleaseTask}` implements renewable read ownership, asynchronous release recovery and close/drain behavior. These are concrete reader/close obligations. Generated `crates/pse-operations/src/generated/surreal.surql` is current physical design, not evidence that table/function counts themselves violate AP-01. Historical failure counts cannot establish that the proposed replacement closes the failures.

Immutable occurrence facts and content-deduplicated payloads are a sound direction under AP-05/H25. But append-only facts still require atomic publication, retry settlement, ordering, retire/delete decisions, reader protection and cross-occurrence payload retention. One writer removes peer-write races while it holds exclusive authority; it does not remove crashes during append/acknowledgement, uncertain worker delivery, reader/GC races, or ownership transfer. Minted identities alone do not replace receipts when the caller must learn whether a particular effect happened.

SurrealDB-native constraints are credible partial replacements, not a complete invariant owner. The exact 3.3 corpus documentation `.../neo4j-surrealdb/surrealdb/content/corpus/docs/reference/query-language/language-primitives/record-references.mdx` restricts reference tracking to suitable top-level record/array fields. It cannot protect files or leases. Current [transaction documentation](https://github.com/surrealdb/docs.surrealdb.com/blob/main/src/content/learn/querying/concepts-and-guides/transactions.mdx) describes snapshot isolation and locked reads; a unique index or sequence does not make a read-dependent multi-record decision serializable. Keep the claim fence check inside the committing transition; preserve ordering and retry interpretation. A sequence is an issued token, not proof that its claimant remains current.

Lifecycle declarations can have a smaller route without becoming a second authority for scientific meaning. Judge which operations and consumers need those records, rather than treating every lifecycle declaration through a scientific registry as intrinsically wrong.

### F03 — keep as an independent topology opportunity; conditional recommendation

The actual pin enables only `protocol-ws`/`rustls` for the vendored SurrealDB SDK (`Cargo.toml`). Embedded SurrealDB would be a different build/lifetime composition, carrying engine dependencies into the local binary. The review correctly distinguishes crash-isolation processes from independent writers. A runner with child workers can serve durable studies and process-exclusive solvers without peer database clients.

There are two unresolved premises, not one: independent same-host writers and writers/worker jobs that must survive the runner or operate on other hosts. The first does **not** by itself imply a database server. A library-serialized local catalog can admit several independent client processes. Conversely, “one writer per study log” still permits several study owners to publish to the same project catalog or move the same head. The target must name who arbitrates that shared catalog and how log ownership transfers after a crash.

For runner-owned workers, keep owner incarnation/attempt attribution in messages and completion facts, define late completion rejection after resume, and drain or terminate old workers before ownership transfer. Pipes remove WebSocket request machinery; they do not make delivery acknowledgement and process death equivalent. These are bounded contracts, not a request to reconstruct the existing transport system.

**Alternatives that need comparison:** see the table below. The current record supports a store-free interactive path under every alternative. It does not support automatically removing independent writers or equating that capability with a supervised remote server.

### F04 — retain bulk/analytics direction; distinguish conversion, transport and publication

`crates/pse-runtime/src/workflow/results.rs::{table, into_table_cursor, cursor_by_id_range_controlled}` creates projection cursors and calls relation encoders. Thus repeated presentation can reconstruct Arrow relations. However, `crates/pse-py/src/inspection/stream.rs` already exports Arrow through `pyo3_arrow`; `FieldCheckedBatch::checked_export` in `crates/pse-relations/src/columnar.rs` shares buffers and retains backing owners. The missing optimization is often retaining/reusing checked result batches, not inventing a zero-copy Python transport.

These paths are distinct: live scientific-result-to-Arrow conversion, stored IPC decode, and Python C-stream export. F04 should state which is eliminated and retain bounded projection/range behavior. Retaining every advertised relation eagerly can undo the current demand-shaped cursor benefit. A demand-populated checked-batch memo or bounded chunk spool can compose with the existing C-stream boundary.

Arrow/Parquet files plus a small transactional manifest catalog fit analytics and growing trajectories. A committed manifest must enumerate an exact immutable snapshot; listing a directory is not equivalent because it can include staged/unpublished files or mix commit generations. Arrow and Parquet are formats, not the durability protocol. A complete Parquet file requires its closing metadata; write independently sealed chunks or explicitly recoverable IPC journal segments rather than promising every partial row group survives a crash. Record committed prefix, gaps, terminal state and interpretation before a reader treats it as a complete horizon.

Move integrity checks to the actual trusted boundary and cover schema/metadata as well as payload. A scientific content identity and storage-integrity identity may have different scopes; avoid casually dropping the latter because the former exists.

### F05 — retain local dependency-graph authority; revise cache and lineage model

**Existing foundations.** `crates/pse-compiler/src/workspace/modeling/granular.rs` already has declaration/field/occurrence Salsa inputs and tracked parsed/typed/complete queries. `CompilerWorkspace::trim_queries` uses LRU and may rebuild the database when retained metadata exceeds limits. `workspace.rs::PreparedCase` deliberately exports owned products without Salsa handles. `crates/pse-runtime/src/math/modeling.rs::{compiler_lane, with_modeling_compiler, modeling_revision_at}` already retains lanes by complete lineage/context and detaches requests that must not rewind the current head. Therefore “coexisting lineages” is an extension and simplification opportunity, not an entirely missing behavior.

`math/retention.rs::{Key, Product, Pressure}` supplies a shared pressure owner across weighted modeling retention and compiled artifacts; immutable products keep allocation leases independently. `math/preparation.rs::BasisKey` includes complete dependencies/bindings/demand/limits and exact equality. Those stores are not automatically rival **semantic** authorities: memo retention, in-flight coalescing, native build effects and durable trust are different responsibilities. `selected_flights` is coalescing/lifetime control, not another semantic derivation. Consolidate overlapping invalidation and retention work where source shows duplication; preserve distinct contracts when they remain necessary.

**Salsa contract correction.** The exact 0.28.4 corpus `.../salsa/content/corpus/source/storage.rs::Storage::cancel_others` cancels and waits for other cloned handles before mutation. Clones share storage; they are not independent historical snapshots. Current [Salsa runtime documentation](https://github.com/salsa-rs/salsa/blob/master/book/src/plumbing/database_and_runtime.md) agrees. One independently allocated database per mutable lineage is viable; immutable revision-keyed inputs in a shared database are another viable option. Neither makes every prior revision free to retain. A study should freeze owned products, release database handles before mutation, and carry explicit allocation owners.

Raw Salsa identities are database/generation-local and cannot be the content key for sharing products across independent databases, processes, restarts or the disk memo. Interned values may be reclaimed/reused under the 0.28.4 contract. Use durable semantic/content identities outside the database; scope any in-process id-indexed retention by database ownership and generation. Content-addressed retention underneath Salsa can coexist with a single dependency authority without contradiction.

“Byte-bounded retention keyed by Salsa identities” is not supplied by Salsa LRU. LRU bounds query values; input/key/dependency metadata and foreign heaps remain separate. Existing generation rebuild and allocation leases answer real parts of this problem. Bound live lineages and pinned studies separately from evictable memo values; eviction cannot reclaim a product still borrowed by a solve, Python stream or study. Complete key coverage includes physical/provider context, guarded programs, derivative/output demand and backend/runtime configuration. An expression edit with unchanged incidence can backdate pattern products while invalidating form/program products; value rebinding still requires current-state checks.

The disk memo is optional. Where cold starts/worker compilation actually dominate, compare content-addressed serialized pure products against rebuilding from source, including key construction, load validation, version migration and retained bytes. `Cargo.toml` has no Salsa persistence feature enabled. Native executable compilation is explicitly an effect outside compiler queries (`workspace.rs` module contract); do not place impure native setup inside tracked queries merely to call reuse single-authority.

### F06 — narrow diagnosis; preserve the existing structural/operational distinction

The blanket statement that structure does not reach scheduling or per-block execution is false at this baseline. `pse-compiler/src/workspace.rs::prepare_bound_initialization` derives plans from structural analysis. `pse-structural/src/initialization.rs::Plan::with_execution_dependencies` merges numerical blocks using execution/validity dependencies and topologically orders them. `pse-runtime/src/math/solves/blocks.rs::{automatic_block_count, prepare_blocks}` consumes compiler alternatives; `math/initialization.rs` executes predecessor blocks under a shared admitted backend. The real gaps are finer per-block method decisions, parallel ready-level execution and reuse across additional consumers.

A shared, incrementally derived structure product is a strong Proposed improvement. Preserve separate numerical incidence, execution/validity edges and optimization coupling. `pse-structural/src/incidence.rs::{StructuralAnalysis, BlockId, CaseIncidence}` already distinguishes these and refuses crossing objective support. Pattern identity must include selected rows/free variables, equality classification and the relevant operator kind; dynamics/DAE, Jacobian and KKT patterns are not interchangeable merely because they arise from the same authored definitions. Control/value-only derivatives can change executable dependencies without changing numerical sparsity. Weak-component reuse must account for component merge/split and objective/inequality coupling before independent execution is claimed.

Keep form facts dependent on body programs and contextual assumptions. Affinity or solvability may also depend on fixed/free interpretation, domains and parameter assumptions; an incidence-preserving expression edit invalidates those facts. Structural nonsingularity does not establish numerical rank or validity at a new point. A coefficient becoming zero changes numeric evidence even when the conservative structural graph is unchanged. Pattern facts may remain exact **structural** facts while being only advisory for numerical method suitability.

An ordering can be shared where the consumed library accepts that ordering and index space; a library's own BTF/analysis is not necessarily a redundant project implementation. I did not re-audit every KLU/MUMPS/FERAL integration claim. Preserve the review's restriction that generic factorizations remain library-owned. Produce colourings/critical paths only for identified consumers; they are opportunities, not demonstrated defects simply because absent.

### F14 — retain crossing opportunity; correct existing implementation; tighten trust semantics

`pse-relations/src/validate/planner.rs::LocalPlanner::prepare` already coerces/simplifies and calls `datafusion_physical_expr::create_physical_expr` without a session. `validate/prepared.rs::{ValidationContext::local, prepare, relation, construct, PreparedLocalContract}` already caches compiled physical contracts under immutable registry/native owners; evaluation does not plan. `columnar.rs::FieldCheckedBatch` already carries established structural/validation ownership, and `checked_export` shares that owner rather than revalidating every buffer. Therefore the remedy “compile validation once to PhysicalExpr / carry typed validated wrappers” is partly implemented. Focus F14 on actual rebuilding/re-evaluation at specific conversions and on SQL binding/context dependencies still imposed by `pse-engine::NativeValidation`.

SQL row checks (`pse-schema/src/catalog/row_checks.rs`) deliberately bind against actual functions/configuration. `LocalPlanner::create_logical_expr` refuses SQL. Replacing that path requires a complete binding/coercion/NULL/volatility/function/configuration contract, not merely a call to PhysicalExpr. DataFusion 55.1's [physical-expression interface](https://docs.rs/datafusion-physical-expr/55.1.0/datafusion_physical_expr/fn.create_physical_expr.html) supports direct lowering; it does not itself parse or validate arbitrary SQL. Keeping one immutable expression-binding context need not imply one full query session per validation.

The target's skip rule—matching validation-contract version plus matching digest—is insufficient **by itself** for foreign bytes. A digest establishes correspondence to hashed bytes, not that a recognized trusted producer established semantics for those exact bytes/schema/context. Preserve trusted provenance or reader-established validation evidence, decoder/format validity, and interpretation/configuration premises. Untrusted or merely version-compatible writers still need admission. Keep independent checks of each new numerical state under PS-10; they are not redundant validation of immutable definitions.

`pse-py/src/workflow.rs::local_python_configuration` refuses the abi3 local replay proof because no process-wide environment owner exists. This substantiates an unsuitable replay mechanism for that path, not permission to replace executable equivalence with a content hash. Cross-process **pure data** memo loading and executable/native generation use have different trust/lifetime obligations.

## Complete alternatives and preserved boundaries

| Candidate | Functional strengths and composition | Retained obligations and tradeoffs | Selection condition |
|---|---|---|---|
| Local admitted snapshots + existing remote store for publication/coordination | Removes critical-path canonical reads, retains independent writers, existing durable APIs and native crash isolation | Keeps server/transport for consumers that use them; simplify native transitions separately | Strong incremental option while concurrency remains unresolved; no need to await server replacement |
| Local snapshots + one runner-owned journal/catalog with child processes | Simple local edit/solve; restartable study and crash-isolated workers; no external server | Durable acknowledgement, exclusive writer succession, worker late messages, catalog/head arbitration, readers/GC and backup remain | When runner ownership and its failure semantics satisfy actual product consumers |
| Local snapshots + SQLite WAL transactional catalog + immutable files | Independent same-host application processes can publish without an application server; transaction/uniqueness/backup mechanics library-owned | One writer at a time, busy/retry handling, checkpoint behavior, external-file publication/GC and schema migration remain; different library integration | Credible missing comparator when independent writers are local; no benchmark or selected exact-version fit established |
| Local snapshots + per-writer immutable journals/manifests + shared commit arbitration | Crash-local append and reproducible snapshots; bulk analytics stays file-native | Discovery, global heads/latest order, retire/reference closure, partial commit recovery and GC can become a bespoke database | Viable if global mutable queries/ordering are truly small or absent; compare complete lifecycle, not file format brevity |
| SurrealDB-native shared coordination + immutable bulk files | Keeps richer shared mutation while reusing record constraints/transactions | External-file atomicity, leases/readers, locked read-dependent transitions, retries and remote uncertainty remain | When shared coordination has concrete consumers or remote workers need independent survival |

SQLite is a Proposed comparator, not a replacement decision. The primary [WAL contract](https://sqlite.org/wal.html) allows independent same-host processes, concurrent readers and a serialized writer; it excludes network filesystems and long reads can hold back checkpoints. The [backup API](https://sqlite.org/backup.html) supplies a database copy mechanism, not a snapshot of external files. Context7 discovery was followed by these primary docs; no SQLite version or Rust binding was selected/qualified.

All file-backed alternatives need four explicit boundaries:

1. **Publication/recovery:** persist the referenced immutable objects before the catalog exposes them, then acknowledge the commit; distinguish a crash before commit from a lost acknowledgement after commit. Retries retain occurrence identity and compare immutable intent. Content deduplication cannot resurrect retired occurrences.
2. **Reader/GC:** a grace period cannot promise completion for arbitrarily paused/unbounded readers. The review explicitly proposes weaker mid-read retirement; that is a capability change requiring RC04 expansion. Compare strong alternatives—snapshot pins, open-file ownership on supported Linux paths, or read/GC exclusion—before selecting that weakening. External files are outside database REFERENCE protection.
3. **Backup/restore:** pause GC **before** taking the catalog snapshot and retain its referenced closure until copying completes. Include input journals, attempts, starts, interpretation manifests and restart cursors needed by promised APIs. A database snapshot plus files does not automatically cover unpublished journals; a per-study log also needs a consistent captured boundary. `docs/dev/surreal-substrate.md` currently consumes restore isolation, credential/incarnation changes and semantic validation; preserve the outcomes with a simpler mechanism where appropriate.
4. **Public visibility/retention:** define local, journaled, published and retired selectors, terminal ordering, unavailable/missing distinctions, and historical promotion/analysis ownership. A manifest can preserve a failed/partial result without pretending it is usable. Seed/artifact context must survive retirement of the producing run where the API promises independence.

## Priorities, prerequisites and further opportunities

**Highest priority in this scope:** establish local admitted snapshot consumption and preserve current immutable owners; correct F06/F14 overstatements; settle edit acknowledgement and reader/API preservation before committing to a replacement topology. This enables targeted, store-free modeling/preparation tests independently of a catalog rewrite (AP-06).

**Prerequisites are per consumer.** A complete local dependency graph is prerequisite to eliminating store eligibility rechecks. It does not require a new bulk format, independent-writer removal or all lifecycle simplification first. Result batch retention, compiled-validation reuse, and structure products can improve independently. Pure native allocation reuse can be lane-owned with current durable publication if compatibility and drain are sound; it need not wait for RC05. Cross-process memo reuse alone requires its trust contract. Parallel block execution requires complete numerical plus execution/validity dependencies and independent outcome assessment. Distinguish this dependency order from consequence-based priority.

**Additional concrete opportunities:**

- Separate structure/preparation identity from current attribution and demanded output/derivative projection where source shows those dimensions unnecessarily sharing a key (`math/preparation.rs::BasisKey`). Preserve demand-dependent compilation where it is real; do not make every solve compile every derivative or relation to gain reuse.
- Admit distinct structures lazily during structural/discrete studies rather than necessarily preparing every possibility at study admission. Freeze each consumed prepared bundle; preserve provider/physical context and owner lifetimes. A large discrete space need not become an upfront structural census.
- Use existing checked-batch/Arrow C-stream ownership for result retention. Preserve lazy range projection and cancellation instead of eagerly retaining all output families. This gives a local F04 improvement without changing durable representation.
- Define a compiler-facing consumed contract for model preparation, leaving remote storage and session placement at the composition root. Inspect actual Cargo/dev-dependency closure before claiming a responsibility can compile/test locally; deleting runtime calls alone does not remove unrelated native build dependencies.

These are Proposed opportunities supported by source structure, not measured improvements or implementation instructions.
