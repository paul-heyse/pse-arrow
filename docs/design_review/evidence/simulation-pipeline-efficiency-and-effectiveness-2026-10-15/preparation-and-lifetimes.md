# Preparation and resource lifetime inquiry

Supporting inquiry for `docs/design_review/reviews/design_review_simulation-pipeline-efficiency-and-effectiveness_2026-10-15.md`; this is not an overall simulator verdict or a second disposition ledger. Original audit status stays with 39d; new recommendations await adoption through a future authorized plan-creation step. Baseline: HEAD `a08f5fa091db1840fc95b46c4d4f849ce4c5de62` plus the live, extensively dirty tree examined on 2026-10-15. No repository edits, builds, tests, probes or services were run. Source searches and reads, retained audit artifact reads and Context7 documentation lookups only. The investigator authored scratch only; the coordinator published this supporting document.

## Scoped judgment

Core 3.4, process-simulator 1.5 and the efficient-architecture companion support retaining the existing semantic separation: authored source and physical context -> checked package -> finite specialization -> immutable grouped body/frontier -> prepared basis -> per-case numerical work. Neither replacing the numerical solver nor adding another cache framework addresses the observed cold preparation. The existing design already has useful exact dependency identities, Salsa phase queries, reusable mathematical bodies, detached historical products and completion-owned flights. The material problems are avoidable work inside those boundaries and cancellation/serialization boundaries that do not match their consumers' lifetimes.

AP-07/G9 is violated in the inspected preparation paths by repeated root scans and stable environment reconstruction; the original audit independently supplies a decision-relevant interrupted cold case. AP-05 and AP-07 are violated by the disconnected child cancellation boundary. AP-01/AP-04 are supported locally by separate lexical, scientific, physical and effect authorities; these strengths constrain repairs. AP-06 is supported by existing pure checker/specializer/compiler tests, but the production preparation cancellation composition needs direct local tests. This does not establish all applicable foundations or scientific gates for the whole pipeline. PS-G1/2/3 adequacy of numerical outputs was not assessed here; no numerical cold-case output exists to certify. All replacement benefits are Proposed and unmeasured.

The audit's `cases/cold-large-1/diagnostics/audit-outcome.json` records interrupted status, explicit stop, one successful fixture cleanup, zero workflow native joins and zero managed receiver drains. `capture-cpu.json` and `capture-timeline.json` explicitly report Partial/source_partial, and CPU sampling loss is unknown. The plan records about 36.47 s source admission, 480.52 s preparation and 518.73 s total interrupted wall time. Those facts and the inspected decoded symbols establish preparation activity, not exclusive CPU attribution, an estimated speedup, or a native numerical solver diagnosis. The two captures are bounded windows, not whole-operation profiles.

## Findings and corrective contracts

### P-F1: indexed roots are maintained but not used for import lookup (AUD39-01)

**Implemented diagnosis.** `pse-runtime::workflow::modeling::canonical::SourceIndex::insert` populates `named_roots: BTreeMap<String, Vec<DeclarationId>>`. Its `LexicalLookup::imported` implementation performs required namespace/import and root-name completeness checks, then, for every matching import, scans `rows.values()` to select top-level rows of that name. The canonical `selected_source::resolve_segments` uses this operation for the shared lexical rule: bound formals stop lookup, explicit imports precede ordinary members, and Pending prevents looking through a nearer uninspected scope. This resolver is used by local selected-source acquisition, ingress/delta data closure and replay validation; it is not a solver-specific issue.

**Consequence.** Import-heavy source acquisition repeatedly examines unrelated selected declarations even though the exact root access path is present. Source-traced avoidable work meets AP-07/H5/H9; the recorded sample frames support relevance but do not quantify exclusive cost.

**Proposed correction.** After the same completeness checks, consume the existing root bucket. Keep every candidate and existing import precedence. Bucket insertion follows acquisition order while the old row scan follows DeclarationId order: establish/sustain sorted bucket order, or sort each looked-up bucket, rather than blindly replacing the scan with insertion-order iteration. Preserve import-group order and any multiplicity; a global sort/dedup would be an additional semantic change for atomic lookups. `resolve_segments` only deduplicates/sorts when traversing later path segments.

**Adversarial case.** Two same-named guarded/imported roots arrive in opposite acquisition orders; one nearer import membership is still unread. Fast lookup must return the same ordered candidates only after the original completeness premise, and must not select an outer declaration while the nearer lookup is Pending.

**Scope of adjacent opportunity.** `SourceIndex::member_candidates` recursively expands guards and bases and tracks `probing` to break recursion. Repeated inherited/guarded expansion is source-visible, but this inquiry does not establish its total cost or justify a global member-result cache. Pending, recursion-context temporary absence and an incrementally growing index make owner/name-only memoization unsafe. A finalized-index cache or invalidation against all consumed rows/memberships could be sound; first preserve Pending versus proved absence. Do not merge this unmeasured investigation with the already established root-scan diagnosis.

**Verification candidates.** Direct index tests with mixed insertion order, duplicate/guarded candidates, absent root, missing import membership, nearer shadow and pending-to-found transition; compare complete answers to the existing resolver. Use existing source-selection/namespace controls and retain genuine acquisition integration coverage. An examined-candidate control can demonstrate removal of unrelated scans without claiming latency improvement.

### P-F2: immutable lexical context is repeatedly reconstructed inside specialization (AUD39-02)

**Implemented diagnosis.** `CheckedPackage::named_types_with` already narrows enumeration by package/import prefixes and `names_below`; it is inaccurate to call it a fresh global inventory scan. It nevertheless enumerates visible names, resolves each through current lexical authority and clones a broad type map for each call. `Evaluator::typed_result` calls `Evaluator::named_types` for arithmetic results, then applies actual value and expression refinements. `StaticValue::Apply` inside `Evaluator::syntax` computes `preset_definition` and `package.named_types(*id)` separately for every constructor argument. `Engine::source_types` starts from `p.named_types(at)`, walks scope/type parameters and function arguments, then overlays the current Environment and evolving `function_types`. These are concrete repeated constructions over an unchanged borrowed package during one specialization. They affect all consumers of finite specialization, including steady state, declared studies, dynamics and fitting.

**Proposed correction.** Let the specialization/evaluation context retain the stable lexical base for the lifetime of its borrowed immutable CheckedPackage, qualified by lexical owner. Apply reader admission extents, actual function arguments, scope parameter/type-variable resolution, current values, missing/present refinements and evolving synthetic-function types as explicit separate overlays. Constructor target/base lookup can be hoisted once before the argument loop; actual argument evaluation and type checking remain per argument. A borrowed lookup view can avoid cloning the entire base when infer/resolve APIs can consume it; a first implementation may memoize the stable base locally, but repeated cloning should remain an explicit residual rather than being called full closure.

**What cannot be cached that way.** Admission evolves the type population. `ResolutionEnvironment::resolve` explicitly consumes persistent preceding `Types` through a lookup closure; `named_types_with` must read that population. Existing `named_types_prefix_enumeration_reads_current_types_without_a_retained_cache` mutates a checked package's types and requires fresh answers. The lexical base lifetime therefore cannot be a permanent owner-only cache on mutable CheckedPackage. `named_types_prefix_enumeration_preserves_lowered_function_resolution_boundary` requires synthetic functions to resolve through `lowered_functions` without adding global qualified names or a parallel type environment. Current visibility, prefix collisions, inherited members and local physical-name shadowing also remain unchanged.

**Adversarial case.** Two replicas share lexical owner but carry different finite arguments or a present/absent optional member; a synthetic function is added between inference requests. Reusing a complete previously overlaid map would return stale types or erase a guard. Reuse only the immutable base; the occurrence owns those changes.

**Local testability.** Checker/specializer tests need source rows, TypeContext/quantity registry, explicit documents where consumed and cancellation callback; they do not intrinsically require a canonical store or a numerical solve. Existing `check/named_types_tests.rs`, `workspace/modeling/granular_tests.rs` and specialization controls are the appropriate correctness owners. Pure controls should stay pure; actual source-provenance/acquisition tests remain integration tests.

**Verification candidates.** Preserve exhaustive-reference comparison and mutation/prefix/import/shadow/lowered-function controls; add repeated-owner/different-overlay cases, admission versus production reader, optional-presence arithmetic and constructor multiargument cases. Check actual environment construction/reuse counts or allocation scope before timing larger cold preparation. No tests were run in this inquiry.

### P-F3: specialization's function override is represented by cloning a complete CheckedPackage (adjacent to AUD39-02)

**Implemented diagnosis.** `SpecializedModel::function_contracts` clones `package`, then inserts finite scalar functions into `package.functions` and `package.lowered_functions`. CheckedPackage's owned BTreeMaps include declarations, names, children, types, members, entities, constants and provenance, so this is materially broader than a function overlay. Calls occur in rewrite, contextual operations, continuous/regime/process/objective specialization, annotations and function admission. Some sites also rebuild maps of every specialized symbol type. Captured clone/drop frames alone do not quantify these sites, but the construction scope is explicit in source.

**Proposed correction.** Make expression admission consume the unchanged package plus the current function overlay, preserving one lookup/visibility authority. A shallow immutable package base with separately owned function updates or a narrow function-contract lookup view are viable. A second synthetic name registry is not. Do not snapshot the overlay before specialization finishes adding functions, and preserve reconstruction-specific body result transformation in `Engine::admit_function_occurrences`, which deliberately alters called function result contracts only in the reconstruction's body.

**Relationship.** P-F2 and P-F3 share repeated materialization of stable source context, but have different change premises: lexical type base versus evolving function contracts and reconstruction-local overrides. They should share a coherent admission-view design, while closure evidence addresses both obligations. Renaming full clones into a helper or caching one stale augmented package is not closure.

**Verification candidates.** Exact agreement with current function inference/guards/physical admissions, finite generated function lookup, generation-after-first-use, reconstruction-local override isolation, and provenance/selection side effects. Demonstrate the complete package copy disappeared, then measure representative preparation if claiming speed or memory gains.

### P-F4: grouped normalization rebuilds a full runtime index per consumer (adjacent preparation opportunity)

**Implemented diagnosis.** `workspace::modeling::executable::grouped::plan` calls `normalize` for every expression/output. `normalize` reconstructs `runtime` by zipping all projection formals and inputs into a BTreeMap. It already trims transitive local members, validity expressions and inputs to the demanded consumer. The existing transitive-demand algorithm is a strength, not the defect.

**Proposed correction.** Construct the projection-level runtime/formal lookup once per immutable grouped plan and borrow it for each consumer. Keep per-expression Let locals separate because they are not demonstrated identical. Keep fresh `Rename` names, dependency-order member/input numbering, cycle detection, quantity hints, normalized validity and checked-member attribution per consumer. Sharing one global Rename would change body identity and falsely merge provenance.

**Verification candidates.** Existing `projected_outputs_bind_only_the_members_they_read`, projection-size/replica tests and grouped validity tests; add distinct consumer local orders, overlapping-but-different dependency closures, validity-only dependencies and different global instance identities producing equal normalized bodies. Show one projection index construction rather than one per output. Benefits remain unmeasured.

### P-F5: selected function requests prepare the full value CasePlan first

**Implemented diagnosis.** `CompilerWorkspace::prepare_modeling_functions` calls `model.admitted.plan(... Value ...)`, then `CasePlan::functions(selected rows, coordinates, requested order)`. The latter filters instances/contributions and rows and prepares a new plan with requested coordinates. The shared route serves fitting per experiment and original checks (`workflow/fitting/modeling.rs`), dynamic model function preparation, conditional strategies, cases and structural partition analysis. Source establishes avoidable whole-plan preparation before exact selected intent, not its elapsed contribution.

**Proposed correction.** Add direct selected-row/coordinate construction from the admitted case/body inventory under the same owned assembly contract. Alternatively retain and reuse an already needed full value plan when a real broader consumer justifies it; caching a full plan only to avoid choosing demand is less selective. Preserve requested coordinate ordering, current row ordering and duplicate/unknown refusal, accumulation of every selected row contribution, bounds, native-form metadata, domain guards, provider demand and original-space checks. A selected row is not permission to narrow an opaque coupled provider's evaluation without its owner establishing the contract.

**Adjacent cache path.** `workflow::modeling::views::observation_program` builds `product.observation_structure(rows)` to derive a program key, and on miss the compiler's `prepare_modeling_observations` reconstructs it. Carry the already selected immutable structure, or derive a key from complete admitted identity plus actual row request/order/profile/physical context. Do not key only by row IDs or silently change the supplied variable view. This is the same demand-loss/materialization family, but each path has distinct ordering and dependency obligations.

**Verification candidates.** Selected versus existing plan equivalence for row sums, requested coordinate permutation, guards in selected and unrelated rows, all supported derivative orders and original-check behavior. Preparation count should follow selected required work. Actual callers across fitting, dynamics and conditional execution must be exercised after owner-level equivalence; no per-mode algorithm copy.

### P-F6: child scope disconnects parent cancellation (AUD39-03)

**Implemented diagnosis.** `CancelSource::child_with_deadline` uses the minimum enclosing/provided clock via `with_deadline`, then replaces its token with `CancellationToken::new()`. It is independently cancellable but is not a hierarchical child. `checked_selection_scoped` and `ModelingPackage::engage` create it and pass it through source/preparation without a parent bridge. `scoped` selects only its supplied child's cancellation/deadline. Original caller cancellation therefore does not reach these loops/flights. This is a lifecycle defect independently of preparation speed.

**All production callers found by repository-wide `rg child_with_deadline`.** (1) `checked_selection_scoped`; (2) `engage`; (3) `workflow::staged::bounded`; (4) `ModelingPackage::admit_study_candidate`; (5) ephemeral `ModelingPackage::study_inner` in `study_execution.rs`. The other occurrences in engagement/study_execution are test code. `bounded` and candidate admission manually bridge parent cancellation and await work; the first two do not. SourceIndex/local-premise loops checkpoint cancellation/deadlines, and Engine checkpoints finite specialization, so propagation should reach existing cooperative controls rather than requiring a new cancellation system.

**Proposed correction.** Use the existing `pse_columnar::CancellationToken::child_token` capability, retaining minimum original deadline and upward/sibling isolation. It delegates to pinned tokio-util 0.7.19. Context7 documentation for Tokio Util confirms parent->child propagation, child->parent isolation and initially-cancelled child behavior; local wrapper source corroborates the access path. Do not replace child scopes with token clones, which would let one child's cancellation cancel parent/siblings.

**Essential compatibility repair.** `study_inner` uses `if parent_cancelled && !work_cancel.is_cancelled` at loop top and the pending wait select to both signal the child AND `frontier.extend(0..facts.len())`. With a real child token, the parent cancels `work_cancel` immediately, making those guards false and skipping policy-frontier refresh. Track parent handling independently of child token state, execute bookkeeping once, then drain every issued future. Candidate admission's guarded parent bridge has no comparable frontier side effect; bounded still needs its interruption classification and await path. Existing correctness tests need to cover cause ordering when parent and deadline coincide.

**Shared-flight preservation.** Never attach shared producer control directly to one caller's child. `Flights::load_owned` owns a separate FlightCancellation, reference-counts waiters, signals only when the last waiter leaves, and retains the entry until producer completion. A cancelled waiter can depart while a second survives. Direct private jobs use cancellation+await. Preserve that distinction and actual native join/foreign destruction before releasing capacity. A drop guard can signal cancellation; it cannot prove drain.

**Verification candidates.** Ordinary public/declared execution cancelled during checked selection and during finite specialization, already-cancelled parent, one child cancelled with parent/sibling surviving, minimum deadline, two waiters with one caller cancelled, last waiter leaving while producer gated and capacity retained, and ephemeral study with blocked/waiting points whose frontier needs reevaluation. Keep source cancellation separate from managed receiver cancellation evidence.

### P-F7: a shared producer inherits the first waiter's deadline (new concurrency finding)

**Implemented diagnosis; runtime consequence source-inferred.** `BasisKey` correctly excludes attempt cancellation/deadline. `plan_frontier_keyed` and `complete_frontier_keyed` share flights under this mathematical key, but the creating closure captures the first waiter's deadline and passes `Some(deadline)` to the controlled job. `jobs::admitted` treats that deadline as producer expiry, cancels control and joins. A second same-key caller with a later still-valid deadline receives the shared load failure even if it remained interested. Caller cancellation isolation in Flights does not isolate this deadline. The outer `scoped` already enforces each waiter's original clock, so this is a separate ownership concern from P-F6.

**Proposed correction alternatives.** A service-owned production policy/clock, with each waiter retaining its own immutable deadline and last-waiter retirement, preserves broad sharing. A compatible execution-clock identity in the flight scheduling key, separate from the pure artifact key, preserves original producer clocks but reduces coalescing. A typed producer-expiry retry can preserve later waiters, but must join the retiring producer before retrying, consume the same caller deadline, and avoid hidden retry multiplication. Choose explicitly; silently renewing a first caller's original operation clock is not acceptable. Adding deadline to the scientific/content key is the wrong authority.

**Adversarial verification.** Start short-deadline A; attach long-deadline B to the same key; allow A to expire before gated work completes; B should obtain the valid product or an independently justified producer-policy refusal, without receiving A's cancellation/deadline as B's scientific outcome. Reverse deadline order, cancel A explicitly, expire both and assert no overlapping duplicate producer before actual join. No such test was executed or found in the bounded inspected preparation/flight tests; this is a narrow search limitation, not repository-wide absence proof.

### P-F8: compiler serialization can consume scarce dispatch capacity and defer cancellation behind another operation (new concurrency finding)

**Implemented diagnosis; workload consequence source-inferred.** `plan_frontier_controlled` dispatches through `job_retained_scoped`; the charged native worker calls `MathService::with_modeling_compiler`, which blocks on `workspace.compiler: std::sync::Mutex` and holds it through specialization/grouped planning. Direct selected-function, parametric and observation preparation also lock inside dispatched workers. A different request on the same lane can hold this lock. Cancellation sets the worker flag but cannot interrupt the blocked Mutex acquisition; the correct join owner consequently remains waiting behind unrelated preparation. CPU/active admission has already occurred before the worker reaches the lock. Fixing P-F6 does not make that wait cancellable.

**Proposed corrective contract.** The compiler workspace owns cancellable exclusive preparation admission before acquiring scarce active CPU/native-thread resources. Transfer its exclusive right into the worker for the actual mutable operation. Preserve the atomic head comparison+use in `with_modeling_compiler`, candidate publication consistency, monotonic lineage head, detached historical revisions and one writer; no unlocked precheck of the head. Pure operations over already-owned immutable products should use their actual consumed compiler context without requiring a mutable Salsa generation if feasible. This need not change the single-writer rule or introduce a new scheduler. Making the mutex asynchronous while acquiring it inside the charged worker would not remove resource coupling.

**Verification candidates.** Gated A holds a workspace; B uses a different preparation key in the same lane, is cancelled/deadline-expired while waiting, and must cease waiting without requiring A's completion. Check B consumed no active CPU/native worker merely to queue, A stays valid, and a third compatible caller sees one coherent head. Retain historical/branch/concurrent-writer and failed-candidate tests. This finding does not attribute the audit's single cold-case delay to contention; no such contention was measured there.

## Resource lifetime assessment and library alternatives

`MathService::workspace` reserves the full policy `workspace_bytes` before constructing CompilerWorkspace, with input/retained halves bounded. Workspace clones retain both compiler and AllocationLease. Prepared products/revisions own separate allocation lifetimes. `compiler_lane` retains one live lineage/context writer, evicts only idle compiler handles, and uses detached workspaces for historical/branch contexts so older preparation cannot rewind the live head. Existing lane tests cover those semantics in source. Thus the two observed 64 MiB compiler reservations in AUD39-07 are real charged owners, not shown duplicates.

Pressure handling already exists: `MathService::reserve` retries after `trim_compiler_lanes` and idle native retirement; dynamic snapshots and clear_program_cache also trim. `trim_compiler_lanes` removes only compiler handles with strong_count==1, preserving borrowers. A result-reader reservation through another pool owner may not trigger this math-specific optional-retention path. That is a cross-owner pressure-composition inquiry for the coordinator, not evidence to delete compiler owners or raise the cap. Smaller/exact workspace accounting is an alternative only after establishing complete Salsa/query/foreign heap bounds and lifecycle safety. Fixed charged envelopes may be intentionally conservative; source alone does not show they can be shrunk safely.

**Simplest/library comparison.** Existing BTreeMap root/prefix indexes and local immutable context reuse remove demonstrated work with no new dependency. Salsa 0.28.4 already provides tracked phase queries and equality/backdating (`granular::{resolved,typed,complete,...}`) and is the right existing owner if reuse crosses source revisions with explicit immutable inputs. Its local skill and Context7 agree on dependency/backdating principles, but Context7 returned older cancellation wording; pinned local evidence governs exact 0.28.4 token/fixpoint behavior. Salsa alone does not see arbitrary plain fields or changing evaluator overlays, and it does not fix caller/producer cancellation or a blocking compiler mutex. Do not add a parallel memo cache around mutation without defining complete inputs. The local math skill pins Symbolica 3.0.0 while the current repository pins 3.0.1; no exact-version math capability claim transfers here. Broader numerical library comparison belongs to the sibling inquiry. No math solver or expression engine can own repository lexical visibility, Pending semantics or source permission by default.

## Consequence priority, prerequisites and rule impacts

Highest prerequisite for slow case reruns is P-F6: deliver cancellation to real preparation, retain study bookkeeping and actual join. P-F7/P-F8 are independent high-priority concurrent lifetime problems; closing the disconnected token alone is insufficient for caller isolation or prompt cancelled-waiter settlement. P-F1/P-F2 are high preparation work corrections, supported directly by source and the bounded interrupted audit. P-F3/P-F4/P-F5 are source-established work amplification with unmeasured end-to-end materiality; prioritize according to representative operation demand, not sampled clone frames. The lexical/overlay contract must be settled before broad cache implementation. Direct selected-function construction requires assembly equivalence before migrating all modes. These are prerequisites, not a staffing/schedule proposal.

For the scoped recommended target, **rule impacts: none required**. The remedies preserve authored semantic authority, exact identity/dependency/pin scopes, required numerical state checks, local source/durable permission distinction, one compiler writer, explicit force validation, minimum original caller clock and join-owned charges. ADR-0178/0183's current single-writer/immutable/local-source statements support those preservation constraints; they are context, not the standard used to decide the findings. If later design chooses to share one writable Salsa generation concurrently, weaken source/absence premises, transfer caller time into scientific identity, or remove original-space checks, that is a distinct rule impact and should be listed explicitly; none is recommended here. Defining service-owned shared-producer clocks may need an enduring contract clarification, but does not authorize changing original caller deadlines.
