## Judgment and target operations

The target boundary has useful composition: Python primarily projects native operations and owned handles; native studies avoid per-point Python orchestration; exact scientific tables cross through Arrow with retained ownership; and relational preparation has actual internal consumers. The principal problems in this scope are the lifetime of stable validation preparation, admission lost during collection completion, repeated structural/diagnostic work, and eagerly reserved file-source capacity with no current runtime source path. These establish bounded AP-07 concerns without a latency measurement. They do not establish that DataFusion itself is unnecessary or that its generic engine contracts are unimplemented.

For interactive edits and repeated result encoding, validation preparation should survive unchanged registry and native implementations. For longer trajectories and study result reads, physical copying and per-field diagnostic construction matter even when the returned Arrow boundary is zero-copy. For interruption, ordinary Python native calls have a signal/cancel/drain bridge, but C-stream pulls use a different path; that distinction needs explicit treatment. For library upgrades, engine field-preservation, effect, resource and actual-implementation checks remain consumed responsibilities even where a high-level Python convenience API is absent.

## F23 — retain diagnosis, split obligations and correct the remedy

**Position: confirmed in its principal repetition diagnosis; improved corrective contract and preservation; re-scoped IPC and interactive-build claims.** This finding groups several independently closable obligations. Keep them visible even if one final ID is retained.

### Validation lifetime and carriage

`EngineFactory::models` stores `Weak<ModelAssembly>`. `validation_context` obtains an assembly, initializes its `OnceLock<Arc<ValidationContext>>`, returns the context, and drops the temporary assembly. `NativeValidation` retains a cloned `SessionState`; it does not retain `ModelAssembly`. The inspection UDTFs retain their own pre-registration validation snapshot, also not the outer assembly. Runtime retains the factory and registry, not a strong assembly. Thus successive deployment-factory validation calls rebuild the assembly unless some other consumer keeps that exact assembly alive. The physical inventory uses a derived factory with target partitions and a refreshed models map, so retaining that session does not solve the deployment-factory lifetime.

The original text says F-P1 confirms this, but the original evidence README V14 says rebuild frequency remains probe-pending and lists validation-context identity among unexecuted probes. Correct that evidence claim. Structure establishes the defect; whole-run frequency and the approximately 22 relation encodes/22k contexts per 1,000 points are source inference, not executed measurements.

`LocalFieldAdmission::matches` compares an equivalent declared contract and `PreparedLocalContract::same_native_owner`, a fresh per-context `Arc<()>`. That is conservative and sound; it becomes unnecessarily expensive when identical immutable context is repeatedly recreated. `Collection::finish` independently loses an admission: `T::finish` returns checked data; completion wraps the same batch in a reserved allocation owner and reconstructs with `FieldCheckedBatch::from_parts`, which has no admission. Other checked transforms explicitly carry admissions.

**Correction.** Retain one reusable validation preparation owner for each live immutable registry/native-implementation scope, and preserve admission through an allocation-only wrapping operation. Make the lifetime owner explicit: a fixed-registry runtime/active assembly or a bounded factory cache are plausible alternatives. Merely converting the public factory's weak map into an unbounded strong map retains every registry ever passed until the factory dies; that is not an acceptable default lifecycle without a retention contract.

Keep actual immutable implementation owners. `EngineSession::function_inventory` hashes DataFusion version and sorted function names; it does not hash actual UDF implementations. `Functions` and `Witness` deliberately compare actual Arc owners and relevant policy/settings/provider dependencies. A same-named replacement UDF is a legitimate extension and must invalidate affected validation. A signature/name hash plus settings cannot certify interchangeability. There is no need to replace all Arc-based admission matching: retaining a stable actual owner can make the current equality useful. If equivalence across distinct owners is desired, it requires a separately established consumed contract, including relevant expression rewrites, configuration, execution properties and selected bindings.

Adjacent A's `SelectedRequest`/`BasisKey` factory and registry identities are compatible with this correction: retain their actual immutable scope, rather than substituting an inventory digest or transient assembly identity. Preserve factory retirement/eviction and the rule against extensions retaining their own enclosing assembly/context cycle.

### Successful validation work

`PreparedLocalContract::evaluate_selected` runs `validate_full` over every column before predicates. `occurrences::Node::root/visit` eagerly builds row locations and visible/index vectors; nested children build coordinates even when values pass. `gather` uses Arrow take unless indices enumerate the whole array, including contiguous strict subranges. These are concrete repeated structural work and eager diagnostic materialization. The code already bounds occurrence work in chunks and uses native predicate kernels; do not describe it as an unbounded whole-table diagnostic collection.

**Correction.** Separate structural ingress admission from semantic predicate evaluation where a concrete trusted structural owner is available; retain or carry that owner through safe operations. Build exact nested paths for failing values, use slices for contiguous visible ranges, and avoid rechecking already-admitted appended chunks when the new operation preserves their premises. Do not remove structural checks merely because a `RecordBatch` is a safe Rust value: schema/row-count constructors do not establish every array's full structural validity. Untrusted IPC/FFI and unchecked/native producer boundaries still need structural protection. Preserve null-parent/inactive-arm masking, SQL false-or-unknown refusal, exact row/path/rule diagnostics, bounded finding samples, cancellation and errors distinct from successful validity.

### IPC framing and copies

The copy diagnosis is real: `result_blocks::decode_block` preflights, then `StreamReader<Cursor<&[u8]>>` allocates metadata/body storage; the canonical codec adds ownership copies before that. `encode_block` preflights the writer's own completed output. A complete owned `Bytes` → Arrow `Buffer` → `StreamDecoder` path can remove selected reader copies. Alignment can still cause copies, and a small slice can retain a larger underlying buffer; zero-copy is not itself the objective.

**Critical remedy correction.** StreamDecoder is not a replacement for all current bounded transport admission. At 59.3 it still invokes `fb_to_schema` and `RecordBatchDecoder::read_record_batch`. The pinned reader's struct path constructs `BooleanBuffer::new(null_buffer, 0, len)` before completing full validation, with a buffer-size assertion. Existing local test `oversized_node_and_short_validity_buffers_are_refused_before_arrow_constructor` specifically protects that failure domain. Current preflight also enforces schema depth/type restrictions, row/value/node/buffer limits, no dictionaries/compression/variadic buffers, exact expected schema, no overlap, one record batch and explicit EOS/no trailing data. These are consumed bounded/refusal contracts, not all redundant decoder checks.

Separate writer-side checking, decoder copy avoidance and bounded untrusted admission. Replace only obligations the selected pinned decoder demonstrably discharges. Preserve the remaining narrow preflight checks, or qualify a fitting decoder/upstream correction first. The original wording “keeping only the semantic checks the decoder lacks” is insufficient: some retained checks are structural and pre-allocation/panic-domain protection. This is a preservation correction, not a rejection of the copy-reduction direction.

Pinned source: [Arrow 59.3 StreamDecoder](https://github.com/apache/arrow-rs/blob/59.3.0/arrow-ipc/src/reader/stream.rs), `RecordBatchDecoder::create_struct_array` in the pinned local `arrow-ipc/src/reader.rs`; local owner `result_blocks::{preflight_block,layout,decode_block}`.

### Interactive build

`py-sync` and `py-sync-native` do explicitly enable force-validate. Production measurement already has a separate unvalidated release recipe. An interactive production-mode extension is a reasonable option; the source alone does not establish the magnitude of force-validation's marginal interactive overhead, because explicit local validation remains too.

Preserve actual correctness closure validation and truthful installed-extension mode. `py-unit` distinguishes linked/dev availability, not a force-validation feature mode. Native Python provenance currently supplies a declared `['force-validate','native-solvers']` feature list. Changing sync defaults without correcting test selection/provenance could silently test an unvalidated extension under a validated claim. This is a prerequisite of the recipe remedy.

**Priority.** Stable context/admission carriage: medium, shared preparation dependency for edit/result/physical routes. Diagnostic work and structural rescans: medium where large trajectories/results reach them. IPC copy reduction: medium potential, but its safe admission replacement must be designed before deletion. Interactive force mode: unmeasured option, not a prerequisite for fixing all other F23 obligations. Mandatory independent scientific checks of each new numerical state remain outside this optimization.

## F24 — narrow to unsupported eager resource allocation; withdraw broad capability/G8 claims

**Position: corrected diagnosis and remedy; retain file-capacity reservation and unread-setting issues; withdraw “no user-reachable inspection route” as stated.**

No in-repository production caller was found for `run_invariants`, generic SQL/DML/schema-transform APIs or file-cache binding. That fact does not make these absent user capabilities. `pse-rules::lib` exports `pub mod invariants`; `pub async run_invariants` consumes candidate rows, a real EngineSession/Registry, explicit InvariantScope and cancellation and returns an owned `InvariantReport`. Public `EngineSession::prepare_sql` parses and binds native SQL with actual source/effect checks; `prepare_schema_transform`, `with_provider` and mutable-capture entrypoints are also public Rust contracts. The documented blueprint §14.2 statement is “Declared registry invariant queries support explicit inspection”; it does not say Python exposes a convenience facade. The public Rust operation supplies that route. A convenience Python invariant API or cross-study TableProvider may be useful, but its absence does not establish this G7 failure.

There are substantial real internal consumers as well. `PhysicalInventory::load` calls `prepare_many`/`PreparedComputation::execute_group`, then consumes checked relations; `physical::plans` runs unit and context selections. This reaches actual rebind/logical cache staging, analyzers/optimizers, physical field restoration, execution context, query admission and completion ownership. NativeCacheService supplies model cache, query/output admission, cache-component registration/inspection and math retention integration. Round/reset and effect machinery compose with public reusable execution paths; absence of a Python session facade is not grounds to remove these contracts. This inquiry does not assert every engine internal is necessary; it rejects deletion by an unproved reachability premise.

**Confirmed narrower defect.** `EngineResources::build` creates `NativeCacheService` whose `Envelope::new` immediately `try_grow`s metadata/statistics/listing capacity. The default engine runtime gets `unbound_config()` with file caches disabled, and inspected application consumers never bind a qualified file source into those caches. `CacheBudget::for_memory` caps metadata/statistics at 50/16 MiB; at a sufficiently large pool, including 4 GiB, that consumes exactly 66 MiB of *accounted capacity* before entries exist. This is not proof of 66 MiB physical RSS: a reservation can reduce usable admission capacity without allocating those bytes. The original “each runtime pool starts with about 66 MiB” needs the pool-size condition; smaller pools reserve smaller fractions. Syntax has its own reservation and public SQL consumers, so it must be considered separately.

**Library-fit correction.** Envelope delegates DataFusion `DefaultCache`; it adds finite-pool reservation/key accounting, source-generation namespaces and maintenance ownership. Those are not supplied simply by native byte limits. `SharedIo` deliberately shares one semaphore across stores and handles nested/reentrant scope and body-stream lifetime. object_store's native LimitStore has a private per-wrapper semaphore; replacing it blindly changes the consumed contract. Lack of a current file consumer supports making its eager allocation/construction optional or retiring that integration, not a blanket claim of G8 reimplementation. Native default caches/LimitStore remain alternatives if the required resource contract changes; no G8 failure is established here from those library names alone.

**Correction.** Do not reserve or build file-source machinery until an actual selected file-source role needs it; alternatively retire that narrow integration if the product drops the role. Retain query/output admission, model/math/cache ownership, observation and actual native semantic contracts. Delete or implement the unread `ResourceBudget::hashing_may_use_pool` setting: production source uses it in declarations/projection only, with no hashing execution read. Distinguish deletion of a dead user setting from refusing a library capability for lacking a consumer.

An optional canonical result TableProvider should be judged on study-inspection demand, pushdown/fidelity/retention and total machinery. Adding that provider does not make unused file metadata caches necessary; canonical result blobs are not ListingTable/Parquet file metadata. It is not a prerequisite for eliminating eager unused reservations.

**Priority.** Low-to-medium bounded resource cost depending on pool size and simultaneous runtime count; low setting hazard. Do not rank a new query platform as required low-priority cleanup. Reusing the engine's existing actual contracts is a preservation constraint, not an argument for forcing all result reads through DataFusion.

Pinned library source: [DataFusion 55.1 CacheManager](https://github.com/apache/datafusion/blob/55.1.0/datafusion/execution/src/cache/cache_manager.rs). Current Context7 cache documentation was consulted for discovery; local pinned wrappers and consumers establish the narrower diagnosis.

## Additional candidate D-N1 — Python signal/cancel bridge stops at the C-stream boundary

**One falsifiable cause.** `TableStream::from_canonical` creates a callback that directly runs `runtime.executor.block_on(reader.next_batch())`. It does not use `workflow::blocking_on_with_recovery`, whose 100 ms timeout/poll loop checks Python signals, requests cancellation and waits for native settlement before returning the original exception. After capsule export, C `get_next` reaches `BatchStream::Reader::next` and the canonical callback; the earlier `py.detach(|| self.0.reader())` only creates the reader.

**Workload/consequence.** Main-thread `pa.RecordBatchReader.from_stream(stream).read_next_batch()` or `read_all()` on a slow/stalled canonical read can postpone Python SIGINT handling until a native pull returns. The pinned PyArrow reader performs ReadNext/ToTable with `nogil`, so other threads run; this is **not** a claim that default PyArrow holds the GIL. `CanonicalResultReader` checks the cancellation token before `next_checked`, but renew/page/blob awaits do not consume that token directly. Another thread can request stream cancellation, yet the current RPC may still settle by its normal completion/deadline before the read exits. Canonical RPC deadlines provide an important finite limit; no infinite hang or measured delay is claimed.

**Standard/scenario.** AP-05/AP-07, DP-19/DP-21, H21/H24; grow/interruption boundary journey. Lower-priority source candidate pending a controlled interruption observation; it does not establish PS-G3 failure or changed scientific results.

**Correction direction.** Give Python-controlled consumption an explicit cancellable pull path using the existing signal/cancel/drain owner, or provide an equally clear async consumption path. Keep generic C-stream export's exact schemas/zero-copy ownership and document its consumer-controlled signal behavior. Do not add Python callbacks to generic engine readers or swallow a late read error as EOF. Establish whether native per-RPC cancellation should consume the stream token separately with B's coordination owner.

**Preservation.** Successful exhaustion, close, cancel and native failure stay distinct; yielded arrays remain valid after close; protection and memory owners survive until unread work drains; C consumers need no Python interpreter; no same-executor reentry.

**Verification.** A dedicated delayed-read fixture should arrange a canonical pull in progress, deliver SIGINT on the Python main process, and distinguish prompt signal-to-cancel-and-drain from deferral to pull completion/deadline. Compare with an ordinary native blocking call using the existing bridge. Do not infer this result from a CPU counter or GIL-release test alone. Until that probe, retain as candidate with this exact uncertainty rather than assigning a measured responsiveness defect.

Pinned evidence: [PyArrow 25.0.1 `RecordBatchReader::read_next_batch/read_all/close`](https://github.com/apache/arrow/blob/apache-arrow-25.0.1/python/pyarrow/ipc.pxi), local `pse-py::inspection::TableStream::from_canonical`, `pse-engine::arrow_stream::Reader::next`, `workflow::blocking_on_with_recovery`, `CanonicalResultReader::{next_relation_batch,next_checked}`.

## Strengths, omitted-scope results and non-findings

- `import pse` checks compiled version/fingerprint and registers eleven passive extension types once. It does not call runtime acquisition or connect to canonical storage. The default numerical executor, engine factory and deployment observation belong to first explicit runtime/registry inspection use. Eager imports may still have cost; no measured import finding is asserted.
- `inspection::runtime::acquire` shares one process runtime/executor/resource budget, completes fallible registry/session setup before publication, and rejects mismatched budgets. That is an explicit process policy with reuse benefits. Its construction is not repeated on every Runtime handle. Registry reflection currently constructs this broad owner and executor too; lazy setup is an opportunity whose actual marginal cost remains unmeasured, not a new proven dominant startup defect.
- NativeRuntime construction includes fresh deployment observation after detached shared-runtime acquisition. `observe_deployment` is called while attached, before the later signal-aware blocking reconstruction bridge. This is relevant to A/F05's observation frequency and placement; do not attribute all startup time to DataFusion. No timing was measured here.
- Ordinary blocking native operations detach, check signals, cancel and retain ownership until completion/drain. Native studies execute in Rust, not a Python loop of point calls.
- The default Arrow export is one-consumption, exact-schema, owned and refuses requested casts. BatchStream separately retains structured native failure beyond Arrow's text-only error slot. Close/cancel distinguish EOF from failure and yielded buffers remain owned. Source-read tests verify intended ownership but were not executed in this inquiry.
- `to_ndarray` refuses nullable data and requires an explicit copy reason for non-zero-copy conversion. `compare_schemas` observes nested metadata degradation without claiming semantic value admission. Neither is repeated numerical authority.
- Python edit/fit declaration paths do cattrs unstructure → JSON encode/decode → encode before Rust admission. This extends F02's conversion observation to fitting; it is not a separate independent cause. Converter freshness protects mutable caller hook isolation. Reuse would need an immutable private converter/compiled hook owner, not a mutable global singleton exposed to callers. Version-header raw/typed decoding and strict unknown-key refusal have real semantics; they are not removable just because there are two passes.
- PhysicalInventory still uses actual relational preparation and source-owner checks. Optional sorted-source declarations, cached immutable registry reflection and reduced DTO conversions could help, but source evidence here does not justify a new mandatory subsystem or claim measured benefit.

## Probes and unresolved decisions

No workload probe is necessary to establish the weak-owner/admission-loss source defects, the public Rust inspection route or the eager reservation mechanism. Do not require a benchmark before fixing those structural causes. Decision-relevant probes for coordinator consideration are:

1. **IPC preservation discriminator (highest value before selecting removal).** In a coordinator-owned scratch harness using the exact 59.3 lock, run existing malformed-schema/node/short-validity fixtures through default StreamDecoder wrapped with `catch_unwind`; compare against current preflight+StreamReader. Exact functional recipe after a scratch test is added: `scripts/pse-env -- just unit-package pse-runtime 'test(stream_decoder_admission_preservation)'`. Conditions: correctness force-validation enabled; complete owned buffers; no compression/dictionaries; include current canonical result/source schema bounds. Outcomes: panic, excess allocation or acceptance of an existing rejected shape requires retained narrow preflight or upstream correction; equivalent bounded refusal permits deleting only those proved redundant checks. This requires coordinator-approved scratch code/build scope; not run here.
2. **Python interruption discriminator.** Coordinator-owned `/tmp/pse-efficiency-audit-2026-10-11/canonical-pull-interruption.py`, invoked as `scripts/pse-env --store -- .venv/bin/python /tmp/pse-efficiency-audit-2026-10-11/canonical-pull-interruption.py --state "$PSE_SURREAL_STATE" --run <fixture-run> --attempt <fixture-attempt> --relation runtime.solve_variables --signal-after 0.1`. Preconditions: an exclusive dedicated delayed-read fixture/store, known installed extension feature mode, no other owner affected, main thread enters one canonical pull before the signal; this script/fixture is a proposal, not an existing artifact. Outcomes: signal causes existing cancel/drain path before delayed read completion refutes the candidate; delay to pull completion confirms the boundary gap; signal between pulls is inconclusive. Avoid a full solve campaign.
3. **Interactive force-mode decision, only if choosing that recipe change.** Compare the same representative edit/result loop under `just py-measure-force` and `just py-measure-production`, keeping identical release/native feature family and workload, and observe actual built extension identity/features before every correctness run. Outcomes distinguish material marginal Arrow-construction validation cost from explicit local validation or unrelated preparation cost. Those recipes build/install extensions and are not light source probes; no execution is requested merely to close this inquiry. The principle permits the mode distinction without a speed claim.

A cache reservation probe is optional confirmation, not decision-critical: at a 4 GiB CacheBudget source already proves 50+16 MiB pool capacity reservation and zero bound runtime file caches. A runtime/context identity probe can quantify frequency, but cannot make a function-name hash a valid implementation identity. Exact implementation retention, field-admission carriage, bounded IPC admission and Python correctness feature provenance are prerequisite contracts. Selecting a new canonical relational inspection API is a separate product decision.
