# Build, test and development: independent bounded audit

Inquiry E supports `design_review_efficiency-alignment-audit_2026-10-11.md`. It compares original F25–F28 and RC17–RC19 and extends source inspection into product generation, runner interruption, supervisor integration and parity setup. It does not own overall acceptance or finding disposition.

Baseline: `main` at `b01a45d71a5f5ab29991ad193679f5588ac3662f`. Concurrent validation/Plan 28 edits and audit documents were preserved. Decisive ledger behavior below was checked against both the working file and `git show HEAD:scripts/test_resources.py`; it predates the concurrent reclaim deferral. No repository files were edited. No builds, tests, services, dependency changes, formatting or workload probes were run by this inquiry.

The development-loop diagnosis survives, but its causal explanation needs correction. The hot ledger already retires disposed resources and demotes settled evidence; retained unresolved obligations still share a full-file coordination path. Runtime test helpers really do construct isolated canonical fixtures, but the durable `Operations` constructor only binds handles, so laziness there is not the claimed cure. Python test dispatch and broad generator/dependency placement demonstrably add unnecessary build dependencies. Host CPU policy trades utilization for isolation; some original claims confuse direct CLI dispatch with wrapped recipe execution, polling with no waiting, and configured thread width with measured harm.

## 2. F25 — confirmed residual, corrected breadth and remedy

**Diagnosis: Interface-checked; corrected/re-scoped.** Every `resource_metadata` access takes `host.metadata(registry())`, whose default deadline is `None`. That owner obtains an exclusive lock, parses/validates the hot JSON ledger, yields it, and rewrites it after the operation. Resource validation and retirement additionally loop over the hot owners. Registration checks existing records for identity conflicts; finalization scans for the invocation. These costs grow with hot owners, including unresolved or pinned failures and retained databases, and serialize host-wide.

The original account omitted behavior already in the baseline: `resource_metadata` removes drained, unpinned, unreferenced, unborrowed disposable records after cleanup=removed; it demotes settled compacted evidence to exact `completed/<resource>.json` lookup and a report index. A completed history scan is explicitly absent. Therefore neither “all history stays hot” nor “there is no archive separation” is correct. An old ledger census cannot establish why individual records remain hot or that they lack legitimate obligations.

`reclaim_reports` still opens and rewrites the whole hot ledger before choosing up to four evidence candidates. Its five-second clock does not bound that initial default blocking lock, ledger parsing, or all subsequent work. Passed retained **database** records are not retried by this evidence-only sweep. Invocations and their generated configuration/JUnit/terminal artifacts have no retirement route identified in the inspected owners; this is a bounded source-search result, not proof that no external retention owner exists.

**Dispatch corrections.** Direct `just --list` lists recipes without executing a recipe shell. Bare `just` executes `default`, whose inner `just --list --unsorted` is wrapped. Ordinary newly scoped non-native commands execute the `main` cleanup finally; newly scoped native commands execute `native`'s analogous finally. Inherited/no-scope execution and nested native operations use `exec`, so they do not independently perform that outer cleanup. `--print`, `--explain`, admission refusal and unexecutable-command paths do not all enter it. Replace “every environment exit” with “applicable newly scoped workload exits, including unrelated compilation and the wrapped default recipe.”

The cleanup failure/liveness defect is source-supported within those paths: the initial `reclaim_reports` metadata access is outside its per-candidate catches; exceptions escape the outer finally and are converted to boundary status 125. The original child's status can consequently be lost. The default lock wait has no deadline. This establishes a possible mechanism, not an observed production hang.

**Corrective contract: Proposed.** Separate exact resource coordination from unrelated report sweeping. A resource-free workload need not open the fixture ledger at exit. Keep current live/unresolved obligations queryable through exact records or indexed state; full JSON rewrite is an implementation choice, not required semantics. Preserve and complete the existing cold-evidence mechanism rather than describing it as new. Give the runner or explicit cleanup owner bounded, eligible retries for database disposal deferred by service state. Archive or retire invocation artifacts only after identifying remaining association/reconciliation/evidence consumers.

Per-record files and library-owned indexed storage are alternatives; SQLite/WAL is not a required architectural choice. Direct Rust registration or batching is likewise optional: removing two interpreter launches does not itself solve full-ledger exclusion, and a new direct writer must not duplicate registration/retention policy. One authority must continue to own it.

**Preservation.** Exact selected-test association; opaque database identities; service-generation/namespace checks; reference and borrower fences; no recreation; terminal-owner authority; actual drain before eligibility; pinned/unknown outcomes. Keep child outcome, cleanup outcome and drain outcome distinguishable. An unrelated report-sweep error should not erase a failed command or turn a passed command into an unattributed failure; a genuine failure to drain the command's own admitted work must still fail the boundary and retain its charge. “Ignore all cleanup errors” is not an acceptable correction.

**Priority/order.** High within the development loop for cross-owner status/liveness and growing serialized work. Remove unrelated exit sweeping and make failure ownership explicit before selecting a new ledger backend. Retention/disposal contracts precede automatic artifact retirement. A latency ranking against product findings remains unmeasured.

**Verification.** Use isolated temporary ledgers to show exact access/update cost independent of unrelated retired evidence, retained/unknown records remain protected, deferred database cleanup is retried only by its owner, and a poisoned unrelated ledger cannot mask a resource-free command's terminal result. Check both native and non-native outer routes plus inherited execution.

## 3. F26 — confirmed helper coupling, reject lazy-Operations as its cure

**Diagnosis: Interface-checked; improved causal contract.** `runtime_on` constructs SharedRuntime, registry and sessions, then calls `canonical_deployment` before `with_durability(Ephemeral)`. That helper selects a fresh canonical fixture database, registers it, connects, and invokes `store.create()` for the complete schema. The Rust bridge and remote schema installation are real setup costs. Some subjects do require that scientific admission/integration path; others assert bounded local policy or composition properties and should not need it.

`Runtime::from_shared` accepts an already supplied `CanonicalDeployment`; it does **not** itself start a service or install a schema. `Operations::from_store` simply stores existing handles, worker text, policy and pool. Eagerly allocating that durable object is not the explanation for per-test database startup. Making it lazy cannot eliminate the canonical source dependency. The hidden-start concern belongs to fixture `register`, which can demand/unpark/start a profile-v2 service, not to the inexpensive `Operations` binding constructor.

Concrete subjects are `workflow::tests::workflow_composition_preserves_custom_same_owner_factory_and_partition_demand`, which provisions a fixture and then asserts only that a custom session extension and target_partitions=3 survive composition, and `workflow::tests::workflow_composition_refuses_foreign_consumed_owners_and_width`, which provisions two fixtures and asserts rejection for foreign allocation/spill/cache/object-store/CPU owners or width, then accepts the matching factory despite an in-flight permit. `Runtime::check_deployment` consumes SharedRuntime and EngineFactory only, comparing Arc ownership and configured CPU width; it never reads the canonical deployment. These are direct examples of local composition assertions paying unrelated database registration/schema setup. Direct tests of that owner can retain a smaller end-to-end Runtime composition control without weakening scientific admission.

The original 1.31-second median is cold setup **before store consultation** in a particular shared-host JUnit run. It is not measured schema cost, fixture cost, Runtime-only CPU cost or the speedup available from lazy durability. No decomposition was performed here. “Policy and algorithm assertions cannot run without a store” is too broad: directly tested policy owners already exist, and `.config/nextest.toml` explicitly treats several as pure. The narrower problem is store-requiring tests that compose a Runtime although their asserted responsibility does not need canonical semantics.

**Corrective contract: Proposed.** Choose by subject. Test explicit policy/transition/admission owners directly with actual typed inputs. Keep Runtime/store integration tests for behavior that consumes canonical source or publication semantics. For the remaining integration population, consider amortizing initialized fixtures or runner-owned provisioning after one compatibility preflight; pooling is optional and must have a clear reset/isolation contract. A fixture reused after mutation, incomplete drain or interpretation change cannot silently certify another test.

No “store-free ephemeral Runtime” follows from these changes. Such a production capability would change the canonical scientific-source contract and needs its own rule impact and design, beyond original options (a)–(c).

**Preservation.** Scientific source admission even for ephemeral scientific execution; per-test isolation wherever state is asserted; late interpretation/refusal checks; real compiled/native execution for integration subjects; honest failures; fixture drain and retention ownership. Required independent post-solve checks remain.

**Priority/order.** High development concern where the subject/setup mismatch is demonstrated. Audit representative assertions and extract direct owner tests before designing a database pool. Fixture preflight can proceed independently of a large product decomposition. Removing the tiny `Operations` allocation is low priority and does not close F26.

**Verification.** Demonstrate a named pure policy test without selected store authority, alongside unchanged canonical integration tests that reject incompatible interpretation and preserve isolation. Separately measure SharedRuntime/session setup and store lifecycle if magnitude would affect prioritization. Counts of helper references do not determine which tests may safely move.

## 4. F27 — confirmed in parts; refine dependencies, generation and rule implications

**Diagnosis: Interface-checked.** The `py-test` recipe runs `scripts.arrow_validation run ... --package xtask --bin xtask` with xtask's default `package-fixtures`. `xtask::python_tests::run` merely spawns the project Python interpreter with `-m scripts.python_tests`. The latter already owns selection, observer placement and fixture runner composition. This Rust build hop is unnecessary for that Python operation. Removing it does not remove the extension's own real Rust dependencies.

The full codegen route intentionally bootstraps Rust contracts and Surreal schema first, then builds the package-fixture-enabled generator under `--native=compiler,solver`. Physical fixture projection imports the production authoring driver and `PhysicalInventory` from `pse-runtime` and constructs a SharedRuntime/engine to use those contracts. Document schemas also derive actual runtime/boundary types. These dependencies are real at their current placement; it would be wrong to replace them with a handwritten schema or reduced scientific checker just to cheapen generation.

The corrective direction is capability-shaped generator targets and better placement of the production admission/inventory owner, not merely skipping work based on the filename that changed. `codegen::ipopt::run` derives bindings from actual selected headers; `--only` targets already exist. A “headers or generator changed” shortcut must cover transitive included headers, bindgen/clang configuration and tool versions, relevant feature/target choices and missing/stale outputs. `codegen-check` still needs actual regeneration comparison. Native preparation and physical projection are separate requirements: there is no evidence that a physical registry projection intrinsically requires a solver installation; the current all-target command does because it also invokes Ipopt bindgen.

`pse-math` normally depends on egobox-ego/moe/gp and argmin for `surrogate`; **egobox-doe is a dev-dependency**, contrary to G/L1's wording. The inspected direct consumers of public `pse_math::surrogate` contracts are within `pse-runtime`, including prediction, strategy, starts and tests, not just one actor file. Moving the coherent surrogate library integration into that consumer or a lower dedicated crate can narrow compiler/math roots while preserving public/local contract ownership. Under mandated workspace feature-unification a feature enabled by the Runtime consumer can remain enabled for a selected math root; feature gating alone is not an established fix.

The workspace-hack really adds otherwise unrelated dependencies to some narrow roots. But it is not an unexplained duplicate: ADR-0122 explicitly supplies a fallback for Cargo ignoring `[unstable]`, and acknowledges wider small-root closures. The audit may recommend removing that fallback, but must say so. Narrowing membership is an alternative that retains some fallback coverage. Original pruning/unit counts are supporting evidence from the original graph; they were not recomputed here and are not latency measurements.

**Corrective contract: Proposed.** Call the Python runner directly with the same selected environment/store and argument semantics. Separate native header generation from physical/document projections while retaining full aggregate comparison. Move a coherent production preparation/inventory capability below the high-level Runtime if that gives real narrow consumers; no crate split is required merely because a function has a domain name. Relocate surrogate integration if it meaningfully narrows affected roots. Retire or narrow hakari only after explicitly settling its fallback purpose.

**Preservation.** One authoritative registry/declaration; production-path physical admission; actual boundary serde types; generated output root/pruning contracts; byte- and mtime-preserving no-op publication; complete regeneration comparison; exact locked dependencies; one Arrow/DataFusion type universe; explicit force-validation in actual correctness closures; checkout-local targets/shared content-safe compiler cache; unwind and floating-point settings. Removing a wrapper must preserve Python exit/signal reporting, selected test arguments and native observer requirements.

**Priority/order.** Medium overall. The Python hop is a low-risk independent correction. Codegen placement and surrogate dependencies affect cold/worktree/dependency-change work more directly than cached warm checks. Retire/narrow fallback only after owner and supported-toolchain decision. No broad Runtime split is justified by source size alone.

**Verification.** Compare selected target/host/dev Cargo units before/after without dropping actual opt-ins; show direct py-test selects the same tests and propagates failure; regenerate all product outputs and compare both directions; confirm no-op mtimes; exercise physical admission and binding generation independently. A pruned lexical Cargo tree is not a compiled feature/profile experiment.

## 5. F28 — retain concrete policy concerns, narrow asserted harm

**Diagnosis: Interface-checked; corrected and partly unresolved.** Functional/compile allocations use four of eight declared functional physical cores with hard CPU-time quota of 400%; the other eight physical cores are statically assigned to timing. Cargo's default jobs are capped to admitted **logical** CPUs, which can be eight for four SMT physical cores; ordinary nextest defaults to sixteen test processes. This describes different units, not by itself an oversubscription failure or a quantified lost speedup. I/O-bound tests may legitimately use more processes than CPU quota.

`acquire` really assigns a second one-slot functional owner the other four cores; it does not stack both slots on the initial `functional[:4]`. It polls until the original admission deadline. Thus “does not queue” should mean “bounded polling without an explicit fair waiter order,” not immediate refusal. A 30-second refusal is possible when slots stay occupied, not inevitable for every third agent.

Ordinary recipe-line commands reach the outer wrapper as `bash -euo pipefail -c <one string>`; classifying first command words cannot inspect their inner cargo/nextest operation. The inner wrapper inherits the admitted owner and cannot repair that original classification. This can give cheap work a functional slot or narrow an intended wider test route. However explicit `--recipe-default-class` is already supported and used for discovery/control recipes; `just activity` has its own fixed read-only exception; direct `just --list` uses no workload wrapper. “Every recipe is functional” is false.

**Correction: Proposed with policy decisions remaining.** Declare classes at actual workload launch boundaries using the existing mechanism, preserving explicit user selection and inherited owner authority. Decide whether idle timing capacity may be borrowed, and under what interference/revocation contract. CPU weighting, whole-functional-lane placement or elastic borrowing are alternatives, not an unconditional demand to remove CPU bounds. Derive/test sensible runner width from the admitted operation where useful, respecting nextest effect groups and workload waiting behavior. Add fair admission only if contention/starvation requirements justify it; bounded waiting may remain a deliberate policy.

**Preservation.** Finite per-command/ancestor memory caps, non-agent headroom and pressure guard; actual unit/generation/drain proof; ownership until opaque work drains; process/solver thread coordination; dedicated timing isolation while measured; resident storage charges; exclusive campaign semantics. A memory-only remedy must still satisfy DP-20 CPU/I/O coordination and cross-repository interference requirements. Neither a larger thread count nor removal of quotas is scientific/performance qualification.

**Priority/order.** Low for general utilization tuning; explicit wrong-class launches may merit Medium where a concrete command is blocked or constrained. Current source establishes intentionally idle capacity under narrow work, but whether that violates the supported host-use contract rather than pays a deliberate isolation cost remains unresolved. F28 should not supply an independent proven DP-20 failure from sixteen-versus-four arithmetic. G9 already has stronger development-loop causes in F25–F27.

**Verification.** Static recipe/launch tracing distinguishes classification from inner argv; temporary-owner controls distinguish two disjoint normal slots, explicit precedence and bounded admission. Optional end-to-end wall-time/throttling observations should use unchanged sources/artifacts and a quiet admitted host; no shared cache clearing or touching concurrent sources is justified.

## 6. RC17–RC19 and corrective compatibility

**RC17 — modify.** The exact consequential rule is AGENTS.md: “An ADR comes before the change ... when the change alters a D1–D14 decision, adds or removes a crate,” with the decisions rule as its route. Following that rule to add an authoring/inventory or surrogate crate is a prerequisite decision, **not a recommendation to change the rule**. If kept, a reviewed crate extraction remains possible through its ADR; it is not limited to moving code into Runtime. Removing the Python hop or rearranging existing modules needs no crate-addition rule change. The actual rule impact is ADR-0122 Outcome 5's fallback workspace-hack and its documented support for Cargo ignoring `[unstable]`. Retiring that fallback changes an accepted design; narrowing it changes which roots retain the fallback. Keeping it leaves some closure breadth unless membership is narrowed. Preserve exact family and force-validation rules independently of either choice.

**RC18 — modify.** `.config/agent-capacity.toml` declares timing/functional core lists, slot/memory profiles and `admission_seconds=30`; the environment guide explains finite CPU quotas, timing isolation and inherited lane authority. Replacing static partition/quota with weights or borrowing changes this policy. Existing declared class selection can be used without inventing or relaxing the authority. Keep timing state/store affinity and resident-service lifetime semantics visible. If the current capacity rule is kept, use correct explicit launch classes and retain a documented utilization/isolation tradeoff; runner-width changes are workload-specific. Do not present memory-only admission as automatically satisfying all shared-capacity obligations.

**RC19 — modify substantially.** Plan 33's “Live coordination and complete analysis deletion” says hot metadata contains “live owners, pending handoffs and unresolved reclamation”; completed records leave only after authentic disposition/drain; exact outcome/reference information stays only while a current owner consumes it and outside full-ledger hot scans; unknown metadata never proves success. Those are preservation constraints that already favor a narrower realization. The baseline already partially implements them with exact cold evidence and disposed-record removal. F25 chiefly calls for completing that realization and detaching unrelated sweep work, not overturning retention semantics. Do not move current pending/drain/reference obligations into an inaccessible archive, delete pinned failures on age, or prune invocations merely because a runner returned. If the full-JSON hot realization is retained, unrelated exits can still skip sweeps and metadata locks can be bounded; hot-owner scaling remains. Any new physical backend must keep one coordination authority, migration/refusal and no-recreation behavior.

No additional rule change is recommended for the unconfirmed build-script opportunity below. A production store-free Runtime would require an additional canonical-source rule impact, but is not recommended or implied by this inquiry.

## 7. Extended inquiry: candidates, contrary evidence and limits

### E-C01 — native environment alternation can invalidate a disabled-capability build script

**Candidate, not an additional accepted high-impact finding.** `pse-backend-native/build.rs::main` unconditionally emits `rerun-if-env-changed` for IPOPT_DIR, PKG_CONFIG_PATH and PSE_ROOT_ISOLATION_DIR, before checking native capability features. It always rewrites solver-manifest.txt and pounce-source.txt. The no-native-feature build produces an empty solver manifest; the POUNCE source identity is legitimately consumed by `execution::Table::build_identity` even outside native solver linking, so its workspace pin dependency must remain. The Ipopt manifest consumer lives in the feature-specific Ipopt integration.

**Falsifiable cause/workload.** Alternate the same no-native-feature backend unit between a plain environment and one with those native prefix variables. If the Cargo unit is the same, native environment presence can rerun its build script despite no changed consumed capability. Current upstream Cargo docs explicitly describe env-change reruns. The strong original G-07 claim—recompilation of the complete backend/runtime on every alternation—is not established here: feature/profile identity, equal generated output handling and actual fingerprints must be examined.

**Consequence/standard.** At minimum unnecessary build-script execution/output rewrite; potentially wider invalidation on a warm edit loop (AP-07, H13/H26; AP-06 if a broad rebuild is demonstrated). Priority Low pending the discrimination; no timing or whole-runtime rebuild claim.

**Correction/preservation.** Track native variables only for features that consume them; keep the actual POUNCE source identity and its pin changes, native link/configuration tracking, generated receipts and source provenance. Write stable outputs only when bytes change if the selected Cargo behavior benefits. Verification must separate script rerun, changed output bytes/mtime, backend rustc execution and downstream work.

### No new finding from counts or unexamined breadth

Product generation already has a pure `GeneratedTree` emitter, declared roots, separate bootstrap targets, production admission for physical fixtures and byte-preserving writes. The problem is broad dependency placement/target composition, not that generation exists. No algorithmic generator bottleneck was established by the inspected emitting loops. Full aggregate regeneration remains a useful correctness operation even when focused edit routes improve.

Supervisor lifecycle/context exclusion is deliberately short around metadata while start/drain IPC occurs elsewhere in the inspected paths. `observer` has ownership cleanup, and native operation cancellation/foreground association has its own drain authority. These are important contrary evidence to a blanket “synchronous subprocess means orphaned native work” conclusion. Unknown observations and exact pending proofs intentionally retain charges.

`test_run::{run_rust,run_python}` constructs terminal composition after synchronous child return, without a local interruption finally. A Python interruption before that point may leave an invocation without terminal reconciliation, while fixtures remain pinned/incomplete. That is relevant to F25 retained-obligation growth and diagnostic completeness; it is **not** evidence of unsafe disposal, a passed cancelled run, or uncharged live native work. Recovery/salvage must preserve the selected terminal owner and authentic JUnit/selection evidence. No separate cancellation finding is asserted without tracing enclosing owner signal delivery and recovery. Existing script controls protect exact inventory, inherited terminal ownership, native-local isolation and import identity; they do not constitute fresh executed cancellation evidence.

The parity recipe always runs locked environment sync and native extension development before selected pytest comparisons. Those are candidate amortization opportunities, but incremental sync/build may already be cheap; no rebuild speed finding follows merely from always invoking them. The isolated Python interpreter/reference pins, selected native solver prefix, fail-never-skip preflight and session-scoped comparison Runtime are useful preservation constraints. No recommendation removes the independent IDAES/Pyomo oracle, changes tolerances, or substitutes producer-derived expectations. Shared support reconstructs physical/reference package documents across comparisons; correctness and admission/reuse ownership should be settled before caching that test input. No timing claim is made.

### Native record-retirement correction relevant to F05

`native_operation::pinned_generations` locks each record, verifies drain, and unlinks settled operation/lock records unless matching registration or a foreground-parent association still owns the proof. Unknown records conservatively refuse reclamation. Therefore original G-05's “settled records are not being retired” inference from a growing directory is false. A record census must distinguish live, pending, unknown and removable records. Per-command sealed-file verification and collection discovery remain separate opportunities belonging to F05/RC05; no entire-history lifetime conclusion should be imported from test_resources.
