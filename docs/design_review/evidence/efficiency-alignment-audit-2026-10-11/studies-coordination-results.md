## Decisive library correction: what FOR UPDATE means

The workspace declares SurrealDB =3.3.0, with its vendored SDK patch and protocol-ws/rustls features. The configured server is v3.3.0 and `scripts/surreal_server.py` selects RocksDB with `sync=every&versioned=false`. This establishes the configured deployment, not an observed version handshake against a running process during this inquiry.

Context7's SurrealDB documentation describes FOR UPDATE as a registered commit-time conflict read, not a blocking/exclusive reader lock. Pinned local implementation agrees (Cargo.lock resolves surrealdb-kvs, surrealdb-kvs-rocksdb and surrealdb-core 3.3.0): `surrealdb-kvs-3.3.0/src/api.rs::Transactable::getu` requires that no committed write occur to the registered key after the transaction snapshot; `surrealdb-kvs-rocksdb-3.3.0/src/lib.rs::getu` uses optimistic `get_for_update_opt` against snapshot read options. The pinned core test demonstrates retryable reader commit failure after a concurrent writer, and ordinary SELECT lacks that additional protection. Upstream reference: [SurrealDB v3.3.0 select_for_update_test.rs](https://github.com/surrealdb/surrealdb/blob/v3.3.0/surrealdb/core/src/kvs/tests/select_for_update_test.rs). Exact record targets, including named absence, matter; this is not a predicate/range-lock facility.

Thus two transactions registering the same unchanged record and writing disjoint other records do not conflict merely because both used FOR UPDATE. Original D-P1 is not a necessary prerequisite for selecting the read-register-cancel-row/write-cancel-row variant on this pinned backend. The current shared writes, local exclusive pacing and retries remain real. Say “registered read conflicts with a committed write,” not “exclusive read lock” or “no shared lock mode” as a reason readers must serialize. Other backends/releases need their own qualification. The vendored finite request/session/drain patch does not alter this datastore concurrency contract, nor does closing a socket prove remote effect settlement.

## Positions on original findings

### F08 — shared serialization: diagnosis upheld; remedy requires a complete protocol

**Diagnosis.** `canonical.rs::ProblemTurns::run` assigns Mutation an exclusive per-problem RwLock turn; `CanonicalStore::protected_query` holds it across definite conflict retry/backoff. `PROTECTED_BEGIN` registers the shared retention record. Acquisition/release, result opens/renewals and lifecycle transitions write that record. `canonical_execution.rs::protected_execution_query` separately resolves the immutable run problem on every call because AttemptFence omits it. Generated execution `writer` touches the study guard through `study_cancelled`, as do study claim/observe/finalize paths. A result open also runs `available`, which touches the execution-run guard, before installing result protection. This means opening and renewing results creates real shared writes, not just harmless registered reads. Heartbeats execute writer checks and mutate the attempt lease; their study-wide conflict participation must be included, not only result appends.

**Correction to consequence.** Same-process Mutation decisions really serialize. Across processes each actual common guard write can invalidate overlapping registered readers; it does not abort every transaction unconditionally, and reader-reader registration alone is not the cause. Repeated hashing/preparation and numerical costs must remain separately assessed. Plan 28e failure history was not reproduced here.

**Corrective contract.** Split cancellation, source retention, result retirement, execution ownership and local pacing domains by the actual premise that can change. Register an exact cancellation row that cancellation actually writes; preserve immutable point-to-study association and named-absence/new-association races. Removing only the writer's touch leaves study dispatcher/settler shared writes. Carry problem in the checked AttemptFence and pace run/attempt writes locally. Backoff outside local turns only on definite typed transaction conflicts, under the original absolute deadline; never replay an uncertain application mutation.

Source reclamation needs both commit orders: creators register/check the reclaim fence and reclaimed intervals, create their durable root/pin, and write a creator fence; reclaim registers that creator fence before scanning roots/pins and writes the reclaim fence. Existing-pin renewal must prove the exact live pin and cannot resurrect an expired/released pin; reclaim registers the affected pin rows or equivalent stable authority. Reader registration and pin renewal alone do not settle phantom creation. Result pin creation/retirement must receive the analogous exact run/attempt/manifest protocol independently of source roots. Existing analysis creation closed-through watermark and authority-incarnation rules must survive any guard replacement.

Cancellation is serial-order semantics: a committed append before cancellation can remain in the retained prefix; append/renew after acknowledged cancellation must refuse. Joined native work and a complete export racing cancellation retain their original assessment under the declared cancelled terminal outcome; partial export cannot become usable science. “Cancellation wins against late appends” must not mean erasing a valid earlier committed append.

**Preserve.** Original operation clocks, exact roots and positive/absent/membership premises, live-pin refusal after expiry, independently retained copied Arrow arrays, claim/lease/generation fencing, uncertainty receipts, recovery without numerical rerun, joined renewal/drain, and named absence. An A-inquiry study engagement may reuse an owned protected basis only within these rules; it is not cached publication permission and must stop admitting new points on renewal failure while owning issued/uncertain work through drain.

**Priority.** High for concurrent durable studies and concurrent readers. Protocol design precedes implementation; no need to delay that design for D-P1. Performance magnitude remains unmeasured.

### F09 — repeated discovery and round barriers: diagnosis upheld; arithmetic and readiness simplified

`worker.rs::work_once_scoped` starts study/candidate traversal at the beginning for each call. Indexed candidates exclude settled/assigned points, but not predecessor-waiting points, and each candidate costs `study_scope` before policy Wait/Reconcile. `serve` latches Idle and stops refill until pending lanes drain. `finalize` writes the study guard before checking that unsettled points remain; finalization then rereads individual point records for fields a page can project. These mechanisms are concrete.

The exact `(w−1)N²/2` scope-read formula and ten-million example are not guaranteed by source alone: concurrent ownership suppression, scheduling, candidate visibility and idle latch affect repeated traversal. Keep it as a workload hypothesis, not a source-established count. An empty-table EXPLAIN confirms neither populated selectivity nor skewed workload behavior; the composite candidate index exists, but current populated execution was not observed.

A maintained readiness frontier/counter is sound as a discovery hint, with authoritative pure `study_policy` and claim rechecking exact predecessors, retry eligibility, seed availability, refusal/cancellation and recovery. A boolean “ready” is insufficient unless those transitions invalidate/re-establish it. Continuous refill and a read-only pending check before the authoritative guarded finalizer address independent causes. Single-successor session/seed affinity can reduce storage preparation and seed rereads, but must be bounded and migration/restart-safe; it is not guaranteed affinity with multiple workers.

Preserve ordinal result placement, cancellation, claim ownership, recovery settlement and exact seed lineage. Priority High for long continuation chains; measured count/latency and relative priority against F11/F12 remain open.

### F10 — resource grain: uphold the five mechanisms with separate remedies

(a) Native job admission is immediate `try_acquire_owned`, including queued-session entry, while CPU admission can wait. Durable width is capped by both cores and jobs/2 and a lane covers preparation through publication. Stage-separated admission can improve use independently of completing F08; the original “benefit only once F08” is too strong. Blindly changing all try-acquires to waits is unsafe: idle native sessions retain job permits and native subwork may need another permit. Specify session/population/job ownership and ordering to avoid all lanes waiting while holding the resource each other needs. Bound population and retained prepared state; retain original deadline/cancel/drain semantics. Priority Medium–High depending measured idle time.

(b) `PreparedFit::start_owned` charges profile width and memory for the entire fit, while estimation is serial and profiles later use multiple workers. This mismatch is real; fair many-permit waits can obstruct smaller work. Do not let several fits each hold estimation permits while blocking for additional profile permits: release/reacquire at a safe phase boundary, or make profile chains independently admitted jobs with retained-state memory still charged. Numerical/covariance/profile semantics remain unchanged. Priority Medium.

(c) Fresh workspace reserves 4 GiB; non-flat compilation lacks a finite selected bound and uses the 8 GiB worker fallback. These are current accounting policy, not measured allocations or guaranteed peak foreign-heap bounds. They can raise retention pressure and evict warm state. Demand accounting can distinguish hard cap from charged live allocation, but construction, stack, foreign scratch and unknown-provider allocations need honest pre-allocation protection. “Incremental accounting” must not permit an uncharged allocation followed by retrospective reservation. Priority Medium; actual object/population sizes are unknown.

(d) `implicit.rs::Problem::new` captures `faer::get_global_parallelism` and uses it for factorization/scratch instead of the admitted scope. Context7 and pinned local `faer-0.24.4/src/lib.rs::{Par::rayon,get_global_parallelism}` plus `faer-0.24.4/src/sparse/linalg/lu.rs` support the mechanism; default Par::rayon(0) resolves the current Rayon pool width. Do not universally say “logical CPUs/global pool”: environment and a caller-installed pool can differ. Carry explicit admitted Par, preserving deterministic/numerical checks and scratch accounting. Materiality depends on factorization path/size, particularly supernodal dispatch, and is unmeasured. Priority Medium/conditional.

(e) `SelectedCollection::push_ref` creates an unspillable result:row-copy consumer per row; ReleaseNotifyingPool unregister always notifies all waiters. Batched/chunk consumer ownership is a sound opportunity. Correct the blanket “notify only on actual byte release”: pinned DataFusion 55.1.0 FairSpillPool divides capacity among spillable consumers, so unregistering a zero-byte spillable consumer raises others' allowance. Keep nonzero shrink and allowance-changing unregister notifications; suppress only departures proved irrelevant to admission. Context7 plus [DataFusion 55.1.0 pool.rs](https://github.com/apache/datafusion/blob/55.1.0/datafusion/execution/src/memory_pool/pool.rs) support this distinction. Wake-storm magnitude is unknown. Priority Low–Medium.

### F11 — scalar metadata dictates publication: diagnosis upheld; descriptor remedy corrected

`result_projection.rs::scalar_cells_at` emits the stated per-field cells; `result_export.rs::store_result_chunk` runs metadata_prefix against the 128 KiB index metadata bound before the 512 KiB payload limit. The empty path encodes schema-only IPC, and store_result_table requires at least one ordinal. Each append has its operation receipt and current two-RPC routing. The cells have five indexes including the unique key. Source supports amplification and unnecessary small/empty append crossings; tens-of-rows and exact RPC magnitude require measurement.

The current scalar-selection route fixes relation/owner/field/partition and verifies scalar selection against decoded original rows. It is not a demonstrated general cross-output query workload. Selection identity, IEEE bits/signed zero, finite/missing distinction, original row coordinates, attempt boundaries and Arrow admission must survive physical-index changes.

The existing coordinate_min/max are optional finite Float64 coordinates represented with exact bits plus a projection, used for trajectory time. They cannot safely hold an arbitrary typed composite primary key. Use a new typed exact key-bound contract or one exact row locator, with a defined ordering/comparison and decoded-row verification. Do not require a global resort without proving consumer ordering/range compatibility. Dense symbol grouping must preserve output ranges/time identity. Declared empty sets belong in acknowledged close/manifest membership; no append must never mean empty before close. Multi-relation append can retain per-block bounds and total message preflight. A new cross-output Arrow/DataFusion feature is an optional separate capability, not prerequisite evidence for replacing this index.

Priority High for small repeated solves/studies; protocol for empty declaration/coverage and selection correctness is prerequisite. No measured storage or throughput savings.

### F12 — completion rereads: diagnosis upheld; distinguish missing accumulator from held acknowledgments

`Operations::settle` reconciles pages of server batches, stops and joins heartbeat, seals, then calls record. `record` fully opens a protected result, reads completion chunks and renews for seed inventory pages. NativeStoredResult usable/completion/diagnostics each invoke this again. `closed_response` also reads closure_operation after successful close. These crossings are structurally redundant in the fully acknowledged normal path, while readback is necessary after uncertainty/restart.

The writer validates compact append acknowledgments but store_result_table discards them; it does not currently hold a complete acknowledgment set. A proposed accumulator can retain bounded keys/digests/counters/coverage, not duplicate every payload. The final server check must cover all advertised result sets, completion, progress/seed coverage and exact close authority, not just guessed local totals. Removing closure_operation requires the successful close acknowledgment to return the same authoritative recovered/closed authority the caller needs; attempt.generation is not automatically the closure authority.

A cached immutable completion also needs an explicit ownership contract. Current key-only handles reopen and refuse retired/reclaimed records. Keeping unpinned completion forever changes that behavior. Choose an owned copied-snapshot API deliberately, retain an exact live result pin and revalidate renewal, or provide a slim protected completion-only read; avoid seed enumeration when only completion is asked for. A terminal bulk page can reduce crossings but still obey retirement and memory admission.

Early scientific return before durability is optional and changes the current “acknowledged stored completion, never provisional success” rule. It is not needed to remove readback. Any opt-in must expose independent persistence state, keep publication/uncertain settlement owned through drain, and prohibit durable study facts/seed readiness before acknowledged terminal admission. Priority High for interactive return and result-handle scans.

### F13 — full detail/live history: uphold study/horizon diagnosis; extend the retained-state inventory

Durable store_tables publishes all table_ids; study request has no output demand. Ephemeral study_inner retains all `Arc<RunResult>` until returning a StudyResult whose public report consumers expect full occurrence reports. Full-detail retention therefore is a real contract, not a detail that can silently be dropped. Add explicit demand/compact-result semantics, preserving a declared full-detail path and mandatory outcome/diagnostic/PS-10/provenance information. Failed/flagged detail policy must be explicit, not unbounded by accident.

Horizon Loop retains every prepared request and result, all measured samples, all applied-input history, step reports, and indexed accepted/estimate/background references. In addition, `workflow/staged.rs::Staged::record` retains a `Vec<Record>` cloning every scalar-value map and native warm start. Streaming only Loop vectors leaves that live history. Staged::seed(Start::Accepted(index)) and predecessor_at(index) support historical index access for other sequences, so a bounded horizon-specific role-state owner or explicit release contract is needed.

One horizon can remain one run/attempt: stream private append-only per-step blocks under its ingestion fence, freeze/close/seal the coherent final manifest and preserve partial failure/cancellation truth. Retain last accepted result per role (possibly older than the latest failed step), current estimator, advanced background result/factor, priors/anchors, MHE rolling measurement/input window, exact candidate permission and seed provenance. Small step outcome/index history may legitimately remain step-proportional while large values/seeds/results become bounded. No resumability or per-step independent success is implied by streaming.

IDAS sensitivity demand and interpolation claims require inquiry C's independent capability/consumer assessment; not qualified by this B report. Priority Medium–High for long horizons/large sweeps; demand API, streaming coverage and live-state ownership precede implementation. No numeric peak bound established.

### F14 — telemetry affects execution: diagnosis upheld; avoid inventing another guaranteed stream

Progress::push taps before local bounded retention. Durable Tap tries a bounded channel; a synchronous native producer outside Tokio can block up to the heartbeat interval, while an async-runtime producer refuses overflow immediately. Overflow cancels and Streamer::finish reports admission failure. Progress append uses the same current mutation/fence path. This is a concrete solver-to-storage-latency coupling.

Do not describe every affected solve as already scientifically sound: overflow can occur before independent assessment completes. It is nevertheless an operational diagnostic failure causing scientific execution interruption. Numerical adequacy and durable transport failure must remain distinct.

Sample/coalesce iteration telemetry with exact drop/partiality counters, retained ordering/timestamps and bounded accounting. Mandatory terminal scientific outcome and seed permission already have completion/seed lifecycle authority; a new “guaranteed small phase/failure/terminal channel” is not automatically small, necessary or independently authoritative. Identify required event consumers before creating it. An explicit strict-audit telemetry policy may choose interruption on loss; it must be declared independently of the ordinary scientific-result contract. Preserve hard work limits and cancellation responsiveness without deriving them from sampled events. Priority High for store-contended native studies; no measured stall distribution.

### F15 — residue: diagnosis upheld; deadline-only deletion unsafe

collect_run deletes scientific result/index payload but leaves execution operation receipts and execution-operation guards. Released source protections remain tombstones; result protections also have retained bookkeeping. Range-based protection checks include retained historical rows. These are current growth mechanisms; exact protection count per point, scan cost and storage lifetime are unmeasured.

Release deliberately upserts a tombstone even when acquisition has no visible row: `canonical.rs::release_protection` documents the submitted acquisition that can outlive its failed local response. Deleting after merely observing expires_at or a wall-clock acquisition deadline can allow an older snapshot/in-flight acquisition to commit after deletion. Current rows do not by themselves encode a settled original immutable acquisition grant.

Collection requires retirement/replay authority covering all commit orders, an immutable grant deadline and settlement/closed-through authority or equivalent fence, plus exact-key registration for absent creation. The existing analysis-creation settlement design in blueprint §20.4 supplies a useful pattern: registered creator/header conflict, monotone closed-through floor, no renewed key grant, incarnation retained across restore. A timestamp wait alone is not that protocol. Likewise receipt collection must prove a retired replay fence precedes/remains visible to all late operations and preserve run-level lineage and required lost-ack settlement. Periodic compaction without lifecycle authority does not fix unbounded obligations.

Priority Low for short-lived fixtures, Medium for long-lived high-publication stores. Design lifecycle eligibility and settlement before any deletion; the audit authorizes no production cleanup.

## Additional candidates

### B01 — one selected durable seed is reopened and decoded repeatedly

**Falsifiable cause.** `durable.rs::latest_seed` calls seed(solution) to admit it but returns only SolutionId; `run.rs::with_stored_start` then calls seed again. Each `seed_document` opens read_results and separately calls record, which opens a second protected result and scans seed inventory; chunk reading renews and decodes the selected payload. prediction(solution) calls seed_document again, decoding warm bytes even when the caller needs portable prediction. This is not merely a property-handle reread and persists if F12's post-seal tail alone is fixed.

**Workload/consequence.** Durable continuation or explicit Latest warm start with a substantial warm/prediction payload; repeated result opens, retention mutations, inventory reads and decoding on the critical path and overlapping temporary live objects. Ephemeral same-process continuation can hand off owned seed data and is contrary evidence that the repeated store roundtrip is semantically inevitable. Magnitude unmeasured.

**Standard/source.** AP-07, DP-10, H12/H19; PS-11 requires exact compatibility/permission. Sources `workflow/durable.rs::{seed_document,seed,prediction,latest_seed}`, `workflow/run.rs::with_stored_start`, `workflow/study.rs::{prepare_study_candidate,prediction_sample}`.

**Correction/preservation.** Return one owned admitted seed object containing immutable header, selected warm payload, optional prediction and exact completion permission/lifetime; pass it through discovery/start/prediction. Slim completion-only read can avoid inventory. Bound worker/study reuse by exact attempt, seed identity, compatibility, original clock and live ownership; do not cache stale store permission. Preserve bit-exact payload, retirement refusal/lifetime contract, scientific candidate permission and result start provenance.

**Verification.** Trace/counter a compatible selected seed through discovery/start/prediction: count protected opens and payload decodes, confirm one owned admission rather than repeated complete reopen; compare exact seed/preparation/attempt provenance and starts. Also expire/retire before subsequent independent use and require the declared refusal/snapshot semantics. Proposed, not executed. Priority Medium, compatible with F08/F12 and A engagement.

### B02 — bounded pre-eligibility seed discovery can falsely refuse an explicit Latest start

**Falsifiable cause.** `canonical_execution.rs::result_seed_candidates` returns only LIMIT64 ordered by run_sequence/attempt_generation/step, excluding retirement but not nonterminal attempts and with no cursor. `durable.rs::latest_seed` filters terminality after that cutoff and returns None when all returned candidates are nonterminal. It cannot establish exhaustive eligible absence.

**Supported workload/consequence.** `ModelingSolvePreparation::with_stored_start(..., StoredStart::Latest)` is a public supported caller. Its documented newest-compatible selection returns the contract error “no retained seed matches preparation” on None. A newer compatible multi-step run exporting at least64 seed headers before terminal seal can temporarily mask an older sealed eligible seed. This explicit Latest request spuriously refuses available reuse. This is not a mandatory study-predecessor example: study continuation supplies Some(exact predecessor attempt), so cross-attempt masking does not apply there. A caller intentionally choosing cold fallback would instead lose warm reuse; no false scientific success is alleged.

**Standard/source.** AP-02/AP-05/AP-07, H5/H10/H12, G5 consistency of discovery/absence, PS-11 exact seed eligibility. Sources above and `workflow/run.rs::with_stored_start`.

**Correction/preservation.** Page deterministically to an eligible terminal occurrence under the original absolute deadline/cancellation, or atomically expose an eligible header at terminal admission. Distinguish exhausted absence from incomplete discovery. Keep compatibility, retirement and independent scientific admission authoritative. Do not swallow corruption/infrastructure/incompatibility errors or make unsealed prefixes reusable. Define tie/cursor ordering explicitly.

**Verification.** Isolated canonical fixture: retain one older sealed compatible/usable seed, then append64 newer compatible seed headers without terminal seal; explicit Latest must select the older seed or explicitly report incomplete discovery, never exhaustive absence. After newer seal it should select the newest admitted occurrence. Baseline source predicts None before seal. No fixture was created or run. Priority Medium functional correctness; exact fixture scientific admission must use existing helpers, not fabricate usability.
