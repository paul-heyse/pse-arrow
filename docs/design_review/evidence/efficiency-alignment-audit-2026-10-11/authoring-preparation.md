## Independent operation model

The useful distinctions are authored structure, numerical coordinates, variable state, admission premises, immutable mathematical products, mutable attempt state, and canonical eligibility. They already have meaningful owners. The problem is that several user operations compose those owners at an unnecessarily short lifetime.

An interactive Python source edit calls complete replacement. `with_declarations` first reloads the old inventory/data and reconstructs document metadata; `persist` validates/frames/extracts references over all submitted rows, derives data suppliers, and only then computes the store delta. A changed consumed row invalidates selected admission/basis premises. Declared-case preparation obtains the fixture through one full preparation, and `resolve_case` performs another preparation after extending demand. Equal body and view identities recover substantial mathematical reuse after that work.

A warm stored study point follows a different route: the revision is fixed and compiler products can hit, but the point reloads source/context, establishes fresh protection, adopts/rechecks selection and settles descriptions again. Per-point scalar binding and new numerical checks are necessary; repeated canonical establishment of the same study inputs is the avoidable part.

Runtime qualification is not one undifferentiated check. Python construction observes outer checkout context and establishes a local replay observation. A preparation that needs eligible persisted acquisition/publication qualifies that observation. A fully acknowledged preparation does not rehash the process. Managed-primary selection/readiness verifies another executable/receiver boundary. Native-cache preparation verifies a generation once per real operation and remembers it within that operation. Each boundary needs its own preservation argument before widening its validity lifetime.

## Positions on original findings

### F01 — Confirm diagnosis, improve contract and correct the start/bound uncertainty

**Diagnosis.** The examined Python interactive surface exposes `with_declarations`, a complete replacement; it does not expose an overlay solve over an unchanged selected preparation. In `declared_execution`, fixture values are recovered from the specialized model; in `resolve_case`, the changed consumed revision reaches structural preparation before the existing cheap bound-view rebind. This violates the functional target and AP-07. DP-09 itself requires structural/value separation; the issue is not merely an unmet PS-11 SHOULD.

Qualify the language: a new revision does not automatically invalidate all selected products. `qualified_selected_candidate` can recheck exact dependencies across revisions and adopt an unchanged closure. The defect concerns value edits to *consumed* authored inputs. A no-op replacement can return the old revision; an unrelated out-of-closure edit can reuse selection/basis. These are real strengths.

**Resolved field semantics.** `admit_overlay` accepts finite, physically typed assignments only to `PreparedModeling.admitted.inputs` whose symbol role is Variable or Parameter. It does not accept arbitrary internal/eliminated coordinates. `prepare_bound_operation` assigns admitted values to `execution.analysis.case.members`; `resolve_starts` applies these after default, predecessor, named case and continuation values, before unresolved start annotations. Thus it can replace a free variable's start and a fixed variable's coordinate without changing fixed/free status, as well as parameter values. Direct lower/upper/fixed state is not representable in `PointOverlay`; `variable_states` separately interprets bound hints and `case.variables`. Parameterized bound hints may change *indirectly* after a parameter overlay. This should not be described as direct bound-edit support.

**Corrective contract.** Expose numerical binding over an admitted parent and reuse the existing physical/target admission and value rebind. Keep the roles explicit: start, parameter/fixed coordinate, and variable-state edit have different downstream dependencies. If direct bound/state editing is part of the desired interactive API, compose the existing variable-state operation rather than pretending scalar assignment expresses it. Structural literals, membership/shape, discretization and fixed/free changes must invalidate the products that consume them; equality of resulting body or view keys may still recover downstream reuse.

Results must identify parent source revision, exact admitted overlay identity, physical/context and start/seed dependencies. Overlay identity deliberately excludes spelling/unit attribution and is not by itself globally sufficient: `AdmittedBinding` separately holds revision/context, and `OperationSource::check` enforces the association. Reopening the unchanged parent must not silently acquire the transient overlay; an explicit source commit or durable named case records that change. Ordinary edit-and-solve should provide clear lineage without requiring users to understand cache mechanics.

**Priority/prerequisites.** High by direct target consequence. The value route does not depend on incrementalizing the checker or choosing Salsa. A shared engagement helps but should not become a prerequisite for exposing an otherwise correct value binding.

### F02 — Confirm diagnosis; correct the unsafe reference-update prescription

`full_source` hydrates modeling rows, physical scopes, all document data, packages and fits. `with_declarations` discards the old modeling rows and fit batch, retains document/source ownership and clears obsolete source-text/spans. `persist` validates a full row batch, computes source identity, parses source references for every row, serializes/hashes edits, derives data suppliers through a fresh compiler when data closure exists, and scans prior membership before discarding unchanged edits. Python additionally structures/unstructures and encode/decode/encodes whole declarations. `from_documents` actually invokes `load_package_documents_owned` on every bundle and `modeling_from_documents` persists without a previous revision, minting a new problem. This is broader than the changed input requires.

A delta ingress owner should consume an exact parent and changed/added/removed declarations or documents. It should preserve unchanged object versions and derived data, reparse changed documents, and preserve problem lineage on an explicitly requested reload. The old complete-replacement API may remain a deliberate bulk operation during transition, but cannot be the only efficient edit intent.

**Material correction to F02's remedy:** it is unsafe to recompute references *only* when name/parent/kind/import changes. `SourceIndex::references` parses expression occurrences, structural/type paths and textual requirements including dataset targets, entity kinds, bases and provenance. Changing `eq e:x==a` to `eq e:x==b` changes references without changing any listed namespace field. Re-extract references for every changed row whose reference-bearing fields changed; then invalidate/re-resolve other rows when additions, deletion, shadowing, import, parent, kind or relevant namespace/membership changes can alter their lookup. Failed lookups and duplicate/cycle witnesses are dependencies, not optional metadata. Data documents or dataset declarations can change `record:` suppliers even with stable member names.

Source-revision identity derivable from member versions is a possible *new versioned frame*, not a free optimization. Define semantic versus representation identity carefully: current member versions also frame serialized payload/reference information and source attribution. Preserve the current meanings, or explicitly migrate/version the changed meaning; do not claim a Merkle/hash composition necessarily preserves the current revision identity.

`SourceIndex::data_closure` also scans `self.rows` for same-name siblings and imported roots on kept items despite indexes; this is supporting evidence within F02, not a separate new finding. An index-based route must preserve duplicate detection and lexical resolution.

Preserve no-op return, exact parent/CAS, unrelated objects and deletions. In particular current complete modeling replacement only deletes omitted `modeling:`, `record:` and `physical_scope_document:` members; fit/data ownership persists through the parent. A delta implementation must not reinterpret an absent fit/data object as deletion.

**Priority.** High for interactive work with data/libraries. Do the edit-intent/affected-input correction before an ambitious incremental checker; performance magnitude is unmeasured.

### F03 — Confirm the two calls; correct unconditional duplication and strengthen engagement semantics

`declared_execution` invokes `prepare` with default analysis bindings. `resolve_case` invokes `prepare` after extending demand with `case.values` and `case.variables` paths. Both calls and their canonical effects are real. However, their `BasisKey`s differ only when demand differs; an empty/already-covered fixture demand may give an exact basis hit. Do not say every solve always rebuilds two distinct bases or performs two receiving qualifications. The second call still establishes current protection/settlement even on a hit.

On a selection miss, `checked_selection` searches retained candidates before and after acquiring the qualification turn. A long edit history can therefore repeat dependency RPC windows, bounded by retention rather than a fixed number of historical candidates. This supports F03's history cost, without assuming unbounded growth.

Compute the final demand before full executable preparation, or obtain fixture semantics through a non-executable preparation and complete once. Raw authored fixture names alone are not proof that resolved fixture values and paths are available before specialization: `declared_execution` currently consumes the specialized fixture. The correction must preserve physical literal conversion, instance/path resolution, policy and applicability. A semantic-only specialization can be a useful first stage; it must be shared with completion rather than silently introducing another complete specialization.

The engagement direction is sound if it is an operation owner, not a cache permission bit. It must carry exact problem/revision, complete acquired dependency delta, root/instance/bindings/limits, physical/provider and validation/registry context, live protection and completion/settlement state. `SelectedRequest` and `BasisKey` already retain EngineFactory/Registry owners and compare their identity. Preserve that lifetime contract when coordinating with F23; source identity alone is insufficient.

Renewal must validate an existing non-released, non-expired protection and must not recreate it. Failure stops new admissions; issued effects and uncertain acknowledgments keep their original completion owner/clock through drain. Idle engagement state must be bounded/evictable; no source protection, compiler workspace or mutable evaluator should be kept alive merely because a disconnected UI once prepared a model. Source/run roots and engagement pins are distinct lifetimes.

Batching the union of candidate premises is a promising access improvement, but perform bounded windows with early mismatch handling and merge only premises of the accepted candidate. Resolving every historical union unconditionally can increase live state and examined work or lose today’s early rejection.

`prepare_flow` does instantiate an uncached semantic workspace; its call frequency was not established. Keep it as a covered opportunity rather than treating unknown use frequency as equivalent to the demonstrated double declared-case path.

**Priority.** High shared correction; the exact engagement/publication contract precedes any removal of canonical checks. Removing the redundant full preparation is independently useful.

### F04 — Confirm body-times-premises amplification; prefer decoupling payload from eligibility

`ProductDescription::prepare` snapshots the whole `SelectedRead`, serializes its complete premises and builds a payload-plus-premises blob. `matches_read` requires exact equality across Name, Scope, Interpretation, Logical, KindScope and References premises. A consumed change therefore invalidates descriptions for unaffected mathematical bodies. `settle_preparation` processes portable bodies sequentially and is awaited before returning. Changed descriptions reframe/re-stage body payload together with selection evidence.

The defensible growth claim is B copies/encodings of a P-sized premise set and repeated admissions for a change that can leave most mathematical payloads equal. Roughly quadratic growth requires B and P to grow together; that is a credible large flowsheet scenario, not a universal size law. Body payload sizes and actual transferred blocks remain unmeasured here. Different frame/domain hashes may establish distinct identities; their mere multiplicity is not proof of identical assurance. Sharing one exact dependency encoding is sounder than deleting distinct identity roles blindly.

The first correction should separate immutable payload identity/content from current selection eligibility and reachability. Keep one encoded full selection receipt under its owner initially, and have individual body records/reference roots refer to the shared content and receipt. An exact mathematical body's `SemanticBodyHash` can establish substitutability of that body; it does **not** automatically establish that the selected source is still admissible, all namespace absences remain absent, or publication permission is current. `grouped::plan` frames normalized expression, physical identity, formals, hints/validity, function identities and provider descriptors. This is strong evidence for mathematical content reuse, not an inspected completeness proof for whole-selection admission.

Consequently, narrowed per-body acquisition premises are optional further design work. They are not necessary to remove repeated payload bytes/encoding, and should not be a prerequisite for solving F04. Require an exact owner/projection argument before deleting absence/membership premises. A separate numeric kernel cache does not license skipping lexical selection checks.

Settling once per engagement can be compatible with this separation. Moving settlement off the waiter's critical path changes observable completion/durability semantics and must be explicit. Preparation success, publication eligibility and acknowledged persistence may be separate outcomes; a background owner must be bounded, retain payload/receipt allocations and protection until its issued effects settle, and have a cancellation/uncertain-commit argument. An ephemeral solve may omit optional reusable-product publication under an approved changed contract; it still requires source admission and whatever result policy it promises. “Ephemeral” does not by itself prove no canonical obligations exist.

Reclamation and root creation need both commit orders protected. Inquiry B independently identifies that root/pin creators must join the reclaim conflict premise and recheck reclaimed state, while reclaimers register creation fences before scanning and register affected existing pins. A longer lease alone does not close creation/reclaim phantoms. Never turn an old rooted acknowledgment into permission to create a new eligible root.

**Priority.** High for edits/studies with many bodies. Correct eligibility/content lifetime and settlement outcome first; scope narrowing later if justified.

### F05 — Confirm repeated observation routes; split assurance lifetimes, correct facts and limit stat claims

**(a) Preparation receiving qualification.** Confirmed: `qualify_replay` invokes `ReplayAdmission::qualify_receiving`, which recaptures current mapped ELF/configuration context through `LocalRuntimeObservation::verify_scoped`; each capture hashes exact paths once and independently verifies loaded paths at closing. It executes under the glibc loader scope. Triggering is per prepare needing a new qualified publication/acquisition, not every use; a matching acknowledged description skips it. Unqualified/no producer paths do not pay this observation, and strict producer behavior differs. Cache retention pressure can remove descriptions and reintroduce the work.

**Cancellation correction:** scoped file observation is already cooperative. `FileObservation::capture_scoped` checks before each 64-KiB read and before sealing; receiving qualification supplies the caller checkpoint. `qualify_replay` dispatches a completion-owned native job, cancels and joins it. The original blanket “FileObservation::capture is non-interruptible” conflates scoped preparation receiving with unscoped native-deployment/outer paths. Loader-lock acquisition and opaque initialization/configuration calls remain checked only around the call, exactly as the source documents.

**(b) Python startup/outer context.** Confirmed: `NativeRuntime::new` detaches shared-runtime acquisition, but `observe_deployment` itself executes while Python is attached. `observe_outer` reads the checkout source inventory and invokes Git. Local replay startup subsequently uses the detached blocking/native-job path. Do not imply the whole local capture is under the GIL. Outer checkout context is different from build-source provenance; changing the former to an executable identity or process-once observation changes what is reported. The checkout can legitimately change during a long process. Memoizing it forever without recording that it is startup context would silently stale the claim. A process-wide owned image observation plus explicit current/lazy checkout context is a better separation than simply relabeling one as the other. `source_files` also materializes all selected source bytes before hashing; no peak-memory magnitude was measured.

**(c) Managed primary.** Confirmed independent full-file verifications in Rust selection, Rust `require_current`, supervisor generation validation and worker matching/readiness. The ordinary already-ready route has repeated checks; exact 7–8 pass count is branch/environment dependent. Unscoped Rust file captures execute synchronously in the async startup path and lack the scoped preparation checkpoint. Content/runtime association, process identity/nonce, placement, receiver generation and storage database admission are distinct checks; preserve them rather than replacing readiness with a digest or stat alone.

**(d) Native generation.** Re-scope. `native_cache.prepare` explicitly verifies **once per real operation**, remembers the admitted generation, pins it before hashing, hashes outside publication coordination, and seals it read-only. This is already an owned amortization boundary, not hashing at every native use. Widening it across operations may be beneficial under a stronger manager-owned immutability contract, but the existence of one full check at a new operation boundary is not on its own proof of redundant assurance. Keep this manifestation lower priority/proposed opportunity pending the selected failure model and workload.

**Retirement correction:** `native_operation.pinned_generations` scans records, but it also unlinks drained operation records and locks when no pending registration or still-present foreground parent requires the proof. Unknown/malformed/unobservable records conservatively stop collection. “Settled records are not retired” is false as a blanket source claim. Inventory growth is not evidence that these records are safely disposable or that a retirement mechanism is absent. Diagnose specific retained obligations/unknown returns before proposing retirement.

**Remedy maturity.** Reusing established observation while premises hold is a sound goal. A stat tuple is a proposed invalidation detector, not a content certificate. The proposed tuple must also preserve mode, canonical path/link resolution, inode association of the *actual mapped artifact*, file/namespace additions/removals for generation manifests, `/etc/ld.so.cache`/preload observations and effective startup/current configuration. Timestamp precision is not guaranteed mutation uniqueness, and one `stat` can contain fields from different instants. Define supported filesystem behavior, racy-clean/fallback rules and an owner that excludes managed mutation through use. Atomic replacement generally changes identity; its possibility does not protect against same-inode writes or truncation. Hash-once-per-owner is strongest when bytes are actually immutable through a retained generation or kernel-backed mechanism, not merely labeled immutable.

The loader lock excludes supported loader publication/removal during its bounded callback, not arbitrary file writes or executable mmap/JIT. `RTLD_NOLOAD|RTLD_GLOBAL` can promote an already loaded object's symbol scope without loading a new file; glibc 2.39 `dl-open.c` has an explicit already-open branch that updates global scope. Thus counters plus map sets are not an exhaustive symbol-universe proof. The current whole-file rehash also cannot detect that scope-only change. This is an existing controlled-root premise, not a newly demonstrated scientific failure. Preserve the exclusion of unmanaged interposition or explicitly redesign admission for it. Do not sell repeated hashes as protection against an event they do not observe.

A late supported load currently causes comparison with the startup observation to refuse local eligibility, even when ordinary fresh mathematical admission remains possible. Automatically recapturing a changed image must issue a new admitted namespace/context or remain refused; it cannot silently renew the old identity. Actual late-mapping incidence remains a useful probe because it decides whether repetition or unavailable replay dominates the ordinary Python route.

Do not adopt mmap hashing merely as a faster equivalent without controlling truncation: accessing beyond a truncated mapped file can raise SIGBUS, unlike a typed streaming-read error. This is an optional implementation choice, not a new product finding.

**Quantitative correction/priority.** Original M1 and G-P3 measured isolated hot-cache full passes on large development artifacts. Preparation/study-start total seconds are arithmetic conditional on qualification, pass count and build; no full-operation totals or improvement were measured. F05(a–c) are material serial auxiliary work; ranking them equal to the missing interactive value route requires actual route/magnitude evidence. Priority should retain their materiality but avoid declaring measured end-to-end seconds. F05(d) and record-scan cleanup need separate evidence and owner decisions.

### F06 — Confirm repeated occurrence establishment; correct compiler/admission wording

`prepare_study_candidate` reads point/study, materializes physical context, reads revision, reopens package and calls `prepare_bound_operation`. That obtains a declared execution and then declared preparation. Each `prepare` acquires current protection and settles portable descriptions. Warm exact basis hits already avoid compiler rebuilding; call this canonical/input-lifetime amplification rather than structure compilation per point.

The stated approximately `25 + 2B` sequential crossings are a source-route estimate, not a measured invariant; demand equality, exact cache hits, seed/prediction branch and requested operation affect the count. The original blanket “DeclaredStudyAdmission is built twice and dropped” is also too broad: the inspected execution route does not build that object. `DeclaredStudyAdmission::prepare` is used by source/overlay and stored-binding admission and supports an `Option` owner reused while descriptor/path/member membership matches; values do not invalidate it. Per-ready-point `prepare_study_candidate` computes its descriptor key but constructs the prepared operation through the separate route. Preserve the existing admission reuse rather than rebuilding it under a new name.

A bounded worker/study engagement can retain the exact immutable operation and settled input basis. Each point still admits its binding/seed requirements, rebinds values, establishes current numerical/provider policy and produces a new independent assessment. Horizons may share the structural mechanism, but controller/estimator/horizon state, windows, arrivals, seeds and native sessions must remain under their actual sample/attempt owners. A single study protection is not evidence those changing states are stable.

Coordinate lease renewal/release with inquiry B's retention/cancellation protocol. The pinned revision is necessary but not the entire preparation key. No engagement may retain a reclaimed root through cached acknowledgment, resurrect an expired pin or release another worker's ownership. Its resources remain accounted until actual drain; immutable products may outlive it only with their own allocation owners and no publication authority.

**Priority.** High for many-point studies, with effect-lifetime contract as a prerequisite. The first correction can hold/reuse admitted input preparation without extending native mutable state across attempts.

### F07 — Confirm runtime cutoff gap and misleading backdating claim; reject “two caches therefore violation”

`MathService::workspace` creates a new `CompilerWorkspace`, and `CompilerWorkspace::with_events` creates fresh Salsa storage. The examined runtime source admission/planning/semantic paths publish the revision into fresh local workspaces; no examined production edit operation updates a previously held compiler database with the next authored revision. The monolithic `Catalog.checked` and checker outside tracked queries also mean merely keeping the workspace alive cannot make checking change-proportional. Backdating requires old memo state to compare against; pinned Salsa 0.28.4 source confirms that condition. Architecture §14.4's cross-edit wording and reuse table overstate what the public authored edit route realizes.

But the public compiler API genuinely supports publishing subsequent revisions, equality-guarded setters and memo rotation, with local memo reuse during a preparation. Detached retained basis/body products have a different allocation/lifetime and no retained source permission. Two mechanisms with overlapping vocabulary are not automatically a DP-09 violation when their scopes are explicit. The failure is unrealized promised cutoff, coarse affected-input modeling and machinery whose claimed across-edit role is absent in the examined runtime. Do not infer unsoundness or absence of all memo benefit from a fresh database.

A long-lived Salsa owner is viable only with a credible writer/concurrency model, per-declaration or appropriate selected-object inputs and explicit namespace membership/absence dependencies. Reads/writes/cancellation across concurrent solves and held historical revisions must be defined; a single writer per problem can introduce new head-of-line waits. Existing canonical requalification/protection is an effect owner that Salsa does not replace. Detached published/frontier/body lifetimes still need representation/retention; retiring `Selected`, `Frontier`, `Basis` and all flights automatically is not justified. Remove only what the chosen library owner actually subsumes, with unchanged A/B/A/absence/cancellation behavior. Salsa cannot memoize store eligibility or publication effects.

Plain functions plus exact keyed retention are the simpler alternative for current runtime lifetimes. Removing Salsa is not itself a demonstrated performance improvement and correcting the text does not fix F01–F06. An optional local accelerator need not be durable: “no persistent Salsa store” concerns process restart and is compatible with a long-lived **in-memory** database. There is no reason to turn this into a persistence project.

**Priority.** Correct misleading claims promptly. The incremental-checker/database decision follows the value route and canonical lifetime correction; its structural-edit benefit is unmeasured and requires more design than the original automatic cache-retirement prescription suggests.
