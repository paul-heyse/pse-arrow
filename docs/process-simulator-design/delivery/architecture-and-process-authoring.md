# Architecture and process authoring

Source: [Notion](https://app.notion.com/p/40b141b5836981c0bd38e4279a3d296a). Imported 2026-11-02.

[Implementation design and IDAES equivalence plan](index.md)

**Status: Adopted implementation architecture** · 2026-11-01. The source-reviewed basis is `pse-arrow` commit `19e7b49a67df24c1bf73005a6186e145e930d53a`. I01–I03 and I06 refinements are incorporated below. This is documentation adoption; scientific equivalence, assembled qualification, performance and implementation completion require their own evidence. No builds or tests were run for this update.

## 1. Recommendation and current starting point

Implement the adopted flowsheet domain by completing and exposing the repository's existing authored modeling system. The domain document should clarify the scientific responsibilities of that system and identify missing capabilities. It should not become a parallel set of persistent objects, a new universal intermediate representation, or a one-to-one list of Rust classes.

The current repository is substantially further along than a numerical engine awaiting its first modeling layer. Its declared architecture already makes authored typed process definitions authoritative, checks physical meaning before algebra, assigns symbolic mathematics to Symbolica/Numerica, keeps incremental preparation in `pse-compiler`, and gives numerical algorithms to their native libraries. Scientific units, thermodynamic functions, reactions, controllers and costing belong in authored packages. Canonical graph and relational state now uses SurrealDB; Arrow and DataFusion retain data, admission and inspection responsibilities. FeOS is an independent reference, not the production property implementation. The first-party product is linked Rust; an additional language binding or graphical application needs its own consumer justification. These are the baseline to preserve.[1](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/architecture-overview.md) [2](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workspace-and-dependencies.md)

Existing source makes the starting point concrete. `pse-modeling::specialize::process` already defines state specifications with independent coordinates, reconstructions, supplied-state status and transport observations; material ports alias those specifications; inventory balances retain inventory, flux, transfer identities, physical types and lineage. Coordinates are keyed by authored semantic slots and actual index values. These are substantial parts of the adopted process domain, already expressed over the existing semantic identities.[3](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-modeling/src/specialize/process.rs)

The next design task is therefore **a precise domain-to-implementation binding, a coherent process authoring path, and completion of the scientific package contracts required by the IDAES target**. The primary architectural test is whether another unit, property formulation, experiment or operating case can be added at the owner of its meaning without reproducing that meaning elsewhere.

## 2. Phase zero: settle the expanded target and repair its owning descriptions

The new user objective expands the accepted functional target. The current `docs/relationship-to-idaes.md` still explicitly excludes the example libraries, `models_extra`, apps and surrogates. It also names a `python/pse/parity` harness and a Python product boundary that conflict with the current Rust-owned architecture. That document cannot remain the authoritative description of a full-IDAES implementation programme. Repair its scope, reference execution description and links in the same decision that adopts the expanded target; do not silently reinterpret its exclusions.[4](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/relationship-to-idaes.md)

The repository principles binding also retains a sentence describing a Python authoring/result boundary. Reconcile that touched description with the scoped current architecture owner; it is not authorization to restore the retired product boundary or to reopen unrelated accepted decisions.[1](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/architecture-overview.md) [19](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/design_review/design_principles/binding/pse-arrow.md)

Record the intended equivalence as **scientific and functional equivalence under explicit formulation and operating-condition mappings**. It does not require reproducing Python class hierarchies, enum spellings or solver implementation details. Preserve the clean-room rule and the current `idaes-pse == 2.13.0` reference pin unless a separate decision changes it. The examples repository, datasets and external dependencies need their own exact revisions in the scope inventory; an IDAES package version alone does not identify an examples corpus.[4](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/relationship-to-idaes.md)

Full scope must be a finite, reviewable inventory of upstream families, operations and examples, with clear treatment of external-data, optional-library and deployment prerequisites. An item blocked by an unavailable prerequisite remains visible as blocked; it is not silently removed from the denominator. The binding between an upstream capability and the corresponding pse-arrow formulation should identify the scientific behavior being reproduced and the evidence needed to establish equivalence. Architectural prerequisites, scientific coverage and execution qualification are related but distinct work.

Use the existing decision and plan routes for consequential changes. Do not revive retired Plan 20 as a new backlog, change accepted ADR history in place, or absorb Plan 58h's assembled qualification and Plan 53's test-architecture obligations into an unqualified claim that this new plan completes them. The current design-change workflow explicitly distinguishes focused plan-foundation assessment from a broad diagnostic audit and keeps each active packet's status with its existing owner.[5](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/design-change-workflow.md) [6](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/plans/README.md)

## 3. Ownership map: bind the domain to existing responsibilities

The following is the adopted mapping of domain responsibilities to existing owners. It does not require a new table or runtime class per row; exact local data structures remain implementation choices.

| Process-domain responsibility | Existing implementation owner | Required contract |
| --- | --- | --- |
| Materials, species, phases, property/reaction definitions and parameter provenance | Authored physical/domain/science packages; retained physical context | Complete quantity conventions, selected membership, applicability, required data and formulation provenance |
| Unit definitions, control volumes, states, ports, balances, costing and controllers | Authored `.pse` interfaces, definitions, functions, contributions and instances | Reusable definition versus occurrence; explicit closure, transport and conservation meaning |
| Names, declarations, source edits and explicit dependency closure | `pse-authoring`, `pse-admission`, immutable `ModelingPackage` source ownership | Stable declaration identity, source attribution, typed admission and revision-aware edits |
| Process composition and scientific checks | `pse-modeling` | Generic physical and structural semantics; no dispatch on familiar equipment or chemical names |
| Selected finite formulation and preparation | `pse-compiler` with `pse-math` | Scope, applicability, original obligations, complete dependencies and lineage through lowering |
| Operating specifications, analysis requests and numerical settings | Existing case, preparation, solve/simulation/fit and strategy owners | Explicit role and bound provenance; separate scientific conditions, temporary initialization and numerical policy |
| Flowsheet inspection and connectivity | Projections over admitted declarations/semantic instances; existing flow selection/preparation | Topology distinct from equation incidence and execution decomposition; exact scope and identities |
| Studies and execution | `pse-runtime::workflow` and native backend owners | Local versus recorded effects, operation dependencies, attempt-owned native state and truthful outcomes |
| Product contracts and durable source/result boundaries | `pse-schema`/`pse-codegen`, native document owners, `pse-operations` | One schema authority, generated projections, exact scientific/source provenance and guarded publication |

These assignments follow the current workspace and schema contracts. Chemistry's species/phase/reaction vocabulary is authored; the kernel does not own a fixed scientific taxonomy. Likewise, old property-selection relations, instance/composition/connection relation families and compiled-mathematics relation families have been retired. Recreating them because the Notion domain contains similar nouns would reverse existing decisions.[2](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workspace-and-dependencies.md) [7](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/schema-and-relations.md)

The binding must distinguish declaration identity, reusable definition, instance, semantic scalar/member, immutable source revision, problem selection, study occurrence, run, attempt and artifact. Match contracts rather than labels: a conceptual “Run” in a design document is not sufficient reason to merge or rename existing run/attempt identities. Paths are useful attribution and selectors; they are not replacements for semantic identity.

## 4. The complete process authoring path

### 4.1 Author and admit one scientific source

Begin with a package manifest and explicit dependency closure. Authors select material/property/reaction definitions, instantiate unit interfaces, connect ports and supply operating cases. Textual `.pse` source and generated declaration values already share one admission boundary. Physical datasets may be authored or loaded from supported typed data documents; the immutable revision retains exact source and physical context.[8](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/models-and-composition.md)

A convenient process authoring API may construct existing declarations or submit typed source edits. Select the editing representation explicitly. `ModelingPackage::with_declarations` computes additions, replacements and removals by declaration identity and admits a new revision with the applicable physical context; it does not retain old document text as the editing authority of that revised IR. Text edits use the existing source/document route, while declaration edits produce an admitted declaration revision. Preserve source lineage and any supported rendering separately. Do not promise two synchronized authoritative representations or maintain a second mutable equipment/stream graph. Existing revision-aware source-delta operations supply the corresponding incremental edit path. [Source/edit owner](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling.rs).

For an editor, an invalid text buffer can remain a draft with diagnostics; it must not masquerade as an admitted, runnable model. Selection-specific readiness is also distinct from source validity: underdetermined cases can be inspected before requesting a solver. Existing case resolution deliberately separates numerical resolution and diagnostics from native solver routing.[10](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling/cases.rs)

### 4.2 Present a process view of that source

Expose a process-facing view containing selected unit occurrences, their public ports/state contracts, directed connections, selected component/phase sets, scientific configuration, operating roles and diagnostics. Every meaningful item should point to its existing declaration/instance/member identity and source revision. Presentation labels, grouping and layout may be separately stored, but cannot become an alternative source of physics.

Keep the three graphs distinct. A source topology view describes equipment and connections. Equation incidence describes selected equations and variables. A solve or initialization graph describes a chosen computational procedure. `ModelingPackage::prepare_flow` already prepares declared topology independently of numerical incidence, through `ModelingFlowSelection`. An authoring-facing source projection can expose lighter information before mathematical preparation when the requested information permits it; do not make every property-panel read compile or solve the plant.[8](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/models-and-composition.md) [9](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling.rs)

Preserve parallel connections, isolated units, nested compositions, direction and declared connectivity cardinalities. A material connection equates compatible independent coordinates and retains independent transport agreement checks; it does not blindly equate every property variable. Judge compatibility by the selected material membership, coordinate/transport meaning, basis, datum and receiving-state responsibilities. Incompatible or incomplete coverage must be diagnosed; an intended change of convention requires an explicit scientific translator, while mixing requires its own balance equations. Matching a package name is neither necessary nor sufficient. Compatibility for connection also does not establish substitution for every requested output, operating region or derivative order. [Composition owner](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/models-and-composition.md); [State and transport owner](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-modeling/src/specialize/process.rs).

### 4.3 Bind scientific questions without mutating the model

Build operating specifications and analysis requests using existing case and operation owners. The same unit definition may support rating, design, optimization, dynamics or fitting when its formulation and selected backend are capable. A design/free variable, specified operating value, physical applicability bound, optimization bound, measured observation and initial guess have different meanings. Preserve their provenance and reconcile their interactions explicitly.

Do not treat the five overall answer profiles as a new universal exclusive enum that replaces existing native operation contracts. Map each supported user-facing request to the relevant existing operation and keep composed studies explicit. A joint fit across multiple experiments may be one inferential operation; a sweep is a study of occurrences. A solver's initialization guess must not select a physical branch or change an operating specification by accident. Existing case handling already tracks typed start sources and immutable step overrides.[10](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling/cases.rs) [11](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workflows-and-results.md)

Classify edits before choosing reuse; these are meanings handled by existing owners, not a new runtime taxonomy.

| Edit | Owning consequence |
| --- | --- |
| Presentation-label rename | Preserve authored identity and references. A contractual state-slot role rename changes scientific meaning: `StateKey` includes that role and actual index values. |
| Numeric operating value | Rebind an already admitted demand with its physical type and source. A newly demanded path or alias requires admission and is not merely another numeric value. |
| Fixed/free role, topology or structural selection | Revisit the selected case layout and affected structural preparation; changing rating to design is not a value-only edit. |
| Method, parameter record, datum or formulation selection | Re-admit the actual scientific dependencies and applicability; never infer compatibility from a display name or reuse a stale coefficient copy. |

`declared_execution_with_demand` admits the required value paths before numerical rebinding. Private `resolve_case` remains an implementation owner, not an API that the frontend should expose automatically. Incremental edits must preserve the admitted meaning and selected observations of a clean reconstruction, while old immutable revisions remain interpretable. [Declared procedure/demand owner](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling/declared.rs); [Semantic state keys](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-modeling/src/specialize/process.rs).

### 4.4 Prepare, execute and inspect through existing owners

Selected configuration is specialized and physically checked before symbolic rewriting. Compiler preparation retains original-domain obligations, full dependency closure and source lineage. Keep symbolic and derivative work with the existing libraries. Backend selection is capability-based; a linked library does not make every problem eligible. Unsupported structure or derivative requirements must yield specific reasons, not a substitute formulation or hidden solver fallback.[1](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/architecture-overview.md) [2](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workspace-and-dependencies.md)

Numerical realization is separate from physical meaning even when both are authored in `.pse` syntax. A spatial approximation's selected stencil, mesh and tolerance belong to its realization contract and provenance; the physical control-volume law remains identifiable. This distinction does not require moving all discretization declarations into a new global IR. Retain the current compiler's formulation and lowering responsibilities and make their mapping inspectable.

Use the declared procedure surface according to its actual contract: `prepare_declared` accepts Solve; `execute_declared` executes Solve/Initialize but turns incomplete initialization into an error. The P1 failure-restoration journey must retain the full `ModelingInitializationReport` through `initialize_declared`, including stage and attempt outcomes. Temporary fixes, relaxed laws and tear values remain procedure-local; an accepted result must satisfy the restored original specification. [Declared procedure APIs](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/modeling/declared.rs).

Use the existing local-study route for exploratory work. `ModelingPackage::admit_study` retains the exact immutable model/physical inputs without initializing or contacting a canonical store, and `LocalStudy::execute` uses those owners. `LocalStudy` deliberately has no serialization contract. `Runtime::record_study` explicitly records the retained sources; recorded execution has its own durable contract. Compose these public choices rather than making publication a prerequisite for local calculation, serializing an internal study handle, or silently converting a failed durable operation into ephemeral execution. A failed operation can return diagnostics without implicitly recording them. [Workflow contract](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workflows-and-results.md); [Study lifecycle](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-runtime/src/workflow/study.rs).

Results should expose physical quantities and original-space checks separately from native termination, feasibility, conservation closure and scientific usability. A returned numeric vector or successful native code is not itself an accepted flowsheet result. The front end should retain these distinctions and the exact formulation/attempt provenance rather than compressing them into one success flag.[1](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/architecture-overview.md) [13](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/design_review/design_principles/profiles/process-simulator/principles.md)

### 4.5 External and procedural model boundaries

For a concrete external or procedural consumer, distinguish contributing residual equations, evaluating a requested input/output relation, and advancing a stateful model in time. The current provider boundary includes mutable attempt bindings, derivative demands and effect-sensitive completion; it is not universally pure, and a provider call does not establish co-simulation capability. A time-advancing integration must declare input interpolation/hold, accepted interval and output coverage, state custody, restart/restore, events, algebraic-loop participation and failure behavior. Repeated residual evaluation must not advance physical time accidentally. Keep external effects outside pure compiler reuse, and assess coupling error and conservation separately from each component's solver status. Select one real consumer and extend the current provider/runtime owner only for the missing contract; no universal adapter or co-simulation coordinator is part of P1. [Provider owner](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-kernels/src/provider.rs).

## 5. Registry, DSL and front-end exposure

There are two extension routes, selected by ownership.

**Scientific content:** add equations, parameter data, state definitions, package interfaces, unit configurations, controllers, costing and scientific eligibility rules in authored packages when existing language constructs can express them. Science vocabulary remains open and source-owned. A new equipment type is not automatically a new registry enum, a Rust constructor or a canonical table.

**A genuinely new generic contract:** extend the owning language/schema/operation once when an actual consumer needs a missing distinction. The registry owns product relations, fields, enums, identities, document mappings and their generated projections. The current modeling catalog explicitly describes itself as the sole durable kernel IR schema. Extend that authority and regenerate its Rust/Arrow/document/SurrealQL outputs; do not handwrite parallel JSON objects, database fields or frontend rules that repeat its meaning.[7](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/schema-and-relations.md) [14](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/crates/pse-schema/src/catalog/modeling.rs)

Discovery already has useful foundations: generated `reference.schema_*` relations expose schema/identity/document metadata, and `runtime.modeling_knowledge` exposes admitted package records. Native public-operation declarations provide typed request/result references, effects, receiver requirements and read lifetimes. Rust-owned boundary documents derive schemas from their serde types through schemars. These mechanisms should supply the frontend's structural contract; process-specific presentation is a projection over them, not a second schema authority.[7](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/schema-and-relations.md) [8](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/models-and-composition.md) [11](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/workflows-and-results.md)

A practical first delivery is a documented native process-authoring journey and coherent inspection/edit operations. A graphical editor, Python binding or universal CLI is not a prerequisite for scientific completeness. If a concrete frontend is selected, it should use the same admission and operation contracts and retain source-revision conflict handling. Do not build a new plugin framework merely to expose existing units.

## 6. Separate missing scientific content from generic capability gaps

The first implementation packet should map the adopted domain concepts and representative IDAES cases onto current declarations and operations, classifying each as already expressible, requiring package completion, requiring a generic extension, or requiring qualification. This is a compact extension map linked to its sources, not a second status ledger.

Two current gaps are explicit in source and should be treated as concrete design work:

- The authored zero-dimensional control volume rejects dynamic multiphase stored transport without explicit phase allocation. It also rejects stored element/total material bases without an inventory projection and transfer allocation. Completing those cases requires scientifically explicit inventory, transport and transfer semantics; simply removing the requirements would be incorrect.[15](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/packages/reference/process/models/control-volumes.pse)
- The authored one-dimensional control volume supports selected backward differences and Radau collocation but explicitly rejects dynamic use until it has a separate time-accumulation closure. A full distributed dynamic target therefore requires time-and-space accumulation semantics, consistent initial/boundary conditions, conservation evidence and an admitted numerical route. Existing spatial syntax alone does not establish that capability.[16](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/packages/reference/process/models/control-volume-1d.pse)

For further families—multiphase/rate-based separation, specialized reactors, multi-stream exchange, electrolytes, advanced property packages, surrogate-assisted workflows or application-specific optimization—derive the necessary contract from the pinned upstream cases and inspect current package coverage before declaring a kernel deficiency. A missing unit equation is package work; a missing physical type refinement, transform contract, temporal operation or native capability may need generic work. Implement the latter once with a small non-scientific witness, then demonstrate it through the real scientific case. The current model-composition owner already prescribes that sequence.[8](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/authoritative_design/sections/models-and-composition.md)

Prioritize vertical slices that reveal different responsibilities: a steady connected process; a recycle with initialization; a design/optimization variation of the same model; a reactive/property-sensitive process; a dynamic inventory process; a distributed process; and a multi-experiment fit. Choose the actual slices from the full parity inventory. Each should exercise reusable scientific definitions, user-visible admission/inspection, native execution and result qualification. Completion of those slices establishes their stated scope, not every combination of their features.

## 7. Principle traceability and acceptance questions

The selected standard is Core 3.4 with ProcessSimulator 1.5. Implementation applies those principles through concrete change scenarios using the existing review workflow; no new scoring system or review ceremony is required.[17](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/design_review/design_principles/standard.toml) [18](https://github.com/paul-heyse/pse-arrow/blob/19e7b49a67df24c1bf73005a6186e145e930d53a/docs/design_review/design_principles/core/design-principles.md)

| Principle | Consequence for this implementation | Useful acceptance question |
| --- | --- | --- |
| AP-04, DP-01, DP-04 | One scientific source; semantic identity distinct from presentation and revision | Can a renamed unit retain its identity while the process view updates without a second edit? |
| AP-03, DP-06, DP-16 | Ordinary scientific variants stay local to packages | Can a new unit using existing physics be authored without new Rust/schema/store machinery? |
| DP-02, DP-03, PS-01–04 | Typed physical meaning, explicit roles and context-specific structural checks | Does an incompatible basis/datum/phase connection fail at its owning boundary, with attribution? |
| DP-07, DP-12, PS-05/08 | Distinct topology, incidence and computational procedure | Can the same recycle topology support different admitted initialization/solve procedures without changing plant facts? |
| DP-08/11, PS-06/07/09 | Explicit approximation, guards, derivative capabilities and native ownership | Are domain restrictions preserved through lowering and are unsupported routes explained truthfully? |
| DP-09/10, AP-07, PS-11 | Reuse compatible structure, bind changed values, cross boundaries in batches | Does an operating sweep reuse preparation without hiding changed scientific dependencies or per-scalar storage work? |
| DP-18–21, PS-10 | Pure preparation, owned attempts, explicit recording and outcomes | Can local exploration and durable recording use the same retained source without hidden effects or false completion? |
| DP-22–24, PS-12/13 | Scoped evidence, independent physical checks and explicit contract evolution | Can each equivalence claim identify its formulation, comparator, tolerances, conditions and remaining limitations? |

The expected benefit is extension locality and a clearer authoring experience over current numerical capabilities. That benefit is a hypothesis until the selected journeys demonstrate it. Architectural adequacy, scientific equivalence, numerical integrity and assembled deployment/performance qualification should have separate conclusions. Source inspection supports the owner map and named gaps above; it does not establish a new passing parity suite.
