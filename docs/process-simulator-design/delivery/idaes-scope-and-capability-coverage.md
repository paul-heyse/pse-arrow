# IDAES scope and capability coverage

Source: [Notion](https://app.notion.com/p/40b141b58369816da914e9105c02717c). Imported 2026-11-02.

[Implementation design and IDAES equivalence plan](index.md)

**Status: Adopted scope contract; P0 resolves the complete versioned case/configuration population.** Source review only; no upstream or native builds, notebooks, solver runs, or parity tests were executed. The companion Reference case register contains the exact 55 documented notebook families and separate held/archive entries.

## 1. Define a finite, inspectable target

The implementation goal is: **users can author the supported IDAES process models and studies in native pse-arrow form, with equivalent physical assumptions, parameterization, admissible configurations and scientifically qualified results.** Python class names, inheritance, object lifetimes and notebook mechanics are reference implementation details. A reference harness may run IDAES separately without turning Python into the product architecture.

The adopted cross-industry constraints guide how this finite target is implemented. They preserve broader material, operating and capability meanings without changing the pinned release population. Additional industry libraries or cases enter delivery scope only through an explicit finite selection in the existing plan. See [Cross-industry domain contracts](../process/cross-industry-contracts.md) and [Industry coverage and expansion strategy](industry-coverage-and-expansion.md).

Freeze three independent inputs:

| Input | Frozen revision | Role |
| --- | --- | --- |
| IDAES core 2.13.0 | 84532d7f99a9f976b05170948147afdd69cfa5f6 | Released model, property, study and utility behavior |
| IDAES/examples | eb64e38ac429b7e3ae4f8db071f8d8cad2eef675, 2026-10-30 | Modern worked examples and their local modules/data |
| IDAES/idaes-compatibility | 8f1ae7a3ca358625128a78722bc2fdb75753a441, 2026-09-09 | Supplementary API-behavior, scientific-verification and robustness evidence |

The examples package identifies itself as 2.10.0 at this snapshot and does not pin its optional IDAES dependency to 2.13.0. Its development instructions use core development sources. Consequently, “the latest examples pass with 2.13” is a hypothesis requiring qualification, not a fact established by the release number. Freeze the complete reference environment, local modules, datasets and external artifacts; record incompatibilities instead of silently switching versions. [Core package](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/pyproject.toml) [Examples package](https://github.com/IDAES/examples/blob/eb64e38ac429b7e3ae4f8db071f8d8cad2eef675/pyproject.toml) [Examples development](https://github.com/IDAES/examples/blob/eb64e38ac429b7e3ae4f8db071f8d8cad2eef675/README-developer.md) [Compatibility scope](https://github.com/IDAES/idaes-compatibility/blob/8f1ae7a3ca358625128a78722bc2fdb75753a441/README.md)

The old IDAES/examples-pse repository is archived and directs users to IDAES/examples. Treat it as historical provenance and a source for explicitly selected legacy cases, not an additional current release. Modern examples already carries an archive. [Legacy repository](https://github.com/IDAES/examples-pse)

A full claim has three tracks: **process models and studies**, **native user/extension workflows**, and **supplemental whole-release applications**. Grid integration belongs in process studies; MatOpt materials-design capabilities belong in the supplemental track. Deferring MatOpt is reasonable for a flowsheet product, but the eventual claim must say whether it covers the whole release or the process-modeling scope.

### Thermodynamics is a major implementation program

A thermodynamic library adapter cannot by itself establish parity. Capture the actual EOS variant, binary interactions, component-property correlations, formation quantities, reference state, phase root, smoothing and parameter values. PR, NRTL, eNRTL and Helmholtz models are different scientific models; substituting an available EOS changes the target problem.

The release provides six modular state formulations, including FpTPxpc, which is easy to miss in older documentation. Modular transport includes Chapman–Enskog/Chung/Eucken component methods and Wilke/WMS mixtures; pure-component correlations include NIST, Perry and RPP families. eNRTL introduces electrolyte composition and reference-state requirements. These capabilities must be explicit in the provider contract and in case specifications and retained reference records. [State definitions](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/models/properties/modular_properties/state_definitions) [Pure properties](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/models/properties/modular_properties/pure) [Transport](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/models/properties/modular_properties/transport_properties) [eNRTL](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/models/properties/modular_properties/eos/enrtl.py)

Reaction coverage also needs specificity: the source includes Arrhenius rate constants and power-law rates; constant, van ’t Hoff and Gibbs-energy equilibrium constants; power-law/log forms and solubility-product/log-solubility forms; and constant reaction enthalpy. Those methods are extendable building blocks, not evidence that every imaginable rate law is preimplemented. [Reaction library](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/models/properties/modular_properties/reactions)

Helmholtz properties use upstream external functions; native code may use another implementation if it reproduces the required equations, reference conventions and derivatives. The compatibility suite provides separate water/CO2 liquid, vapor, saturation and supercritical datasets, plus eNRTL and PR checks. The Haber–Bosch PR verification explicitly handles reference-state alignment and discusses limitations of its independent comparison. This is a useful model for scientifically honest acceptance. [Helmholtz guide](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/docs/reference_guides/model_libraries/generic/property_models/helmholtz.rst) [Verification cases](https://github.com/IDAES/idaes-compatibility/tree/8f1ae7a3ca358625128a78722bc2fdb75753a441/src/idaes_compatibility/verification/properties) [PR verification](https://github.com/IDAES/idaes-compatibility/blob/8f1ae7a3ca358625128a78722bc2fdb75753a441/src/idaes_compatibility/verification/properties/test_haber_bosch_validation_PR.py)

### Advanced studies must retain their actual mathematical meaning

IDAES supplies dynamic/control examples, Caprese NMPC components and CSTR examples; its MHE documentation still says that an MHE module is forthcoming. MHE can be a desired pse-arrow extension, but should not be described as delivered 2.13 parity. Multiperiod studies link models across periods with coupling/rate constraints; they are not the same as integrating a dynamic process model. Grid studies add pricing, bidding, tracking, representative periods and commitment decisions. [Caprese examples](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/apps/caprese/examples) [MHE status](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/docs/explanations/modeling_extensions/caprese/mhe.rst) [Multiperiod](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/docs/reference_guides/apps/grid_integration/multiperiod/index.rst) [Grid applications](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/apps/grid_integration)

Parameter estimation and reconciliation are documented workflows using parmest or an explicitly constructed composite optimization model. Core uncertainty propagation concerns estimated-parameter covariance and local sensitivity of optimized outcomes; broad Monte Carlo, robust optimization or Bayesian estimation should not be assumed from that module name. [Estimation workflow](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/docs/how_to_guides/workflow/data_rec_parmest.rst) [Uncertainty application](https://github.com/IDAES/idaes-pse/tree/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/apps/uncertainty_propagation)

For surrogates, independently inventory training, persisted artifact format, evaluation, embedding, scaling/domain and optimization formulations. ALAMO training requires its separately licensed external tool; a saved algebraic surrogate has a different runtime dependency. The shipped ONNX adapter offers smooth, reduced-space and ReLU formulations, while its standalone evaluate\_surrogate method is unimplemented. Coverage must describe supported behavior rather than promising every method by association. [ALAMO guide](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/docs/explanations/modeling_extensions/surrogate/api/alamopy/index.rst) [ONNX implementation](https://github.com/IDAES/idaes-pse/blob/84532d7f99a9f976b05170948147afdd69cfa5f6/idaes/core/surrogate/onnx_surrogate.py)

Keep those three purposes separate in the native acceptance register: public behavior, physical verification and convergence evidence are different obligations. Configuration closure requires more than comparing default constructors. Extract the supported categorical choices and their restrictions: dynamic/steady and storage; material/energy/momentum balance types; property and reaction package compatibility; number and direction of ports; phase behavior; flow basis and state coordinates; heat-transfer/pressure-loss assumptions; spatial schemes; and alternative design/operating specifications. Record forbidden combinations as contract checks. Continuous operating ranges cannot be exhaustively enumerated; define admissible domains and scientifically motivated boundary/interior campaigns. Do not label an arbitrary sampling campaign as proof over an unbounded domain.

Native extensibility is itself a requirement. The custom-property, custom-reaction, custom-unit and skeleton examples demonstrate the need to add constitutive equations, parameters and observables without modifying a closed enum of known equipment. Utility workflows also need equivalents for degrees of freedom, scaling, homotopy/initialization, serialization of initial states, parameter sweeps, stream/result tables and diagnostic provenance. Their Python mechanics can change, but the engineer must retain the ability to build, inspect, initialize, solve and reuse a custom process model. ## 5. Explicit boundaries and remaining work

DMF is unsupported starting with IDAES 2.6; the 2.13 workflow guide says so. Current UI documentation still links Flowsheet Visualizer, and the release retains optional UI dependencies, so a blanket claim that UI is deprecated would be incorrect.
