# ADR-0215: Resolve physical models and compose demanded library execution

## Context

The integrated review and audit identify repeated source reconstruction, locator publication,
scientific policy and lifecycle interpretation. The operator accepted RC01–RC21 and authorized
49b–49h execution after the completed MX1.0/gRPC store. The operator also selected retention
of the bounded native-child experiment and retirement of the unconsumed relation canonicalizer
(I24). This publication precedes dependent implementation.

## Scope

Amend the cited architecture sections for the remaining Plan49 target, including resolved
semantic representation, body/derived identities, physical Python inputs, covariance and
result publication. This supplements retained mathematical/substrate rationale. Accepted ADR
text/status stays immutable; formal acceptance/supersession remains in the decision-PR route.
Plan49 owns implementation, findings, inquiry outcomes and qualification.

## Drivers

Carry physical meaning once into library mathematics; preserve guards, source attribution,
selected derivatives and original-space qualification. Support finite live-root reuse, one run
lifecycle, one document catalogue and one protected result interpretation across Rust, Python,
workers and operator consumers without another daemon or commit authority.

## Options

Keep existing source/name reconstruction, per-row locators and host orchestration, or compose
resolved semantic products, Symbolica regions, DataFusion pruning/residuals and shared runtime
contracts. Select the latter to remove repeated interpretation and row-shaped writes. A project
arithmetic interpreter duplicates libraries and is excluded. Optional mechanisms require a
reached owner and demonstrated semantic/ownership fit; no universal speedup is asserted.

## Outcome

- Modeling owns immutable resolved symbols, lexical binders, finite membership, physical
  contracts and source occurrences. Identity owns domain/version-separated local-slot body
  and derived frames; instance binding is separate. Symbolica/Numerica own admitted arithmetic,
  normalization, derivatives and evaluation. This replaces the direct-AST/no-resolved-product
  restriction while retaining library mathematical authority.
- Demanded arithmetic regions preserve ordered guards, applicability, lazy branches, fallible
  providers and source checks. Deterministic preflight selects before differentiation; transient
  failure/cancellation cannot change retained arithmetic. Interpreted clones and compiled shared
  code/private scratch keep their actual accounting and conservative numerical profile.
- Salsa count capacities and finite live-root/backdating admission replace routine reference
  rotation. Keep actual shared-root metadata accounting. Compiler annotation/view products and
  pure study-start policy have one semantic owner and every relevant consumer migrates.
- One supervisor pairs native dispatch/finish and owns inherited cancellation, progress,
  completion and join. Shared runtime request/admission/deployment replaces host interpretation.
  StudyOperation Version7 membership stays unchanged; parameter Fit/Simulation points use explicit
  starts and fresh IC/history. Explicit strategies retain their nondurable lifecycle exception.
- Native settings determine capability, map/recovery execution and separately admitted rungs.
  Preserve original residual/scaling/start permission, Uno SQP-LBFGS and its four declared
  numerical hunks; code5 is Numerical. FERAL pre-admission supplements post-factor enforcement.
  Partial allocator hooks retain complete envelopes; actual retained workers join before release.
- Exact admitted batch statistics and registry keys/fields replace scalar locators. DataFusion
  conservative pruning and residual-before-limit preserve original coordinates and full protected
  decode. Generated guarded functions own domain maintenance; privileged install/restore/activation
  remain a separate phase.
- Registry vocabularies/identity metadata and one direction-qualified document catalogue supply
  Rust/Python contracts and actual compiled schema identity. Keyed physical Arrow ingress gets
  operation-local membership/unit admission and immutable custody through native drain. Signed,
  precise physical time remains distinct from wall-clock budgets.
- Qualified fit covariance requires authoritative complete content/validity; external origin stays
  explicit. Scale-aware dimensionless faer PSD admission accepts singular covariance, refuses
  indefinite inputs and never certifies a clamped negative propagated variance.
- Product detail/result-selection contracts precede internal tooling extraction. Conformance
  defaults and cooperating-source launch execution get Rust owners. Optional cache, algebra,
  JIT/device, tracing/crate and allocator outcomes remain bounded inquiries.
- Retire only the unused relation canonicalization engine and dedicated API/tests. Preserve shared
  allocation/admission helpers, float canonical bits, framing and surviving content/encoding
  identities. Keep the native-child experiment opt-in and provider-free; do not expand it into
  another production execution route.

### Consequences

Migrate producers, consumers, generated surfaces and replaced mechanisms together. Regenerate
changed generated data through fenced fresh initialization; no backfill or compatibility path
is required. New data retains durable recovery/protected receipts. Existing native support and
scientific checks cannot be dropped to simplify integration.

### Compensating controls

Exact pins, explicit versions, finite admission, typed refusals and independent expectations
protect changed boundaries. Charges persist through actual native drain. Unknown durable effects
stay with immutable-receipt reconciliation rather than blind replay.

### Confirmation

The integrated review/audit support the selected target. Implementation/testing is not established
by this record. Plan49 records actual package/finding/inquiry outcomes and exact evidence limits.
Quantitative benefits require measurements at comparable workload and durability settings.

## Pros and cons

Removes repeated interpretation and metadata work while preserving library ownership; requires
coordinated representation/boundary migration and explicit native lifetime accounting.
