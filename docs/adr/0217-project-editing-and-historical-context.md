# ADR-0217: Compose project editing and historical context through exact source owners

## Context

Plan51a provides independent branch source heads, raw draft custody, exact publication and research references. Plan51b adds persistent editing and historical engineering selection without introducing another scientific model or preparation authority.

## Scope

New project navigation, immutable draft/savepoint, revision ancestry and historical context declarations within blueprint §20.5–§20.6. Public typed projections follow §21.1; preparation inspection follows §14.3.

## Drivers

Recover malformed work, preserve original operation identity through retries, compose nonoverlapping logical edits and retain original scientific consumption after later corrections. Passive inspection must not create evaluators or guess absent reuse evidence.

## Options

Compose existing SourceDelta, protected source/artifact readers, source activation and preparation owners. A second editor model, text merge authority, floating latest-context references and a separate preparation catalogue would duplicate their meanings and are not selected.

## Outcome

Stable project/branch identities are separate from presentation names. Draft heads select immutable raw versions; savepoints retain exact versions. Admission is explicit and publication uses the existing source CAS. Merge compares base/target/proposal by logical object; undo publishes a compensating revision.

Historical context uses UTC half-open effective intervals and a project-scoped recorded cut independent of source sequences and project membership generations. Corrections name ancestry; ambiguous overlaps refuse. Tombstones do not implicitly resurrect superseded values. Studies/fits retain exact selected context and scientific sources rather than re-running a latest query.

Preparation discovery observes existing resident products and persisted canonical product associations. Availability and receiving eligibility are separate; unknown causes remain unknown. It performs no compilation, solver run, provider transfer or recipe reconstruction.

### Consequences

Registry declarations generate the native installation and public documents. Runtime owns scientific admission and composition; metadata operations stay short and use native transactions. The minimal existing study/fit context bridge does not close Plan51c's wider catalogue/calibration scope.

### Compensating controls

Retained intents bind complete inputs, issuing authority and expected generations. Immutable acknowledgement settlement precedes later mutable draft/head checks. Selected payload readers retain their original protection; deletion visibility does not grant scientific closure release.

### Confirmation

Tested on Linux with the selected SurrealDB3.3.4/MX1.0 service, explicit Arrow force-validation and rebuilt Python correctness extension: Plan51b records 13 storage controls, 16 Runtime controls, five public Python/actual executable components and the actual historical native-fit receipt control. Independent bounded static rechecks found no remaining material blocker in the repaired boundaries. Plan51b owns the exact commands and conditions; Plan51g owns assembled qualification. No performance benefit or ADR acceptance is claimed.

## Pros and cons

Reuses current scientific authority and avoids long-open editing transactions; requires explicit version, ancestry and recorded-cut metadata and truthful limits on passive eligibility evidence.
