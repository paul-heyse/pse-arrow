# ADR-0112: Keep operational state and the publication catalog in PostgreSQL 18 through pse-operations

## Context

Delta publication is the only durable state today. Runs, jobs, progress, warm starts and
sessions live in memory and are lost on exit; admission refuses rather than queues, within one
process; publication is qualified for one local writer (§26, register R-10), with a Delta
control table as the only publication record and OS lock files for retention
([architecture §9.1](../plans/22-solver-capabilities-architecture.md#91-why-an-operational-store-and-why-postgresql)).
ADR-0102's workloads need what that cannot give: long solves that survive a crash (S16),
studies across worker processes (S15), rolling horizons with frequent small records (S14),
warm starts reused across processes, and concurrent publication (S17). DP-19 requires planned,
running, completed, partial, stale, cancelled and failed to be distinguishable durably.
PostgreSQL 18.6 is installed locally (cluster `18/main`, port 5432), and the maintainer admitted
it beside Delta on 2026-09-27.

## Scope

Supersedes **ADR-0091** (publication contract) and **ADR-0016** (D13) and restates the parts of
each that remain in force. Binds the store's role and authority, the new crate, the attempt
lifecycle, the job queue, the catalog commit, reader protection and retention, durability
classes, deployment and failure behaviour. Amends D10 and the §25 limits on multi-writer,
remote-store and multi-process execution. Existing Delta publications are not imported; they
are regenerated by rerun (maintainer, 2026-09-27).

## Drivers

- **DP-19.** Explicit, durable lifecycle; one commit boundary; idempotent retries.
- **DP-20.** Coordinated leases, queues and cancellation across processes.
- **DP-01.** One authority per fact across two stores.
- **DP-04.** Attempt identity is minted once.
- **DP-24.** Versioned job payloads and migrations.
- **AP-01 and AP-06.** The store is its own owner, with pure lifecycle rules testable without a
  database and isolated real databases for store tests.

## Options

| Candidate | Fit for mutable operational and control state | Selection |
|---|---|---|
| Delta only | Every small update is a commit plus files; no multi-table transactions, row locks, queues or notifications; single-writer qualification | Keep for data; rejected for control state |
| SQLite | One writer per file; no cross-host access, `SKIP LOCKED` or `LISTEN` | Rejected |
| Embedded key-value (redb, sled) | Single process | Rejected |
| Delta control table beside a PostgreSQL run registry | Two authorities for publication visibility (DP-01), or a registry that cannot coordinate multi-writer publication | Rejected |
| An in-memory fake of the store for tests | A second implementation of the contract | Rejected; `#[sqlx::test]` isolates real databases |
| **PostgreSQL 18** | Transactions and compare-and-set; `FOR UPDATE SKIP LOCKED`; advisory locks; `LISTEN/NOTIFY`; `uuidv7()`; mature Rust client (sqlx) | **Selected for the operational and control plane** |

## Outcome

**Retained from ADR-0091.**

1. Publication is an explicit effect after completion and never re-runs science; a
   scientifically failed attempt can still be published faithfully.
2. Members are written to immutable attempt-scoped Delta locations. Publication names an
   explicit expected parent and is never rebased. A serializable ticket carrying the attempt
   identity exists before any effect.
3. Conflict, uncertain completion and confirmed completion stay distinct. Settlement is
   read-only, inspects the attempt and its exact members, and an uncertain outcome never
   permits rematerialization.
4. Read-only reopening names exact versions and compatibility contracts; an unsupported
   historical format is a typed migration-required refusal, and opening never migrates.
5. Retention preserves the closure needed to reopen every retained publication.

**Retained from ADR-0016 (D13).** Cases and results never mutate the model. Initialization
stages, homotopy steps, fix-then-release, discrete fixing (ADR-0103) and disjunction lowering
(ADR-0104) are immutable overlays or derived preparation products with their own identity, and
an attempt records the overlay chain it applied. ADR-0016's revisit trigger (a native GDP
lowering that adds equations during a solve) does not fire: lowering happens at preparation.

**Replaced.**

6. **Visibility boundary.** One PostgreSQL catalog transaction replaces the Delta control row
   committed last. It checks that `publication_heads` names the expected parent, inserts the
   publication and its members (URI, exact Delta version, contract fingerprint) and advances
   the head. A lost race is a typed `Conflict`; the loser re-prepares against the new parent.
   The attempt identity is unique in `publications`, so settlement queries the catalog and
   returns `Committed`, `ProvedNoncommit` or `Conflict`; `Unresolved` remains only while the
   catalog is unreachable. Delta `SetTransaction` is no longer a settlement witness.
7. **Reader protection and retention.** Readers hold a lease row with an expiry, taken in a
   short transaction; no reader keeps a database session open while reading Delta files.
   Retention computes the protected versions in the catalog (SQL in `pse-operations`); deletion
   is two-phase — mark `expiring` (no new leases), wait until leases are released or expired,
   let `pse-catalog` delete the member files, mark `deleted` — and transaction-scoped advisory
   locks serialize maintainers. This replaces `.pse-retention.lock` and makes remote object
   stores qualifiable, which decides register row R-10.
8. **Confirmation of D13.** A cancelled or failed attempt is distinguished by its typed
   lifecycle state in `pse_ops.attempts` and in the published `runtime.computation_runs`,
   never by absent rows. `runs.status` no longer exists.
9. **No import.** Existing Delta publications are regenerated by rerun. A store written under
   the control table is an unsupported historical format and is refused with a typed
   migration-required diagnostic that says so. The Delta control table, its code and the file
   leases are deleted once the catalog path is proven (Plan 22 O8). An export command writes a
   read-only manifest from the catalog for offline readers.

**Added.**

10. **Division of authority (D10).** PostgreSQL owns what changes: attempts, jobs, leases,
    cancellation requests, live progress, incumbents and bounds, reusable solutions, study
    status and the publication catalog. Delta owns what is published: immutable member data.
    Published relations (`runtime.computation_runs`, `runtime.run_lineage`,
    `runtime.solve_metrics`, `runtime.incumbents`, study relations) are derived snapshots
    with identity. The registry (D1) owns the meaning of operational relations; SQL
    migrations are their physical representation, checked by a migration-conformance test.
    Enums are stored as text and parsed into registry types at the boundary; there are no
    database enum types.
11. **Crate `pse-operations`.** Owns the store contract, migrations, typed repositories, the
    catalog and reader leases, with errors deriving `thiserror` and `miette` with §23.2 codes.
    It depends on `pse-model`, `pse-schema` and `pse-diagnostics` for meaning; `pse-runtime`
    depends on it; no semantic or native crate does. `pse-catalog` keeps Delta member I/O and
    executes deletion and optimization when the catalog instructs.
    - **Client.** `sqlx` =0.9.0, used only in `pse-operations`, with `default-features = false`
      and features `postgres`, `runtime-tokio`, `tls-rustls-ring`, `macros`, `migrate`, `uuid`,
      `chrono` and `json`, matching the workspace's chrono, uuid and rustls/ring pins. The exact
      pin lives in `Cargo.toml`.
    - **Queries.** Runtime-typed only: `query` and `query_as` with `FromRow`. No `query!`
      macros and no `.sqlx` offline metadata. SQL stays SQL, in the repository modules.
    - **Migrations.** `sqlx::migrate!` embeds versioned `.sql` files with LF line endings.
    - **Connections and coordination.** `PgPool`; `PgListener`, which reconnects
      transparently, for cancellation and progress notifications; `PgAdvisoryLock`, or
      `pg_advisory_xact_lock` inside catalog transactions.
    - **Batches.** Typed batch inserts with `UNNEST($n::type[])`; `copy_in_raw` only if a
      measurement shows the need.
    - **Errors.** SQLSTATE 40001 (serialization failure), 40P01 (deadlock), 23505 (unique
      violation), 55P03 (lock not available) and 57014 (query cancelled) map into typed store
      errors; retry decisions read the type, never the message.
    - **Tests.** `#[sqlx::test(migrator = "pse_operations::MIGRATOR")]` against the local
      PostgreSQL 18 server gives each test an isolated database with library-owned cleanup; the
      `just` recipe maps `PSE_DATABASE_URL` to `DATABASE_URL` for test runs.
    - **Server features.** PostgreSQL 18 `uuidv7()` (for surrogate keys of rows without a
      runtime-minted domain identity; see 13), `FOR UPDATE SKIP LOCKED`, advisory locks,
      `LISTEN`/`NOTIFY` and `idle_in_transaction_session_timeout`. `pg_stat_statements` is
      optional, for measurement. No extension is required.
    - **Query surface.** Operational tables reach DataFusion sessions read-only. The mechanism
      is chosen at Plan 22 O9 between the ADBC PostgreSQL driver and typed row-to-Arrow builders;
      `datafusion-table-providers` is blocked by the one type universe.
12. **Lifecycle.** planned → queued → running → {completed, partial, failed, cancelled}; running
    → stale on lease expiry; a stale attempt is superseded by a new attempt. One pure Rust
    transition table in `pse-operations` is the only authority for legality and is testable
    without a database. Repository functions apply it inside a transaction under row locks. The
    database enforces the state-value domain (a `CHECK` from the registry values) and
    append-only history: the application role cannot update or delete `attempt_transitions`.
13. **Identity.** The runtime mints attempt, run and publication identities on its existing
    UUIDv7 `SemanticId` path before any effect; the store records them. Database defaults never
    mint a domain identity. Event rows are keyed by (attempt, sequence).
14. **Queue.** Jobs are claimed with `FOR UPDATE SKIP LOCKED`; a heartbeat extends the lease;
    expiry marks the attempt stale and requeues the job under an explicit retry policy (maximum
    tries, backoff); each try is a new attempt; publication is idempotent per attempt; an
    idempotency key is unique; job payloads are versioned and an unknown version is refused;
    source bundles are content-addressed by the §6.1 content hash. `MathService` queues durable
    work through the store instead of refusing.
15. **Cancellation.** `cancel_requested` is the authority. The heartbeat returns it, and
    `NOTIFY` only shortens latency: a worker issues `LISTEN`, commits, then re-reads state, as
    PostgreSQL's delivery rule requires. `PgListener::try_recv` returns `Ok(None)` when the
    connection was lost (notifications sent meanwhile are gone), and the worker re-reads state
    on every such return. Cancellation maps onto the existing cooperative cancellation lease.
16. **Durability classes.** `Ephemeral` — no store, in-memory queue and progress, cannot publish;
    for library calls and unit tests (AP-06). `Durable` — a registered attempt; may publish,
    queue, run studies or run long. The class is an explicit policy, never a fallback;
    publication without the catalog is refused.
17. **Streams and solutions.** Progress, incumbents and bounds are inserted in batches or with
    `COPY`, retention-bounded, and snapshotted into Delta at publication. Reusable solutions are
    keyed by the coordinate-compatibility stamp and the preparation identity; the seed identity
    enters lineage.
18. **Workers.** `pse-worker` is a binary target of `pse-runtime`, the composition root that
    already owns `MathService` and the workflows; a separate crate would hold only `main` and
    configuration. It sets the process-level OpenMP environment required by SPRAL (ADR-0108)
    at start-up.
19. **Scope of distribution.** Durable multi-process execution through the store — workers on
    one or more hosts claiming jobs — is in the design target. Distributing one solve across
    processes is not (ADR-0102).
20. **Deployment.** PostgreSQL ≥ 18 (locally 18.6, cluster `18/main`, port 5432); a login role
    `pse` (SCRAM) owning database `pse`, with `CREATEDB` for `#[sqlx::test]`; connection by
    `PSE_DATABASE_URL` or the libpq service `pse`; no credential is ever committed. Recipes
    `db-bootstrap` (idempotent, behind the outward-recipe confirmation), `db-migrate`,
    `db-status`, `db-backup` and `db-restore`; a doctor check for version, reachability and
    pending migrations; dump-based backups.
21. **Failure.** With the database unavailable, durable operations fail with the
    infrastructure class naming the connection target; ephemeral solves are unaffected; there
    is no fallback to Delta control. After a crash, leases expire, attempts become stale and
    unpublished members stay reclaimable through the catalog.

### Consequences

A database server is a deployment dependency for durable work. Publication, retention and
settlement code move from `pse-catalog` to `pse-operations` and `pse-runtime`. Existing local
Delta stores become unreadable until regenerated. §3.2, §20, §25, §26 and D10 change as the O
packets land.

### Compensating controls

The `Ephemeral` class keeps library use and unit tests database-free; the pure transition
table; `#[sqlx::test]` isolation; the migration-conformance test; typed infrastructure failures;
the offline export manifest.

### Confirmation

The tests named in `verification:` (Plan 22 O1–O9, G8). *Interface-checked* against the
PostgreSQL 18 documentation (`uuidv7()`, `FOR UPDATE SKIP LOCKED`, session- versus
transaction-scoped advisory locks, `LISTEN` taking effect at commit and the documented
listen-then-inspect rule), the sqlx `#[sqlx::test]` contract (a fresh database per test,
`DATABASE_URL` required for Postgres) and the crates.io metadata of sqlx 0.9.0,
`datafusion-table-providers` 0.13.1 and the ADBC crates (2026-09-27). Nothing is built yet.

## Pros and cons

PostgreSQL gives transactions, queues, leases and notifications that Delta cannot, and it makes
multi-writer and remote publication qualifiable with one visibility authority. The cost is a
server to deploy and operate and the loss of existing local stores, accepted because the system
is in design, not production.
