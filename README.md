# pse-arrow

An Arrow-native process systems engineering core in Rust: typed relations as the only
model authority, a relational math IR, DataFusion-based inference, native NLP solving,
and a generated Pyomo backend. Python package `pse-arrow` (import `pse`).

**Status: phase 0 — foundations.** The repository is being seeded: the authoritative
design, the decision records, the toolchain, and the CI graph land before any solver
runs. No published release yet; `0.0.1` is a placeholder version and nothing here is
API-stable.

## Relationship to IDAES

`pse-arrow` is a **clean-room re-implementation** of core IDAES-PSE capabilities. It is
**not affiliated with, endorsed by, or derived from** the IDAES project or its sponsors.
`external/idaes-pse` (fetched, never vendored) is read to understand *behaviour*; source
is never copied. The only durable coupling is the parity harness, which pins
`idaes-pse==2.12.0` and compares numerical trajectories; moving that pin requires an ADR.
A small set of enumerations is preserved by name for interoperability, and those are
listed explicitly in the blueprint.

See [`docs/relationship-to-idaes.md`](docs/relationship-to-idaes.md) for the full
statement: the clean-room rule, the parity pin and how it moves, the trademark and
non-affiliation notice, and the citation of the IDAES paper.

## Quick start

```bash
just doctor      # report what is missing, without touching the network
just bootstrap   # install the pinned toolchain, tools, and environments
just --list      # the command surface — this list is the contract
```

`just --list` is the contract: every gate a pull request must pass has a recipe, grouped
by cost tier (`env`, `discovery`, `local`, `pr`, `scheduled`, `decisions`, `mutating`).
Mutating recipes are `[confirm]`-guarded and are never a gate dependency.

## Layout

```text
crates/pse-*/          Rust workspace crates (relations, math IR, passes, backends, …)
crates/pse-ipopt-sys/  Ipopt FFI; bindings generated by `cargo xtask codegen`
xtask/                 repo logic that needs Rust APIs (codegen, family-check, doc-lint)
benches/               criterion benchmarks
tests/                 governance | engine | conformance | lifecycle | structural crates
tests/golden/          golden stores and fingerprints (data, not a crate)
python/pse/            the `pse` package: contracts (generated), codec, adapters, parity
packages/reference/    shipped reference packages
docker/solvers/        the pinned Ipopt + MUMPS + ASL container recipe
docs/                  the mdBook source and everything authoritative (see below)
scripts/               stdlib helpers: doctor, bootstrap, adr, register, generated checks
.github/               CI workflows, issue forms, and the declared repository settings
```

## Where authority lives

| Question | Authority |
|---|---|
| What the system is and how it is structured | `docs/authoritative_design/blueprint.md` |
| Why a decision was made | `docs/adr/` (index: `docs/adr/README.md`) |
| What is deferred, and what re-opens it | `docs/adr/register.md` |
| What versions are pinned | `Cargo.toml`, `Cargo.lock`, `pyproject.toml`, `uv.lock` |
| What a library can actually do | `docs/capability-maps/` and its `evidence/` |
| How work is sequenced | `docs/plans/` |
| How to contribute, and when an ADR is required | `CONTRIBUTING.md`, `GOVERNANCE.md` |

Design reviews are evidence, not authority. When the code and a plan disagree, the code
is what runs.
