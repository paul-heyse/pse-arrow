Source: `src/config.rs:1196`. [Exact documentation build](https://docs.rs/crate/datafusion-common/55.1.0/json).

(reading) If true, parquet reader will read columns of
physical type int96 as originating from a different resolution
than nanosecond. This is useful for reading data from systems like Spark
which stores microsecond resolution timestamps in an int96 allowing it

nanosecond resolution.

## coerce_int96_tz

`struct_field` · `datafusion_common::config::ParquetOptions::coerce_int96_tz` · datafusion-common 55.1.0

```rust
coerce_int96_tz: Option<String>
```

Source: `src/config.rs:1196`. [Exact documentation build](https://docs.rs/crate/datafusion-common/55.1.0/json).

(reading) Optional timezone applied to INT96 columns when `coerce_int96`
is set. When `Some`, INT96 columns coerce to
`Timestamp(<coerce_int96>, Some(<tz>))` instead of the default
`Timestamp(<coerce_int96>, None)`. Spark and other systems write INT96
values as UTC-adjusted instants, so callers that need the resulting
Arrow type to be timezone-aware (e.g. for Spark `TimestampType`
semantics) should set this to `"UTC"`. No effect when `coerce_int96`
is `None`.

Source: `src/config.rs:1196`. [Exact documentation build](https://docs.rs/crate/datafusion-common/55.1.0/json).

Maximum number of values in an `IN (...)` list for which pruning will
occur. Longer lists will not be used to prune files, row groups, or
data pages.

Higher values help in cases such as filtering on a list of

evaluate. Set to 0 to disable `IN (...)` list pruning entirely.

## max_row_group_bytes

`struct_field` · `datafusion_common::config::ParquetOptions::max_row_group_bytes` · datafusion-common 55.1.0

```rust
max_row_group_bytes: Option<MaxRowGroupBytes>
```

Source: `src/config.rs:1196`. [Exact documentation build](https://docs.rs/crate/datafusion-common/55.1.0/json).

(writing) Target maximum size of each row group in bytes. When set,
the writer flushes whenever either this limit or `max_row_group_size`
is reached, whichever comes first. Useful for bounding writer memory
on wide schemas where a row-count limit can map to very different
byte sizes. Matches the behavior of `parquet.block.size` in
parquet-mr. If `None` (the default), only the row-count limit
applies. Currently only honored when `allow_single_file_parallelism`
is `false`; by default the parallel file writer ignores this limit.

(reading) If specified, the parquet reader will try and fetch the last `size_hint`
bytes of the parquet file optimistically. If not specified, two reads are required:
