# Review library leverage options

Recommend the best ways to address selected codebase opportunities. Use the opportunity account
and accumulated library applicability as challengeable inputs, then investigate enough to judge
complete options and their interactions. The result is a comparative judgment and bounded target
recommendation that subsequent design and planning can use.

## Output in this repository

Maintain the living comparative review account under docs/library_leverage/reviews/, starting
from its [entry page](../../../docs/library_leverage/reviews/README.md) and adding coherent topic
pages. The first real review identifies its consumed assessments. Shared additional-pattern definitions belong in
docs/library_leverage/assessment-patterns.md, created with the first useful addition.

## Establish the decision and inputs

Read the [repository framework](../../../docs/library_leverage/library-leverage-framework.md), [shared language](../../../docs/library_leverage/references/shared-language.md),
selected opportunities, relevant library types and contextual assessments, and the current review
account. Establish the source state, consumed publication revisions and library realizations
being assessed. Reconcile consequential changes before relying on inherited conclusions.
Read the shared additional-pattern output when present. Relevant output patterns and base
patterns have the same role in the review's working set; prior manual promotion is unnecessary.

Load the governing design principles, relevant heuristic guidance and profiles through the host's
declared standard. The opportunity-pattern framework supplies recognition and explanatory leads;
the governing standard and intended outcomes guide design judgment. This skill does not initiate
a broad diagnostic audit or automatically fulfill a formal review required by the host's cadence.

Keep the requested scope clear: an opportunity, coherent group, subsystem or current opportunity
set. Judge enough adjacent consumers and interactions to support the decision. Relevant existing
plans explain accepted work and current execution boundaries; they do not make a candidate best.

## Challenge and develop the options

Inspect decisive code, contracts, callers and constraints yourself. Ask whether the opportunity
still has value, whether current behavior is promised or incidental, and whether a different
boundary would expose a better solution. An earlier applicability conclusion can be incomplete
or mistaken. Current assessed types are useful knowledge, not a closed set of admitted candidates.

Consider whether comparing complete options exposes a missing or insufficient pattern framing.
Record or refine useful additional patterns in the shared assessment output and apply them to
the affected reasoning, coordinating corrections with earlier accounts. Definitions belong in
outputs; changes to skill or base pattern guidance remain separately selected manual maintenance.

Compare credible complete options. Include existing repository capabilities, applicable library
features and combinations, configuration or native extension, version moves, native system
functionality and deliberate custom realization where relevant. Existing dependencies deserve
early consideration without becoming a rule that blocks a better mechanism. Avoid an exhaustive
cross product or a fixed number of alternatives.

Research deeper capability semantics and composition when they could change the choice. Use the
host's overview, Context7 and primary-source routes; preserve recognizable APIs/features, why
they matter, version conditions and evidence. Direct new research is permitted. Communicate
corrections and new reusable knowledge for integration into the library collection without making
another scheduled assessment pass a prerequisite to finishing the judgment.

## Make the comparative judgment

Explain why an option best serves the intended operation and consumers. Consider the relevant
semantic fit, domain authority, ownership, composition, change locality, isolated reasoning,
execution, failure/recovery and total developer/operator machinery. Compare preparation, normal
use, growth and credible failure far enough to expose material tradeoffs. Reason qualitatively;
quantitative performance claims need measurements. Probes serve consequential questions rather
than a required review ritual.

Challenge a consequential recommendation with a revealing legitimate case. Could it erase a
distinction, reject valid work, weaken a guarantee, obscure effects or move policy to the wrong
owner? Establish a credible physical route and preserve useful native optimization capabilities
across boundaries. A simpler declaration alone does not establish a simpler complete system.

Develop a bounded target: concrete enabling mechanisms, responsibility boundaries, domain rules
retained, intended behavior changes, consumer integration, important residual work and machinery
that can disappear. Include transition feasibility where it changes the choice. Detailed work
packages, schedules and execution acceptance belong to later planning.

Recommend retaining current code when its complete case is strongest. Reject a mistaken premise
when evidence warrants it. If a decisive condition remains unsettled, preserve the competing
options, consequence and suitable settling evidence instead of forcing a winner. Explain rule
impacts through existing decision routes; the recommendation does not silently apply them.

## Synthesize a coherent set

Use the original opportunity IDs and group related decisions when they need joint reasoning.
Explain shared prerequisites, reinforcing mechanisms, competing options and conflicts. A series
of locally attractive choices can introduce duplication or incompatible lifecycles when composed.
Keep consequence-based priority distinct from prerequisite order.

Use the [collection-writing guide](../../../docs/library_leverage/references/collection-writing.md) for flexible presentation.
The review entry page owns the current synthesis and routes to fuller comparisons. Keep enough
premise near the judgment to make it readable; cite the source assessments and precise library
evidence rather than duplicating their detailed accounts.

## Maintain and hand off

Refresh the review in place with its input scope, source/library baselines, dates and material
limits. Inherited judgments retain their original evidence dates until reconsidered. Reopen a
choice when its decisive premises change. Git holds earlier judgments; no per-pass directory or
growing status history is required.

Keep the current recommendation while it informs an opportunity or downstream decision. Link
accepted plans for scheduling and closure evidence instead of maintaining another execution
ledger. When opportunities retire, carry surviving mechanism rationale and obligations into their
proper owners and reconcile current links before retiring a review that loses its last reader.

Deliver the comparative conclusions, bounded targets, material alternatives, evidence limits
and next consequential decisions, including the route to additional patterns collected or refined.
The review entry page routes to the shared pattern output. Identify any further functional or
formal architectural review required by the host's existing routes, without automatically starting it. A strong result enables
an informed choice and subsequent design/planning; it does not authorize product changes or
accept implementation scope.
